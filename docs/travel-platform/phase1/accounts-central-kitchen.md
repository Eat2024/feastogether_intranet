## 概述

- 這份是「庫存驗收系統」（央廚驗收系統）的帳號管理 PRD，不是旅遊平台的需求。頁尾標示「庫存驗收系統 — 帳號管理 PRD v1.0 ｜ 2026-06-23」。旅遊平台沿用這套程式，但改了不少規則，旅遊平台版的需求見 [accounts.md](accounts.md)。兩版的關係見〈與另一版本的差異〉。
- 目的：讓驗收系統有一個管理「在職同仁」帳號的地方。管理員在這裡集中管理系統帳號、指派角色、啟用或停用帳號，人員異動時，系統存取權限跟著即時調整。
- PRD 列出的核心價值：
  - 帳號和 HR 在職狀態連動，離職人員不會留有系統存取權。
  - 集中管理各角色帳號，能快速看出各部門的人數與狀態。
  - 支援批次建立帳號，減輕大量人員上線時的行政負擔。
  - 密碼初始化流程標準化，減少同仁忘記密碼造成的維運成本。
- PRD 列出的上線目標：
  - 支援 100 位以上同時使用的使用者。
  - 帳號與 HR / OAuth 中心完成同步串接。
  - 管理員能自己啟用、停用帳號與重設密碼，不必找後台工程師。
- 使用者：只有「管理員」角色能操作帳號管理（可新增、可停用、不可刪除）；其他角色沒有帳號管理權限。
- 帳號來源原則：以 HR 系統的在職狀態為準，經 OAuth 中心同步到本系統。帳號不能手動刪除，只能停用。
- 選單位置：首頁 / 權限管理 / 帳號管理。
- 左側選單（依截圖）：系統名稱「庫存驗收系統」，選單有「央廚驗收」（驗收單查詢、驗收完成項目查詢）、「物料資訊」（新增物料規格異動通知、物料規格異動查詢、新增特殊允收天數、特殊允收天數查詢）、「權限管理」（角色管理、帳號管理），其餘是「選單名稱」佔位。

## 功能需求

- **ACCT-CK-01** 只有角色為「管理員」的帳號能使用帳號管理，入口在「首頁 / 權限管理 / 帳號管理」。
- **ACCT-CK-02** 進入列表時預設顯示第一個 Tab（管理員）。
- **ACCT-CK-03** 每個 Tab 標題顯示該角色的帳號總數（含停用帳號），數字要與資料庫的帳號數一致。
- **ACCT-CK-04** 列表預設依工號遞增排序。
- **ACCT-CK-05** 狀態欄：啟用帳號顯示藍色勾＋「啟用」，停用帳號顯示灰色禁止圖示＋「停用」。上次登入沒有值時顯示「－」。
- **ACCT-CK-06** 搜尋：可用姓名、工號搜尋，跨 Tab 生效（開放議題 #3 決議）；輸入關鍵字就即時篩選，清空後恢復完整列表。
- **ACCT-CK-07** 批次停用：勾選帳號後才能按。
- **ACCT-CK-08** 新增帳號：員工編號欄可輸入工號或姓名做模糊搜尋；選好員工後，事業部自動帶入，不能手動修改。
- **ACCT-CK-09** 密碼不符合 6–8 碼英數混合，或密碼與再次密碼不一致時，儲存前就顯示錯誤提示。
- **ACCT-CK-10** 權限（角色）必填、單選；沒選不能儲存。
- **ACCT-CK-11** 員工已經有帳號時，系統提示「該員工已存在帳號」，不讓重複建立。
- **ACCT-CK-12** 新增成功後，帳號出現在對應角色的 Tab，該 Tab 人數 +1。
- **ACCT-CK-13** 批次新增：PRD 第 3.3、3.4 節與 Story 2 寫「員工編號可多選，儲存後每位員工各建一個帳號，初始密碼都是預設密碼」；開放議題 #5 決議「本次暫不做批次新增，上線後有需要再增加匯入功能」。
- **ACCT-CK-14** 編輯帳號：從列表的編輯按鈕進入帳號設定；員工編號、事業部唯讀；密碼欄留空表示不修改。
- **ACCT-CK-15** 修改角色後，該使用者下一個請求就依新角色生效，舊角色的功能立即不能用；帳號移到新角色的 Tab，原 Tab 人數 -1、新 Tab 人數 +1。
- **ACCT-CK-16** 停用與啟用：在帳號設定頁用啟用開關切換。停用後，該帳號所有 session 立即失效，下一個請求回 401；停用的帳號不能登入，顯示「帳號已停用」；停用的帳號仍留在列表、計入 Tab 人數，狀態欄顯示停用樣式；停用的帳號可以重新啟用。
- **ACCT-CK-17** 帳號不能刪除：畫面沒有刪除按鈕；直接呼叫刪除 API 也會被拒絕（QA 預期回 405 或 403）。
- **ACCT-CK-18** 恢復預設密碼：管理員按「恢復預設密碼」並在確認視窗確認後，密碼立即重設為預設密碼；重設後，員工可用預設密碼登入。
- **ACCT-CK-19** HR 標記員工離職後，OAuth 同步會自動停用該帳號，既有 session 立即失效。同步頻率依開放議題 #1 決議「比照 Oauth，每日同步」。
- **ACCT-CK-20** HR 的事業部資料有異動時，下一次 OAuth 同步後自動更新。
- **ACCT-CK-21** OAuth 同步失敗時，系統發告警通知給管理員；通知方式尚未確認（開放議題 #2）。
- **ACCT-CK-22** 以下操作都寫入審計日誌：新增、修改、停用、啟用、恢復預設密碼、同步造成的自動停用。同步自動停用的操作人記為「系統同步」，不是管理員帳號；密碼重設的日誌不記錄密碼明文。

## 登入、員工資料來源與 OAuth

以下是本頁和登入、員工資料、OAuth 有關的原文重點。這些點和公司的 OAuth server（feastogether_oauth）直接相關。

- 帳號來源：HR → OAuth 中心 → 本系統。PRD 寫「帳號以 HR 系統的在職狀態為準，透過 OAuth 中心同步至本系統」。
- 員工基本資料：新增帳號選好員工後，「系統自動從 OAuth 帶入姓名與事業部」。也就是說，PRD 預期 OAuth 中心能提供員工清單（可用編號或姓名搜尋）以及事業部。
- 密碼：欄位表一方面要求新增時輸入 6–8 碼密碼，另一方面在「再次密碼」註明「密碼在 Oauth 不在此作業」；PRD 另外還有「預設密碼＝身分證＋生日」與「恢復預設密碼」功能。三者互相矛盾，見〈待釐清問題〉。
- 停用與登入：停用的帳號「不可登入，顯示『帳號已停用』」，已登入的 session 立即失效、回 401。
- 離職同步：Story 6 寫「HR 標記員工離職後，OAuth 同步觸發系統帳號自動停用」，QA 測試點寫「模擬 OAuth 推送離職事件」；開放議題 #1 決議「比照 Oauth，每日同步」。
- 同一份 PRD 的〈權限管理-角色管理 (央廚)〉第 3.1 節也寫：「帳號不可刪除，帳號來源為 Oauth，Oauth 同步來源為 HR。」

## 與另一版本的差異

**判斷：兩頁不是新舊版，也不是草稿與定稿，而是不同系統。**本頁是央廚驗收系統（庫存驗收系統）已有的帳號管理 PRD，旅遊平台把它當作沿用程式的基礎；〈帳號管理〉（[accounts.md](accounts.md)）才是旅遊平台的需求。旅遊平台沿用央廚的程式，但依自己的使用情境改寫規則。

判斷依據：

1. 本頁頁尾標示「庫存驗收系統 — 帳號管理 PRD v1.0 ｜ 2026-06-23」，Figma 檔名是「央廚驗收系統」。截圖的系統名稱是「庫存驗收系統」，選單有央廚驗收、物料資訊，Tab 是央廚人員、採購人員、門市人員，都不是旅遊平台的內容。
2. 〈帳號管理〉頁面寫「系統共用，拿程式 不出畫面，央廚系統延用」。它連結的《旅遊平台重構_PRD_帳號管理》在〈來源追溯〉寫「央廚驗收系統的帳號管理與角色管理（拿程式延用）」。
3. 該 PRD 的變更紀錄 v0.1 寫明參照「ClickUp〈權限管理-帳號管理 (copy)〉（央廚驗收系統 PRD）」，正文也多次引用「央廚版帳號管理 Story 2、Story 4、第 3.2、3.3 節」，章節編號和本頁一致。由此推斷，本頁原本叫「(copy)」，後來才改名為「(央廚)」。
4. 該 PRD 第 15 章列出風險「沿用央廚程式但規則不同」，附錄 A 用【差異】標出和央廚版不同的地方。

主要差異（完整對照表見 [accounts.md](accounts.md)〈與另一版本的差異〉）：

- 密碼：央廚版有密碼欄、預設密碼、恢復預設密碼；旅遊平台全部拿掉，登入走 OAuth，系統不存密碼。
- 停用效果：央廚版停用後就不能登入；旅遊平台停用只拿掉後台權限，同仁仍可登入投票、報名。
- 新增：央廚版「新增」可多選員工；旅遊平台改成「指派角色」，只能單選，選到已有帳號的同仁時直接進入該帳號的編輯頁。
- 旅遊平台新增了草稿狀態（草稿可刪除）、Email 欄位、分頁器、系統管理員保護規則，以及 HR 同步失敗時的重試與告警信。
- 搜尋：央廚版決議跨 Tab；旅遊平台建議只搜目前分頁。
- 批次操作：兩版都只做批次停用。央廚版截圖另有 ✓ 圖示，旅遊平台確定不做批次啟用。

## 待釐清問題

旅遊平台要沿用央廚程式，所以這些問題主要影響「央廚程式現在到底長什麼樣」。

1. **密碼規則前後矛盾**
   - 現況：欄位表要求新增時輸入 6–8 碼英數混合的密碼；預設密碼規則卻是 18 碼（身分證＋生日），超過 6–8 碼的上限；「再次密碼」又註明「密碼在 Oauth 不在此作業」；截圖的帳號設定頁沒有密碼欄，也沒有恢復預設密碼按鈕。
   - 要問：央廚現行程式有沒有密碼欄與恢復預設密碼？密碼存在央廚系統還是 OAuth？
2. **批次新增做了沒有**
   - 現況：第 3.3、3.4 節與 Story 2 都寫可多選、批次建立；開放議題 #5 決議本次不做；截圖的提示文字仍是「可多選」。
   - 要問：央廚現行程式的員工編號欄是單選還是多選？
3. **有沒有批次啟用**
   - 現況：文字只寫「批次停用」；截圖 Tab 列右側同時有 ✓ 與 ⊘ 兩個圖示。
   - 要問：✓ 是不是批次啟用？央廚程式有沒有實作？
4. **搜尋行為沒有定案**
   - 現況：第 3.4 節寫「待 PM 確認是否跨 Tab」，開放議題 #3 已決議跨 Tab；Story 1 的 QA 測試點「搜尋後切換 Tab，搜尋條件是否重置」仍註明要與 PM 確認。
   - 要問：跨 Tab 搜尋時，Tab 人數與列表怎麼呈現？切換 Tab 時要保留還是重置搜尋條件？
5. **列表欄位與截圖不一致**
   - 現況：PRD 欄位表從「工號」開始，沒有勾選框與姓名；截圖有勾選框與「姓名」欄。
   - 要問：以截圖為準嗎？
6. **欄位名稱不一致**
   - 現況：欄位表叫「權限」，截圖的表單欄名是「角色」；列表表頭則是「權限」。
   - 要問：名稱以哪個為準？
7. **列表截圖的麵包屑寫錯**
   - 現況：列表截圖的麵包屑是「首頁 / 權限管理 / 角色管理」，頁面標題卻是「帳號管理」；表單截圖則是「帳號管理」。
   - 要問：確認列表截圖的麵包屑是筆誤。
8. **工號排序方向**
   - 現況：PRD 寫預設遞增，截圖工號表頭是 ↓ 箭頭。
   - 要問：箭頭只是「可排序」的標示，還是代表遞減？
9. **帳號管理權限是固定的還是可設定的**
   - 現況：第 2 節寫「管理員」是唯一能操作帳號管理的角色；〈角色管理 (央廚)〉第 3.2 節的權限表卻有「帳號管理」可勾選的檢視、新增／編輯、刪除。
   - 要問：其他自定義角色能不能被授予帳號管理權限？
10. **離職同步的方式**
    - 現況：Story 6 寫「OAuth 推送離職事件」，開放議題 #1 決議「比照 Oauth，每日同步」。
    - 要問：是 OAuth 中心主動推送，還是央廚系統每天去拉？PRD 說的「OAuth 中心」是不是 feastogether_oauth？它要提供事業部嗎？
11. **停用時要顯示的訊息與 session 失效機制**
    - 現況：停用後要顯示「帳號已停用」，session 立即失效並回 401；PRD 註明 SA 需確認失效機制。
    - 要問：登入既然走 OAuth，「帳號已停用」要顯示在哪個畫面？
12. **啟用開關的生效時機**
    - 現況：Story 4 只寫「用開關切換啟用／停用」，沒寫是切換當下生效，還是按「儲存」後才生效。
    - 要問：哪一種？
13. **驗收條件前的 ✓ 標記**
    - 現況：Story 1、Story 2 的驗收條件前面多數有 ✓，Story 3–6 沒有。
    - 要問：✓ 代表已實作、已驗收，還是只是格式差異？
14. **告警方式與日誌保存期限**
    - 現況：開放議題 #2（同步失敗告警方式）、#4（審計日誌保存期限）仍未確認。
    - 要問：結論是什麼？旅遊平台 PRD 也把保存期限列為待法務確認。
