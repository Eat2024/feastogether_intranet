# Feature Specification: 舊授權清理與電子簽資料基礎

**Feature Branch**: `[001-auth-cleanup-schema]`

**Created**: 2026-10-12

**Status**: Draft

**Input**: User description: "Spec 1 不實作登入；保留 Auth 中未來移回主平台仍會使用的 SSO 串接，移除本系統不需要的 permission、role 等驗收系統舊功能，並建立 Stage 1 電子簽所需的 schema tables。"

## Clarifications

### Session 2026-10-12

- Q: Spec 1 要一次建立全部 12 類電子簽資料表，還是只建立下一個功能立即會使用的最小集合？ → A: 一次建立目前資料字典中的全部 12 類資料表。
- Q: 目前是否已有任何必須保留資料、不能重新建立的共用／staging／production 資料庫，套用過現有 Auth/RBAC migrations？ → A: 沒有，所有現有資料庫都可以重建。
- Q: 當文件允許拒絕簽署，而且其中一位簽署人拒絕時，整份文件接下來應進入什麼狀態？ → A: 其他人可繼續簽；所有簽署人都已簽署或拒絕後，文件仍可完成並註明拒絕結果。
- Q: 除了 role／permission，驗收系統移植來的使用者管理功能在 Stage 1 要保留到什麼程度？ → A: 移除全部使用者管理端點，只保留登入與內部流程需要的員工資料能力。
- Q: Stage 1 的簽署人是否只允許公司內部員工，還是也要支援以 Email／手機加入的外部簽署人？ → A: 支援內部員工與 Email 外部簽署人，包含尚未具員工身分的面試錄取人員；不支援手機外部簽署人。
- Q: 時間相關欄位的索引範圍為何？ → A: 十二張 Stage 1 資料表中的每個日期與時間欄位都必須建立單欄索引；既有複合索引不取代該單欄索引。
- Q: 移除 API permission registry 後，一般 API 如何決定是否需要登入？ → A: 所有未明確標示為公開的 API 都由全域 guard 預設要求有效員工 session；刪除 `RegisterApi` metadata。未來外部 Email 簽署使用獨立外部簽署 session，不建立假員工，也不能以裸公開端點直接簽署。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 清除不需要的角色權限功能 (Priority: P1)

系統維護者可以在不保留角色、permission、功能選單授權及相關管理功能的情況下建置並啟動系統；這些從驗收系統移植而來的功能不再影響電子簽系統的資料模型、啟動流程或後續開發。

**Why this priority**: 若先讓電子簽資料模型依賴舊角色權限架構，後續每個功能都會承接錯誤邊界，增加清理與遷移成本。

**Independent Test**: 在全新環境建立資料庫並啟動系統，確認沒有角色或 permission 資料也能完成啟動、健康檢查及既有基礎驗證。

**Acceptance Scenarios**:

1. **Given** 一個全新環境沒有任何角色或 permission 資料，**When** 系統完成初始化並啟動，**Then** 啟動與健康檢查成功，且不要求建立預設角色或權限字典。
2. **Given** 系統執行一般受保護流程，**When** 載入登入者身分，**Then** 不查詢角色、permission、角色權限關聯或功能選單授權資料。
3. **Given** 維護者檢查系統對外能力，**When** 搜尋角色管理、permission 管理與使用者權限配置入口，**Then** 不存在可被使用的相關頁面或端點。
4. **Given** 舊開發登入曾依賴管理員角色，**When** 清理完成後執行非正式環境驗證，**Then** 測試登入若保留也不再需要角色或 permission 才能建立一般員工 session。
5. **Given** 維護者檢查驗收系統移植來的使用者管理能力，**When** 搜尋員工查詢、批次匯入、啟停帳號與本地備註等管理入口，**Then** 不存在可被使用的相關頁面或端點。

---

### User Story 2 - 保留未來可復用的 SSO 串接 (Priority: P2)

系統維護者清理舊授權功能時，保留現有 SSO 串接、身分交換、員工識別、session 與登出相關能力，使未來功能移回主平台時可以重新啟用，而不必重新開發整套 SSO 流程。

**Why this priority**: SSO 雖然不是目前 WebView Stage 1 的登入方式，卻是已知的未來需求；它與角色權限是不同責任，不應在清理時一起刪除。

**Independent Test**: 在不啟用正式 SSO 入口的前提下執行現有 SSO 單元與契約測試，確認授權導向、回呼交換、員工編號對應、session 建立及登出能力仍可驗證。

**Acceptance Scenarios**:

1. **Given** 角色與 permission 功能已移除，**When** 執行 SSO 串接相關驗證，**Then** SSO 核心流程仍可獨立通過，且不依賴角色或 permission 資料。
2. **Given** 目前 Stage 1 尚未使用 SSO，**When** 系統在正式環境啟動，**Then** 不會因此自動開放或宣稱 SSO 已可供使用。
3. **Given** 未來主平台需要重新啟用 SSO，**When** 維護者檢視保留能力，**Then** 身分提供者串接、員工識別與本地 session 邊界仍清楚可用。

---

### User Story 3 - 建立電子簽資料基礎 (Priority: P3)

後續電子簽功能可以共用一套具明確關聯、狀態與證據邊界的資料基礎，涵蓋員工、部門、文件、欄位、簽署人、簽署證據、私有檔案中繼資料、稽核事件、公開驗證、通知及匯出工作。

**Why this priority**: 文件建立、簽署、驗證與匯出功能都依賴共同資料關係；先建立一致基礎，可避免每個後續 spec 自行定義不相容的資料結構。

**Independent Test**: 在空白資料庫套用資料結構後，建立一組只含必要欄位的員工、文件、簽署人與關聯證據測試資料，確認合法資料可建立、違反唯一性或關聯規則的資料會被拒絕，並可完整撤回。

**Acceptance Scenarios**:

1. **Given** 一個空白且符合版本要求的資料庫，**When** 套用 Spec 1 的資料變更，**Then** 所有 Stage 1 資料實體、必要關聯、唯一性規則與查詢索引均建立成功。
2. **Given** 一名員工與一份草稿文件，**When** 建立文件欄位及指定簽署人，**Then** 所有資料均能關聯至正確文件與員工，且同一員工不得重複成為同一文件的簽署人。
3. **Given** 一份已進入簽署流程的文件，**When** 嘗試把簽署證據或稽核事件當作一般可修改、可軟刪除資料處理，**Then** 資料模型不提供該操作語意。
4. **Given** 已成功套用的資料變更，**When** 在無新增業務資料的驗證環境執行撤回並重新套用，**Then** 可重建相同的乾淨基準，且 SSO 所需的員工資料結構仍完整存在。
5. **Given** 一份尚未另行設定選項的草稿文件，**When** 建立文件資料，**Then** 浮水印預設關閉且拒絕簽署預設開放。
6. **Given** 一份允許拒絕簽署的文件已有簽署人拒絕，**When** 其餘簽署人皆完成簽署且不存在待簽署人，**Then** 文件可進入完成狀態，並保留每位簽署人的已簽署或已拒絕結果。
7. **Given** 一名面試錄取人員尚未具公司員工身分，**When** 建立人以姓名與 Email 將其加入文件，**Then** 系統建立 Email 外部簽署人，不建立虛構員工資料，且同一 Email 不得重複加入同一文件。

### Edge Cases

- 全新基準不得建立角色或 permission 資料；員工資料只保留未來登入與電子簽需要的欄位。
- SSO 程式目前未啟用時，清理後仍須保持未啟用，不得因測試通過而自動註冊正式入口。
- 新增 endpoint 即使忘記任何授權 decorator，也必須預設要求有效員工 session；只有明確列為公開且具自身驗證責任的入口可以例外。
- 相同員工編號、文件公開編號、檔案物件鍵或驗證公開識別重複時，資料結構必須拒絕衝突。
- 日期或時間欄位即使已出現在複合索引的非首欄或首欄，仍須保有該欄位自己的單欄索引，不得因查詢尚未實作而省略。
- 文件已進入簽署中後，其簽署內容、欄位及簽署人不得原地改寫；實質變更建立新文件。
- 文件進入簽署中後，不得切換浮水印或是否允許拒絕簽署；實質變更必須建立新文件。
- 允許拒絕的文件有人拒絕時，其他簽署人仍可繼續；只要仍有待簽署人，文件不得完成。
- Email 外部簽署人與內部員工資料相同時不得自動合併；簽署人類型及發起當下身分快照必須保持明確。
- 外部簽署人 Email 大小寫不同但實際為同一地址時，不得藉此重複加入同一文件。
- 簽署證據、稽核事件與驗證紀錄不得因一般業務刪除或軟刪除而消失。
- 私有檔案尚未實際上傳時，不得留下宣稱檔案已成功持久化或封存的中繼資料。
- 資料變更套用途中失敗時，不得留下部分新結構或已被破壞的既有員工身分。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系統 MUST 移除 Stage 1 對角色、permission、角色權限關聯、功能選單授權及 API permission 登錄的執行期依賴。
- **FR-002**: 系統 MUST 不再提供角色管理、permission 管理或替員工配置角色／permission 的使用者介面與對外操作。
- **FR-003**: 系統 MUST 不要求預設管理員角色、角色種子資料或 permission 字典才能啟動及通過健康檢查。
- **FR-004**: 舊開發／測試登入若保留，MUST 與正式環境隔離，且不得再依賴管理員角色或 permission。
- **FR-005**: 現有 SSO 的授權導向、回呼交換、員工身分對應、本地 session 與登出能力 MUST 保留，不得因移除角色權限而刪除或失去可驗證性。
- **FR-006**: 本規格 MUST NOT 啟用 SSO、實作 WebView token 登入，或改變正式環境目前可用的登入入口。
- **FR-007**: 員工身分 MUST 成為登入、未來電子簽及稽核操作人的共同主體，且不得包含角色或 permission 關聯。
- **FR-008**: 乾淨基準中的員工資料模型 MUST 保留 SSO、session 與後續電子簽需要的識別及基本資料欄位，但 MUST NOT 包含角色或 permission 關聯。
- **FR-009**: 系統 MUST 建立部門、員工、電子簽文件、文件欄位、簽署人、簽署證據、私有檔案中繼資料、稽核事件、公開驗證紀錄、通知批次、通知明細及匯出工作共十二類 Stage 1 資料實體。
- **FR-010**: 每類資料實體 MUST 定義必要識別、業務狀態、關聯完整性、唯一性規則及支援已知主要查詢的索引需求。
- **FR-011**: 文件 MUST 具有不可預測且唯一的對外識別；員工 MUST 以唯一員工編號對應公司身分；同一員工在同一文件中最多只能有一筆簽署人指派。
- **FR-012**: Stage 1 不建立獨立文件版本實體；文件進入簽署中後，文件內容、欄位、簽署人與固定簽署參數 MUST 不可原地修改，實質變更須建立新文件。
- **FR-013**: 成功簽署 MUST 產生一筆與簽署人唯一對應的不可變簽署證據，包含實際文件摘要、固定簽署參數摘要、同意版本、身分驗證事件及簽署時間。
- **FR-014**: 稽核事件 MUST 採只追加模式，並保留同一文件內可偵測竄改的事件順序與摘要鏈；一般管理流程不得修改或刪除既有事件。
- **FR-015**: 私有檔案資料 MUST 只保存物件識別、版本、用途、類型、大小、摘要及封存狀態等必要中繼資料，不得保存永久公開網址或檔案內容。
- **FR-016**: 公開驗證紀錄 MUST 使用不可預測的公開識別，並能關聯完成文件摘要、最終檔案摘要與稽核根摘要；不得直接公開文件內容、簽名圖片或未遮罩個資；Constitution III 公開簽章驗證例外允許的簽署人完整姓名與文件標題除外（2026-10-16 修訂）。
- **FR-017**: 通知批次、通知明細與匯出工作 MUST 保存可追溯的處理範圍、狀態與結果，但不得保存包含個資的供應商完整回應或錯誤堆疊。
- **FR-018**: 所有業務時間 MUST 以一致的標準時間保存；員工、文件與可編輯設定採可稽核的建立／更新資訊，簽署證據與稽核事件不提供一般更新或軟刪除語意。
- **FR-019**: 所有檔案與摘要 MUST 由後續 Server 流程對實際持久化內容產生及驗證，不得把 client 提供的摘要視為最終可信值。
- **FR-020**: 資料結構變更 MUST 可重複套用於空白驗證環境，並提供安全撤回路徑；現有環境以重建乾淨基準為準，不要求提供舊 Auth/RBAC 資料的向前遷移。
- **FR-021**: 正式資料結構定義、應用程式資料模型、變更歷程與可檢視的 schema 快照 MUST 保持一致，不得各自漂移。
- **FR-022**: 本規格只建立資料基礎，MUST NOT 宣稱電子簽文件 API、簽署交易、檔案儲存、通知、匯出、公開驗證或前端串接已完成。
- **FR-023**: 每份電子簽文件 MUST 保存「是否在下載／匯出的已簽署 PDF 加入浮水印」及「是否允許簽署人拒絕簽署」兩項設定；前者預設關閉、後者預設開放，兩者 MUST 納入固定簽署參數並於文件進入簽署中後鎖定。
- **FR-024**: 當文件允許拒絕簽署時，拒絕只終止該簽署人的待簽義務，其他簽署人 MUST 可繼續；所有簽署人皆為 `signed` 或 `rejected` 且最終產物已建立後，文件 MAY 進入 `completed`，完成結果 MUST 明確區分已簽署與已拒絕者。
- **FR-025**: 系統 MUST 移除驗收系統移植來的使用者管理對外能力，包括員工查詢、批次匯入、啟停帳號、本地備註及角色配置；員工資料只由登入身分對應及後續明確核准的電子簽內部流程使用。
- **FR-026**: 只服務舊角色、permission 或使用者管理異動的通用稽核資料結構 MUST NOT 納入乾淨基準；登入安全紀錄與 `esign_audit_events` 各自維持其明確責任，不得沿用舊管理稽核模型。
- **FR-027**: Stage 1 簽署人 MUST 支援 `user` 與 `email` 兩種類型；`user` 必須關聯既有員工，`email` 必須保存外部簽署人的姓名與通知 Email，且不得因此建立員工資料。
- **FR-028**: 同一文件中的內部員工識別及外部簽署人正規化 Email MUST 各自唯一；每筆簽署人必須且只能符合其中一種識別方式。
- **FR-029**: 手機號碼外部簽署人不在 Stage 1 範圍；外部簽署人的存取與簽署仍 MUST 經後續功能規格定義的 Server 身分驗證，不得只憑 client 傳入 Email 認定身分。
- **FR-030**: 十二類 Stage 1 資料實體中的每個日期及時間欄位 MUST 建立專屬單欄索引；複合索引 MUST NOT 被視為取代該時間欄位的單欄索引。
- **FR-031**: 所有未明確標示為公開的 API MUST 由全域身分 guard 預設要求有效員工 session，且員工必須存在、啟用且未被軟刪除；系統 MUST 移除 `RegisterApi` metadata、API key 與以 route metadata 查詢 permission 的流程。
- **FR-032**: 未具員工編號的 Email 外部簽署人 MUST NOT 建立虛構員工或使用員工 session；其未來存取與簽署流程 MUST 使用獨立、限於指定 signer／document 的 Server 驗證 session，且不得只以公開路由或 Email 字串放行。

### Scope Boundaries

**本規格包含**：

- 移除角色、permission、角色權限、功能選單授權、API permission 登錄、舊使用者管理及其專用稽核功能。
- 解除員工身分、session、開發測試登入與啟動流程對角色／permission 的依賴。
- 保留但不啟用既有 SSO 串接與 session 邊界。
- 建立資料字典與 ER Model 定義的十二類 Stage 1 資料實體及其基本完整性規則。
- 在簽署人資料中支援內部員工與 Email 外部簽署人，但不支援手機號碼簽署人。
- 建立 SSO 與電子簽共用的員工身分資料結構，且不包含角色關聯。
- 建立可套用、可撤回且可核對的資料結構基準。

**本規格不包含**：

- 內網 WebView token 登入、SSO 啟用或任何新登入流程。
- 電子簽文件、簽署、通知、匯出或驗證 API。
- 前端電子簽 mock store 搬移至後端。
- 真實檔案上傳、object storage 串接、PDF 產製、簽名疊圖或證據包產製。
- 電子簽署前重新驗證、WebAuthn、MFA 或 OTP。
- Email 外部簽署人的邀請連結／邀請碼交換、Email 控制權驗證、驗證碼、外部簽署 session、專用 guard、登入體驗與重放防護；由後續外部簽署功能規格定義。
- 平台憑證、可信時間戳記、PAdES 或個人數位憑證。
- 獨立文件版本資料；Stage 1 採發起後鎖定，實質修改建立新文件。
- 部門／員工同步排程或多身分提供者綁定。

### Key Entities

- **部門**: 公司組織節點，可關聯上層部門及員工；停用或刪除不得破壞歷史關聯。
- **員工**: 登入、電子簽與稽核共用的唯一人員主體，以公司員工編號對應，不包含角色或 permission。
- **電子簽文件**: 文件案件、建立人、簽署期間、浮水印設定、是否允許拒絕簽署、固定簽署參數及流程狀態的主體；完成結果可同時包含已簽署與已拒絕者。
- **文件欄位**: 文件上的簽名、日期等相對版面位置，文件進入簽署中後不可修改。
- **簽署人**: 內部員工或 Email 外部人員被指定簽署某文件的關聯與目前狀態；內部員工保存發起當下的員工資料快照，外部人員保存姓名與 Email 快照。
- **簽署證據**: 成功簽署後建立的不可變證據，綁定實際文件、固定簽署參數、同意版本及身分驗證事件。
- **私有檔案中繼資料**: 來源文件、簽名圖、個人簽署文件、完成文件、manifest、稽核報告、QR Code 與匯出檔案的受控儲存資訊。
- **稽核事件**: 文件流程的只追加事件與摘要鏈，用於還原歷程及偵測異動。
- **公開驗證紀錄**: 完成文件的公開驗證識別、manifest、檔案摘要與稽核根摘要。
- **通知批次**: 一次通知動作的文件、篩選範圍、目標數量及發起人快照。
- **通知明細**: 每批通知對各簽署人與管道的發送狀態及安全錯誤代碼。
- **匯出工作**: 文件或簽署紀錄匯出的範圍、發起人、處理狀態及結果。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 系統在沒有任何角色、permission 或角色種子資料的全新環境中，能 100% 完成初始化、啟動與健康檢查。
- **SC-002**: 角色管理、permission 管理、角色配置與 API permission 登錄的可執行入口及執行期依賴數量為 0。
- **SC-003**: 既有 SSO 串接的身分交換、員工識別、session 與登出驗證情境在清理後維持 100% 通過，且不依賴角色或 permission 資料。
- **SC-004**: 十二類 Stage 1 資料實體均可在空白驗證環境一次建立成功，必要關聯與唯一性規則的驗收案例通過率為 100%。
- **SC-005**: 對簽署證據及稽核事件執行一般更新或刪除的驗收案例，100% 無法透過正式資料存取能力完成。
- **SC-006**: 資料結構套用、撤回與重新套用演練各成功完成至少一次；重建後 SSO 所需員工欄位及十二類 Stage 1 資料實體的結構差異數量為 0。
- **SC-007**: 正式資料結構、應用程式資料模型、變更歷程與 schema 快照的自動比對差異數量為 0。
- **SC-008**: 本規格完成後，對外可使用的電子簽業務端點新增數量為 0，避免把資料基礎誤述為業務功能已完成。
- **SC-009**: 文件含一名以上拒絕者且其餘簽署人皆已簽署時，完成條件驗收案例通過率為 100%，最終結果中拒絕者被誤列為已簽署的筆數為 0。
- **SC-010**: 員工查詢、批次匯入、啟停帳號、本地備註及其舊管理稽核的可執行入口數量為 0；SSO 與 session 驗證情境仍維持 100% 通過。
- **SC-011**: 內部員工與 Email 外部簽署人的資料完整性案例通過率為 100%；同一文件重複員工、重複正規化 Email 或同時使用兩種識別方式的無效簽署人均無法建立。
- **SC-012**: Schema 檢查中，日期及時間欄位缺少專屬單欄索引的數量為 0。
- **SC-013**: Route security 驗證中，未明確標示公開卻能在沒有有效員工 session 時存取的 API 數量為 0，且 `RegisterApi`／API permission metadata 的可執行引用數量為 0。

## Assumptions

- `server/docs/internal-electronic-signature-data-dictionary.md` 與對應 ER Model 是 Spec 1 的資料範圍基準；`doc/esign-db-schema.sql` 僅為舊參考稿，不直接作為正式變更來源。
- Stage 1 採十二類資料實體且不另建文件版本實體；文件發起後鎖定，任何實質變更建立新文件。
- 一次建立十二類資料實體是經確認的 schema-first 例外：這些實體共同定義 Stage 1 文件、簽署證據、稽核、驗證、通知與匯出的跨功能關聯；若拆散至後續功能才建立，將反覆修改核心外鍵、不可變資料邊界與 migration。較簡單的最小集合方案因此不採用；尚未接上業務流程的資料表只允許由後續正式功能寫入，若 Stage 1 範圍縮減，移除未使用資料表將需要新增可回滾 migration 並同步調整資料字典與 ER Model。
- 現有 SSO 串接尚未在目前系統正式啟用，但其程式與驗證資產具有未來復用價值。
- Stage 1 不需要系統層級角色或 permission；未來若主平台需要差異化系統角色，必須另立規格。
- Stage 1 不提供一般員工管理後台；後續若簽署人選擇需要員工搜尋，只能由對應電子簽功能另立最小資料契約。
- Stage 1 的外部簽署人限以 Email 加入，主要情境為尚未具員工身分的面試錄取人員；手機號碼簽署不在範圍內。
- 未來外部 Email 簽署流程會以 `esign_signers.id` 作為受限 principal，短效邀請／驗證／重放狀態存於受控暫存，簽署成功證據關聯 signer 而非 user；完整流程須另立規格，本次不實作。
- 文件建立人、指定簽署人、文件狀態與下載範圍等業務授權將由後續功能規格定義，不依賴本次移除的通用 RBAC。
- 目前沒有必須保留資料、不可重建的共用、staging 或 production 資料庫；所有現有環境可從乾淨基準重新建立。
- 現有 Auth/RBAC 初始 migration 可直接整理為本系統需要的乾淨基準，不新增只為相容舊資料庫而存在的向前清理 migration。
- 本規格只建立資料結構與資料存取邊界，不寫入正式文件、簽名、員工個資或其他生產資料。
- 「時間相關欄位」包含所有 `DATE` 與具日期時間語意的欄位，例如建立、更新、刪除、登入、發起、簽署、拒絕、完成、停止、發生、生效與撤銷時間；每欄均建立獨立索引，即使同時存在其他複合索引。

## Dependencies

- 現有 Auth 程式須先完成依賴盤點，區分可移除的 RBAC／permission 功能與必須保留的 SSO、session、員工識別能力。
- 後續電子簽功能必須使用本規格建立的共同員工及文件識別，不得另建平行身分主檔。
