# Feature Specification: 簽章驗證 QR Code

**Feature Branch**: `[004-signature-verification-qr]`

**Created**: 2026-10-16

**Status**: Draft

**Input**: User description: "每位簽署人送出簽名後，為該簽章產生由系統私鑰簽署的驗證網址；前端將網址轉成 QR Code，完成 PDF 在簽名欄位印上 QR Code；任何人掃描後由系統驗章並回傳簽章資料；文件結案時將文件驗證快照寫入 esign_verification_records。"

## Clarifications

### Session 2026-10-16

- Q: 驗證網址何時產生？ → A: 每名簽署人成功送出簽名後才產生。簽署畫面上顯示的是示意簽名可用範圍的佔位圖，不是正式驗證碼。
- Q: 一個驗證碼代表一個簽章還是一份文件？ → A: 代表一個簽章；驗證結果必須同時帶出該簽章綁定的文件（標題、簽署當下的原始文件摘要、文件狀態，以及完成後的完成文件摘要），避免 QR Code 被複製到其他文件時仍顯示為有效。
- Q: 完成 PDF 是否印上 QR Code？ → A: 是，印在該簽署人每個簽名欄位內。
- Q: 公開驗證頁揭露哪些資料？ → A: 為供公司內部稽核查驗，顯示簽署人完整姓名與文件標題；Constitution 1.3.0 已在 Principle III 新增公開簽章驗證例外。正式上線前由法務確認適法性。
- Q: 文件結案時是否保存文件層級的驗證快照？ → A: 是。結案時固定一份驗證快照，內容含原始文件與簽署參數摘要、完成文件摘要、各簽署結果與稽核鏈終點。
- Q: 功能上線前已結案、沒有驗證快照與 QR Code 的文件如何處理？ → A: 不回補。替舊文件補 QR Code 必須重新產生完成 PDF 並改變其摘要，等同改動證據。UAT 驗收前清除既有測試資料。
- Q: 是否在發起時強制簽名欄位最小高度，確保 QR Code 可掃描？ → A: 暫不強制；先以實際列印與手機掃描驗收，再決定是否訂定下限。
- Q: 公開驗證的查詢頻率限制為何？ → A: 沿用既有登入端點的限流設定，不新增設定。
- Q: 本規格與 Spec 03、Spec 05 的關係？ → A: 本規格建立在 Spec 03 的簽署證據與結案流程上；一般匯出由 Spec 05 處理，不在本規格範圍。

## User Scenarios & Testing _(mandatory)_

### User Story 1 - 簽署後取得簽章驗證網址 (Priority: P1)

簽署人成功送出簽名後，立即取得代表這個簽章的驗證網址；建立人與該簽署人日後查看文件時，也能取得已簽署者的驗證網址。尚未簽署的人沒有驗證網址。

**Why this priority**: 驗證網址是 QR Code 與公開查驗的共同來源；只有在簽署證據成立後才發出，才能確保每個驗證碼都對應真實存在的簽章。

**Independent Test**: 使用一份有兩名簽署人的進行中文件，讓第一人完成簽署；確認第一人的簽署結果與文件詳情含驗證網址，第二人在詳情中沒有驗證網址，且網址內容不含姓名、Email 或文件資訊。

**Acceptance Scenarios**:

1. **Given** 簽署人尚未成功簽署，**When** 任何人查詢該簽署人的簽署任務或文件詳情，**Then** 系統不提供驗證網址。
2. **Given** 內部或外部簽署人成功送出簽名，**When** 系統回傳簽署結果，**Then** 結果包含該簽章的驗證網址，且網址不含個資或簽署內容。
3. **Given** 簽署人已簽署，**When** 建立人或該簽署人查看文件詳情、簽署任務或外部完成狀態，**Then** 系統回傳同一個驗證網址。
4. **Given** 簽署人重送相同的簽署請求，**When** 系統回傳既有結果，**Then** 驗證網址與第一次相同。

---

### User Story 2 - 完成 PDF 印上驗證 QR 並保存驗證快照 (Priority: P2)

所有簽署人完成簽署後，系統產生的完成 PDF 在每個簽名欄位內印上對應簽署人的驗證 QR Code，並在結案時保存一份文件驗證快照；兩者都成功才結案。

**Why this priority**: 完成 PDF 是離開系統後流通的檔案，QR Code 讓收件人能從檔案或紙本回到系統查驗；快照固定結案當下的文件狀態，作為日後比對的依據。

**Independent Test**: 讓兩名簽署人完成一份文件；確認完成 PDF 每個簽名欄位右下角都有 QR Code 且與簽名不重疊，掃描後分別指向兩人的驗證網址；DB 中恰好一筆驗證快照，其完成文件摘要與完成 PDF 一致。

**Acceptance Scenarios**:

1. **Given** 所有簽署人都已成功簽署，**When** 系統產生完成 PDF，**Then** 每名簽署人的每個簽名欄位內都印有指向該簽署人驗證網址的 QR Code，簽名與 QR Code 不重疊。
2. **Given** 完成 PDF 已產生，**When** 系統結案，**Then** 同一結案操作中保存文件驗證快照，快照固定原始文件摘要、簽署參數摘要、完成文件摘要、各簽署結果與稽核鏈終點。
3. **Given** 驗證快照保存失敗，**When** 系統處理結案，**Then** 文件不得標示完成，既有簽署保持不變，且可安全重試而不產生第二筆快照。
4. **Given** 功能上線前已結案的文件，**When** 本功能上線，**Then** 系統不為其補寫快照，也不重新產生完成 PDF。

---

### User Story 3 - 任何人掃描查驗簽章 (Priority: P3)

任何拿到完成 PDF 或紙本的人，都能掃描 QR Code，不需登入即可確認這個簽章確實由本系統記錄、由誰在何時簽署，以及它綁定的是哪一份文件。

**Why this priority**: 這是本功能對公司內部稽核的直接價值；它依賴 US1 的驗證網址與 US2 的快照。

**Independent Test**: 以未登入、無 cookie 的瀏覽器開啟一份已完成文件的驗證網址，確認顯示正確的簽署人、時間、文件與摘要；竄改網址任一字元後，得到與不存在相同的結果；查詢前後系統資料沒有任何寫入。

**Acceptance Scenarios**:

1. **Given** 任何人持有有效驗證網址，**When** 不登入開啟驗證頁，**Then** 系統顯示驗證結果、簽署人完整姓名、簽署時間、驗證方式、文件標題、簽署當下的原始文件摘要與文件狀態；文件完成後另顯示完成時間與完成文件摘要。
2. **Given** 驗證網址遭竄改、偽造、格式錯誤或對應的簽章不存在，**When** 開啟驗證頁，**Then** 系統一律回應相同的「查無此簽章」結果，不揭露失敗原因。
3. **Given** 簽署證據、文件驗證快照、完成文件摘要或稽核鏈不一致，**When** 開啟驗證頁，**Then** 系統顯示驗證失敗，不得顯示為有效。
4. **Given** 簽署人已簽署但文件之後被停止，**When** 開啟其驗證網址，**Then** 系統顯示簽章有效、文件已停止，不顯示完成文件摘要。
5. **Given** 任何驗證結果，**When** 系統回應，**Then** 不揭露簽名圖片、Email、員編、部門、職稱、來源 IP、User-Agent、驗證事件識別、文件內容或其他簽署人資料，且查詢本身不寫入任何業務資料或稽核事件。

### Edge Cases

- 文件尚未結案時掃描驗證網址，驗證頁顯示文件進行中，不顯示完成文件摘要。
- QR Code 被複製到其他文件或紙本時，驗證頁顯示的是原文件標題與摘要，供查驗者比對；系統不宣稱能從掃描判斷紙本內容未被修改。
- 大量或自動化掃描驗證網址時，系統必須限制查詢頻率，且不得因查詢而鎖定業務資料或寫入資料。
- 簽名欄位過小時，QR Code 可能無法穩定掃描；本規格以實際列印驗收記錄最小可用尺寸，不在發起時強制下限。
- 多個 worker 同時或重複處理同一份文件結案時，只能產生一筆驗證快照；失去處理權的 worker 不得寫入。

## Requirements _(mandatory)_

### Functional Requirements

- **FR-001**: 系統 MUST 只在簽署人成功簽署後，為該簽章提供唯一且不可預測的公開驗證網址；簽署成功前不得提供。驗證網址 MUST NOT 包含個資、簽名或文件內容。
- **FR-002**: 驗證網址 MUST 可由系統證明為本系統簽發；偽造或竄改的驗證網址不得通過驗證。同一簽章每次取得的驗證網址 MUST 相同。
- **FR-003**: 系統 MUST 在簽署結果、建立人與本人可見的文件詳情及簽署任務、外部簽署人的完成狀態中，提供已簽署者的驗證網址；尚未簽署者 MUST 為空值。
- **FR-004**: 簽署畫面 MUST 只顯示示意簽名可用範圍的佔位圖；Client MUST NOT 在簽署成功前自行產生簽章識別或 QR Code，也不得將其送交 Server。
- **FR-005**: 完成 PDF MUST 在每名簽署人的每個簽名欄位內，以固定版面印上指向該簽署人驗證網址的 QR Code；簽名本身不得與 QR Code 重疊。
- **FR-006**: 文件結案時 MUST 保存一份文件驗證快照，固定原始文件摘要、簽署參數摘要、完成文件摘要、各簽署結果與結案當下的稽核鏈終點；快照建立後不得修改或刪除。
- **FR-007**: 文件 MUST 只在完成 PDF 與文件驗證快照均於同一結案操作中成功保存後進入完成狀態（擴充 Spec 03 FR-025）；任一失敗時不得標示完成，且可安全重試而不重複建立快照。
- **FR-008**: 任何人 MUST 能不登入即以驗證網址查詢驗證結果；系統 MUST 在每次查詢時重新比對簽署證據與文件狀態，文件完成後另比對驗證快照、完成文件摘要與稽核鏈，任一不一致時回報驗證失敗。
- **FR-009**: 公開驗證 MUST 只回傳驗證結果、簽署人完整姓名、簽署時間、驗證方式、文件標題、簽署當下的原始文件摘要、文件狀態、完成或停止時間及完成文件摘要；MUST NOT 回傳簽名圖片、Email、員編、部門、職稱、來源 IP、User-Agent、驗證事件識別、文件內容或其他簽署人資料。
- **FR-010**: 無效、偽造、竄改、尚未簽署或不存在的驗證網址 MUST 得到一致結果且不揭露失敗原因；公開驗證 MUST 限制查詢頻率，且不得設定 cookie、寫入業務資料或稽核事件。
- **FR-011**: 本規格 MUST NOT 為功能上線前已結案的文件補寫驗證快照或重新產生完成 PDF。
- **FR-012**: 本規格 MUST NOT 提供文件層級公開驗證入口、驗證紀錄撤銷或取代、證據包、平台憑證封存、可信時間戳記或一般匯出。

### Scope Boundaries

**本規格包含**：

- 簽署成功後的單一簽章驗證網址，以及在既有簽署結果、文件詳情、簽署任務與外部完成狀態中提供該網址。
- 簽署畫面的示意佔位圖，以及簽署成功後以 Server 提供的驗證網址顯示 QR Code。
- 完成 PDF 各簽名欄位內的驗證 QR Code。
- 結案時的文件驗證快照，以及將快照納入結案成功條件。
- 不需登入的公開驗證查詢與驗證頁。

**本規格不包含**：

- 文件層級公開驗證入口（使用驗證快照的公開識別）、驗證紀錄撤銷或取代。
- 完整證據包、人類可讀稽核報告、下載稽核或浮水印。
- 以公司憑證封存完成 PDF 或驗證快照、可信時間戳記、PAdES-LT／LTA 或個人數位憑證。
- 一般匯出、匯出歷史或大量下載（Spec 05）。
- 為上線前已結案的文件補寫快照或 QR Code。
- 簽名欄位最小尺寸的強制驗證。

### Key Entities

- **簽章驗證網址**: 簽署成功後由系統簽發、指向單一簽章的公開查驗入口；不含個資，可證明由本系統簽發，並印在完成 PDF 的簽名欄位內。
- **文件驗證快照**: 文件結案時固定的文件層級驗證資料，包含原始文件與簽署參數摘要、完成文件摘要、各簽署結果與稽核鏈終點；每份完成文件一筆，建立後不可修改或刪除。
- **驗證結果**: 公開驗證回傳的單一簽章查驗資料，只含 FR-009 允許的欄位。

## Success Criteria _(mandatory)_

### Measurable Outcomes

- **SC-001**: 尚未簽署者取得驗證網址的驗收案例數為 0；已簽署者在簽署結果、詳情、任務與外部完成狀態取得相同驗證網址的比例為 100%。
- **SC-002**: 偽造、竄改、格式錯誤或尚未簽署的驗證網址驗收案例中，被判定為有效的筆數為 0，且各失敗案例的回應無法區分失敗原因。
- **SC-003**: 驗收文件列印後，以一般手機相機掃描每個簽名欄位內的 QR Code，可開啟正確簽署人驗證結果的比例為 100%；95% 的驗證查詢在 2 秒內回應。
- **SC-004**: 功能上線後結案的文件中，缺少文件驗證快照，或快照與完成文件摘要不一致的筆數為 0；結案失敗後重試產生第二筆快照的筆數為 0。
- **SC-005**: 公開驗證回應中出現簽名圖片、Email、員編、部門、職稱、來源 IP 或 User-Agent 的筆數為 0；查詢前後業務資料與稽核事件的異動筆數為 0。

## Assumptions

- Spec 03 的簽署證據、完成 PDF 與 worker 結案流程已可用；本規格只擴充簽署結果、結案條件與完成 PDF 版面，不改變簽署交易本身。
- 驗證代碼為簽署時產生並保存於資料庫的隨機值，不使用金鑰，也不是數位簽章。以公司憑證封存完成 PDF 或驗證快照，待公司取得憑證後另立規格。
- 公開驗證頁依 Constitution 1.3.0 Principle III 的公開簽章驗證例外，顯示簽署人完整姓名與文件標題；正式上線前由法務確認適法性。
- QR Code 只是查驗入口，不宣稱已具平台憑證、可信時間戳記或法定數位簽章效果；紙本內容是否被修改，仍須與系統保存的原本比對。
- 簽名欄位暫不設最小高度；若實際列印後 QR Code 無法穩定掃描，再另行決定欄位高度下限或縮短驗證路徑。
- 驗證網址使用 Spec 03 既有的對外網域；外部掃描者能開啟該網域。

## Dependencies

- Spec 03 的簽署證據、外部受限存取與 receipt、完成 PDF 產製及 finalization lease 必須可用。
- 既有 `esign_verification_records` 資料表（Spec 01）作為文件驗證快照，不新增資料表或欄位。
- 簽署畫面的佔位圖與簽署後顯示 QR（FR-004）由前端工程師實作，不在本規格工項內，並依賴 Client 串接 Spec 03 正式 API；在此之前只能以 Server 自動化測試驗收。
- 公開驗證頁由前端工程師依本規格的 contract 提供，不在本規格工項內；掃描後畫面的人工驗收依賴該頁完成。
- Constitution 1.3.0 的公開簽章驗證例外。
