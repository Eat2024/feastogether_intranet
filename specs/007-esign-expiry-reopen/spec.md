# Feature Specification: 文件已到期狀態與補簽

**Feature Branch**: `007-esign-expiry-reopen`（自更新後的 `dev` 建立）

**Feature Directory**: `specs/007-esign-expiry-reopen`

**Created**: 2026-10-19

**Status**: Draft — 尚未實作

**Input**: 使用者希望文件到期後進入「已到期」，建立人可以設定新期限重新開放補簽，解決目前後端到期即永久停止與前端 mock 流程的差異。

## User Scenarios & Testing

### User Story 1 - 文件到期後保留補簽可能性 (Priority: P1)

文件建立人與簽署人能辨識文件因期限屆滿而暫停，已完成的簽署仍保留，未簽署者必須等待建立人重新開放。

**Why this priority**: 區分時間限制與人工終止，是允許補簽的前提，也避免將逾期文件誤認為永久停止。

**Independent Test**: 準備部分已簽的文件，跨越截止時間後查閱文件並嘗試簽署，確認顯示已到期、拒絕提交且原證據不變。

**Acceptance Scenarios**:

1. **Given** 文件簽署中且仍有人未簽，**When** 現在時間等於或晚於有效截止時間，**Then** 文件對外呈現「已到期」，未簽署者不能新增簽署，不產生人工停止原因。
2. **Given** 已過截止時間但背景到期處理尚未完成，**When** 查詢或提交簽署，**Then** 查詢仍呈現已到期且提交被拒絕，不因處理延遲而允許逾期簽署。
3. **Given** 文件已完成或已停止，**When** 原截止時間到達，**Then** 維持原狀態，不轉為已到期。
4. **Given** 文件沒有截止時間，**When** 時間經過，**Then** 不因到期規則改變狀態。

### User Story 2 - 建立人重新開放未簽署者補簽 (Priority: P1)

建立人為已到期文件填寫新的截止時間與原因，確認後立即重新開放未簽署者簽署，不必重新建立文件或要求已簽署者重簽。

**Why this priority**: 保留既有簽署成果，讓文件能在同一份紀錄上繼續完成。

**Independent Test**: 對部分已簽的已到期文件開放補簽，讓剩餘簽署人完成，確認文件完成且已簽證據未被重建。

**Acceptance Scenarios**:

1. **Given** 建立人操作仍有未簽署者的已到期文件，**When** 提供有效的新截止時間與補簽原因，**Then** 文件立即回到簽署中，顯示補簽標記與新期限，只有原未簽署者重新取得簽署資格。
2. **Given** 文件仍在原簽署期限內、為草稿、已完成或已停止，**When** 嘗試補簽，**Then** 操作被拒絕，狀態與期限不變。
3. **Given** 操作者不是建立人或未登入，**When** 嘗試補簽，**Then** 操作被拒絕，不變更任何業務紀錄。
4. **Given** 截止時間缺漏、格式錯誤、等於或早於操作生效時間，或原因空白／超過 500 字，**When** 確認補簽，**Then** 操作被拒絕，回傳繁體中文且可修正的錯誤訊息。
5. **Given** 補簽期間再次到期且仍有人未簽，**When** 建立人再次提供新期限與原因，**Then** 可再次開放，每次補簽都保留獨立歷程。
6. **Given** 最後一位未簽署者在補簽期限內成功簽署，**When** 完成簽署，**Then** 文件轉為已完成，沿用原有完成與個人副本流程。

### User Story 3 - 未簽署者使用正確的補簽資格 (Priority: P1)

內部簽署人從既有待簽入口繼續簽署；外部簽署人透過新邀請連結補簽，先前失效的邀請不會因補簽而重新有效。

**Why this priority**: 補簽必須真正恢復正確對象的簽署能力，且不能復活已失效的存取憑證。

**Independent Test**: 使用同時含內部與外部未簽署者的文件，驗證到期、新一輪補簽與再次到期時，各入口的允許與拒絕結果。

**Acceptance Scenarios**:

1. **Given** 內部簽署人尚未簽署且文件已到期，**When** 查閱自己的待簽文件，**Then** 仍可辨識該文件及等待補簽狀態；重新開放後可由原入口簽署。
2. **Given** 已到期文件包含外部未簽署者，**When** 補簽成功，**Then** 為各外部未簽署者提供新邀請，建立人可從僅限建立人的取得入口讀取並轉交；原連結仍失效。
3. **Given** 外部簽署人使用新邀請，**When** 新期限屆滿、該人完成簽署或文件被停止，**Then** 邀請不能再授權簽署。
4. **Given** 簽署人查閱補簽文件，**When** 顯示其所需資訊，**Then** 可見有效期限與補簽標記，但不揭露內部補簽原因、設定人或其他簽署人的敏感資料。

### User Story 4 - 建立人追溯補簽與永久停止文件 (Priority: P2)

建立人可查閱每次期限變更的原因與時間，也可明確終止不再需要繼續簽署的文件。

**Why this priority**: 多次延期仍須可追溯，且到期不應剝奪建立人永久停止文件的能力。

**Independent Test**: 使用已有兩次補簽的文件查閱歷程，接著停止文件並嘗試再次補簽，確認紀錄完整且停止不可恢復。

**Acceptance Scenarios**:

1. **Given** 文件已經補簽兩次，**When** 建立人查閱歷程，**Then** 可依時間辨識原截止時間、各次新期限、原因、操作者及生效時間。
2. **Given** 文件為簽署中或已到期，**When** 建立人依既有停止規則填寫原因並停止，**Then** 文件轉為已停止，未簽署者不能簽署或藉補簽恢復。
3. **Given** 舊版本已將文件因到期轉為已停止，**When** 查閱或嘗試補簽，**Then** 維持已停止並拒絕補簽，不自動轉換歷史資料。

### Edge Cases

- 截止邊界以系統權威時間為準：現在時間小於有效截止時間才可簽署；等於截止時間即不可簽署。日期輸入沿用既有時區與截止時間換算規則，不另創補簽專用算法。
- 多個補簽要求同時抵達：同一次到期最多成功開放一次，不產生重複補簽歷程或多組新邀請。
- 補簽成功後重送舊要求，即使文件後來再次到期，也不得自動開放下一輪；建立人須確認最新狀態並另行發起新一輪補簽。
- 到期處理與補簽同時發生：以最新有效期限及狀態判斷，舊期限的到期處理不能讓剛開放的補簽再次到期。
- 人工停止與補簽同時發生：按實際成立順序決定結果；停止成立後，不得被較舊的補簽操作恢復。
- 最後一筆簽署與到期同時發生：只能成立符合截止邊界的結果，不得出現已完成但仍被轉為已到期，或截止後新增成功簽署。
- 補簽儲存途中失敗：期限、狀態、邀請及歷程不得呈現部分成功；若結果未知，使用者可重新查閱結果，不因重送而再開放一次。
- 已簽署者的簽名、簽署時間、驗證證據與已產生的個人副本，不因到期、補簽或人工停止而改寫。

## Requirements

### Functional Requirements

- **FR-001**: 系統 MUST 區分「已到期」與「已停止」。簽署中且仍有未簽署者的文件達到有效截止時間時，MUST 呈現已到期，不再以到期原因自動永久停止。
- **FR-002**: 系統 MUST 在每次簽署時驗證權威時間、有效期限、文件狀態及該人的簽署資格。背景到期處理尚未完成或前端畫面尚未更新，不得放行逾期簽署。
- **FR-003**: 系統 MUST 只允許已登入的文件建立人對仍有未簽署者的已到期文件開放補簽；不能只依前端按鈕或傳入狀態決定資格。
- **FR-004**: 補簽 MUST 要求新的有限截止時間與去除首尾空白後 1–500 字的原因。新截止時間 MUST 晚於補簽生效時間；不提供取消期限或預約開始選項。
- **FR-005**: 補簽成功 MUST 立即回到簽署中並適用新期限；「補簽」為操作、歷程及顯示標記，不新增獨立的補簽中狀態。
- **FR-006**: 補簽 MUST 僅恢復原未簽署者的資格，不變更文件內容、簽署位置、簽署人名單或已成立的證據，亦不要求已簽署者重簽。
- **FR-007**: 系統 MUST 支援多輪到期與補簽，每輪保存前次期限、新期限、原因、操作者及生效時間；保留最初簽署期限，不覆蓋歷史紀錄。
- **FR-008**: 建立人 MUST 能查閱完整補簽歷程。簽署人只能取得自身作業必要的有效期限、補簽標記及文件資訊，不得取得內部原因與設定人資料。
- **FR-009**: 系統 MUST 使到期文件的外部簽署邀請失效；每次補簽為外部未簽署者建立新的限期邀請，原邀請不得復活。新邀請僅授權指定文件與簽署人，且有效期限不得晚於該輪補簽截止時間。
- **FR-010**: 建立人 MUST 能透過僅限建立人的取得入口讀取外部未簽署者的新邀請並自行轉交；沿用既有建立人權限，不擴充角色。此功能不新增自動 Email、SMS 或催簽通知。
- **FR-011**: 系統 MUST 防止同輪補簽因重複提交、回應遺失或並發而重複生效，且不得將舊輪次要求套用至後續到期；到期、簽署、補簽與人工停止之間不得覆蓋較新的有效結果。
- **FR-012**: 補簽的期限、狀態、邀請及歷程 MUST 一致成立或完全不成立；失敗不得留下已開放但無法使用的部分狀態。
- **FR-013**: 建立人 MUST 可依既有停止規則停止簽署中或已到期文件。已停止與已完成文件不得補簽；未設定截止時間的簽署中文件不得因到期規則變更狀態。
- **FR-014**: 文件清單、詳情及個人待簽資訊 MUST 使用一致的有效狀態與期限；已到期的未簽署文件仍可辨識為等待補簽，重新開放後顯示新期限與補簽標記。
- **FR-015**: 系統 MUST 保存到期、補簽與人工停止的可區分稽核紀錄；重複到期處理不得新增同輪重複事件。補簽不得破壞原有簽署證據的可驗證性。
- **FR-016**: 本功能 MUST 不自動恢復既有已停止文件，包括舊版因到期停止者；不得僅以停止原因文字判斷可恢復資格。
- **FR-017**: 所有可預期錯誤與使用者提示 MUST 使用繁體中文，區分無權限、不可補簽狀態、期限／原因不合法與狀態已變更；不得揭露邀請憑證、簽名或非必要個資。

### 狀態轉換

| 原狀態 | 條件／操作 | 結果 |
| --- | --- | --- |
| 簽署中 | 有未簽署者且到達有效截止時間 | 已到期 |
| 已到期 | 建立人成功設定補簽期限與原因 | 簽署中，顯示補簽標記 |
| 簽署中 | 全員在有效期限內完成簽署 | 已完成 |
| 簽署中／已到期 | 建立人合法停止 | 已停止 |
| 已完成／已停止 | 嘗試補簽 | 拒絕，維持原狀態 |

### Key Entities

- **文件**：具有建立人、原始期限、目前有效期限與狀態的簽署標的；已到期可補簽，已停止不可恢復。
- **補簽歷程**：隸屬單一文件的每次重新開放紀錄，保留前後期限、原因、操作者、生效時間及輪次關係。
- **簽署人與簽署證據**：補簽僅作用於原未簽署者；成功證據持續保留且不可改寫。
- **外部邀請**：綁定文件與單一外部簽署人的限期資格；補簽發給新資格，不恢復已失效資格。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 在截止前、截止當下與截止後，以及背景到期處理延遲的驗收案例中，所有查詢與簽署結果均符合有效期限；截止當下及之後的未授權成功簽署數為 0。
- **SC-002**: 一份含已簽、內部未簽及外部未簽者的文件，可完成至少兩輪「到期 → 補簽」，並由剩餘人員完成簽署；原已簽者需重簽次數為 0，既有證據與副本異動數為 0。
- **SC-003**: 未登入、非建立人、不可補簽狀態、無效期限及無效原因的驗收案例全部被拒絕，文件與補簽歷程異動數為 0。
- **SC-004**: 重送與並發案例中，同輪成功補簽紀錄最多 1 筆；舊要求不開啟新輪次，舊到期處理不覆蓋新期限，停止後恢復次數為 0。
- **SC-005**: 每輪補簽均可由建立人完整追溯，舊外部邀請可成功授權次數為 0；新邀請只允許正確的未簽署者在有效期限內簽署。
- **SC-006**: 文件清單、詳情及個人待簽資訊在相同權威時間與文件版本下，狀態及有效期限一致率為 100%；簽署人取得內部補簽原因或設定人資料的案例數為 0。

## Assumptions

- 草稿預設補簽立即開始，只設定新截止時間與原因；不照搬 mock 中可指定未來開始日的設計。
- 草稿預設只有建立人可操作，不新增管理者代理權限。後續若需擴充權限，另行明確定義。
- 草稿預設既有已停止文件不遷移、不恢復；若業務需要救回舊版到期文件，另立具備稽核依據的轉換需求。
- 依賴既有登入、建立人授權、內外部簽署、邀請憑證、稽核與個人副本能力；建立人取得補簽邀請的入口尚不存在，須隨本功能補齊；不因補簽新增通知管道。
- 本文件定義前後端共同的目標行為；目前 client 仍為 mock 原型，不能視為已完成正式串接。後端與前端交付可拆成不同 PR，但完整功能驗收須涵蓋正式串接。

## Scope Boundaries 與既有規格關係

**包含**：已到期狀態、補簽操作與讀取需求、有效期限驗證、補簽歷程、外部新邀請、人工停止邊界、並發與重送保護，以及前後端一致的顯示規則。

**不包含**：尚未到期就延長期限、預約補簽開始日、無限期補簽、恢復已停止文件、修改文件內容或簽署人、拒簽／退回、依序簽署、管理者代操作、自動通知與舊資料自動轉換。

本規格核准並實作後，取代 [Spec 03](../003-core-esign-flow/spec.md) 的到期自動停止決策、對應 User Story 4 驗收情境 5 與 FR-036；補簽不再受該規格「範圍外」條目排除。其餘既有簽署與證據規則仍適用。

後續規劃須同步修訂 Spec 03 的資料模型、契約、到期驗收與相關文件，明確區分原始固定期限與可變的有效期限；不得把舊版到期即停止測試直接保留為新功能的預期結果。本次僅建立規格，未變更前端、後端、資料結構或部署設定。

### 規劃時的既有行為確認（2026-10-19）

- 現有後端在全員簽署後先進入 `finalizing`，待個人副本完成才轉為 `completed`。本規格所稱完成流程包含此既有中間狀態，不移除它；`finalizing` 不可補簽、不轉為已到期，保留原可由建立人停止的規則。
- 正式發起流程目前要求有限期限；「沒有截止時間不自動到期」是防禦性規則，不代表本功能新增無期限發起。
- 原始簽署期間已保存在不可變簽署快照；補簽改變目前有效期限，不改寫快照或其雜湊。
