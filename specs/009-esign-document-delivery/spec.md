# Feature Specification: 電子簽文件與簽署人管理補強

**Feature Branch**: 沿用目前工作分支，本次未建立或切換分支

**Feature Directory**: `specs/009-esign-document-delivery`

**Created**: 2026-10-20

**Status**: 本機實作與整合驗證完成，待最終 review；部署 S3 容量驗收仍待 ticket11（T028未完成）

**Input**: 使用者確認大量副本採背景準備後下載，須支援一次匯出 6,000 份；補充草稿須保存公司員工、外部簽署人及起迄時間，浮水印繪製移至後端並參考前端既有樣式。使用者要求先寫 spec，不進行程式實作；後續確認將拒簽、外部批次催簽、備註與歷程整併於本 Spec 009，內部同事催簽留待接下來的規格。

## Clarifications

### Session 2026-10-20

- Q: 催簽先支援哪些對象？ → A: 本次僅外部 Email 簽署人；內部同事催簽預計在接下來的規格加入，現在不實作。
- Q: 文件是否分開維護？ → A: 將原 Spec 010 的拒簽、催簽、備註、列表及歷程需求全部合併進 Spec 009，以本文件作為單一需求來源。既有 Spec 001–008 維持其歷史及相依責任。

- Q: 浮水印是否強制？ → A: 否；前端記錄該文件需要 watermark 才加印，後端依保存的文件設定繪製，前端只移除繪製責任。
- Q: 人資匯出範圍？ → A: 人資可以匯出所有簽署文件各自的全部已簽署個人副本，不限建立人，無須逐份另行授權。
- Q: 催簽頻率？ → A: 一天一次；以同一文件、同一外部簽署人為限制單位，按台北時間每日午夜 00:00 重置，不採滾動 24 小時。
- Q: 匯出成果保留與重用？ → A: 完成後保留七天，七天內再次匯出直接取得同一份成果，不重新打包；下載不延長保存期限。

- Q: 本專案如何判定人資？ → A: Portal 會設定只有人資可發起電子簽；本專案本次先不實作本地角色／permission 檢查，後續規格再加入。匯出相關 API 先以有效員工 session 為存取條件，不限制建立人；外部簽署 session 不具此資格。

## User Scenarios & Testing

### User Story 1 - 完整暫存簽署名單與期間 (Priority: P1)

建立人在設定簽署頁選擇公司員工、加入外部簽署人及設定期間後，可以暫存、離開，再回到同一份草稿繼續編輯，不必重新輸入外部名單或日期。

**Why this priority**: 避免建立人誤以為已保存完整設定，實際發起時卻遺漏人員或期間。

**Independent Test**: 保存包含一位公司員工、兩位外部簽署人及起迄日期的草稿，重新登入後開啟，比對名單與期間，確認沒有發起或寄信。

**Acceptance Scenarios**:

1. **Given** 草稿包含內外部混合名單及完整期間，**When** 建立人暫存後離開並重新開啟，**Then** 全部人員的類型、身分及外部姓名／Email 與起迄日期正確回填。
2. **Given** 名單全為外部簽署人，**When** 暫存並重新開啟，**Then** 名單完整保留，不要求至少一位公司員工，也不為外部人員建立員工帳號。
3. **Given** 尚未填期間、只填一端，或先前期間已過，**When** 暫存，**Then** 可保存目前編輯進度；發起時仍依既有規則驗證完整期間。
4. **Given** 草稿已有期間，**When** 建立人明確清除單端或全部日期並暫存，**Then** 重新開啟時維持清除結果；只更新名單而未提供日期變更時保留原期間。
5. **Given** 日期顛倒、日期格式不合法、外部名單重複或不合法，**When** 暫存，**Then** 顯示可修正的錯誤，原名單與期間都保持原樣，不只保存其中一部分。
6. **Given** 非建立人，或文件已發起，**When** 嘗試修改草稿名單與期間，**Then** 拒絕操作；已發起文件的固定內容不變。
7. **Given** 有效草稿，**When** 暫存成功，**Then** 文件仍為草稿，不產生邀請或可簽署資格，列表與詳情顯示相同期間。

### User Story 2 - 取得由後端加印浮水印的個人副本 (Priority: P1)

有設定 watermark 的文件，其已簽署副本由後端加印「饗賓集團 內部文件 請勿外流」。建立人及簽署人下載同一份副本時，看到一致的浮水印，不依賴下載當下的瀏覽器繪製。

**Why this priority**: 確保個別下載及批次匯出內容一致，避免不同下載入口產生不同版本。

**Independent Test**: 對含直向、橫向、旋轉與裁切頁面的文件完成簽署，從允許的各個入口取得副本，確認每頁浮水印、簽名、日期及驗證資訊均可辨識，且下載的內容一致。

**Acceptance Scenarios**:

1. **Given** 功能上線後新發起且已保存 watermark=true 的文件，**When** 產生個人已簽署副本，**Then** 每一頁均有固定文字的淡灰色、斜向約 30 度、錯列重複浮水印，沿用既有前端樣式，不僅限有簽名欄位的頁面。
2. **Given** 不同尺寸、旋轉或裁切頁面，**When** 檢視副本，**Then** 浮水印依可視頁面方向鋪排，中文無缺字，原內容、簽名、日期與驗證碼仍可讀取及使用。
3. **Given** 同一已產製副本，**When** 建立人、本人或獲授權的外部本人下載，或建立人從 ZIP 取出，**Then** 各份 PDF 位元組一致，不在每次下載重新加印。
4. **Given** 原始上傳文件及已成立的簽署證據，**When** 產製加印副本，**Then** 原始檔與簽署證據保持不變，浮水印納入完成產物的完整性驗證。
5. **Given** 功能上線前已發起或已產製的文件，**When** 下載或匯出，**Then** 已有副本不被覆寫或補印；未產製副本仍遵守發起時固定的浮水印設定。
6. **Given** 文件保存 watermark=false，**When** 產製完成副本，**Then** 不加印浮水印；前端不得於下載時自行補印。
7. **Given** 浮水印產製失敗或無法正確顯示中文，**When** 系統處理完成副本，**Then** 不得把未符合規則的檔案當作成功成果供下載。

### User Story 3 - 一次申請 6,000 份已簽署副本並稍後下載 (Priority: P1)

人資同仁可對任何建立人的簽署文件，逐份申請匯出所有已簽署副本。系統先受理，在背景準備 ZIP，使用者可以離開頁面，稍後從匯出紀錄查看結果並下載。

**Why this priority**: 大量簽署收件後需要一次取得副本，且不能因匯出拖慢正常簽署，或要求人資逐人點擊下載。

**Independent Test**: 使用 6,000 份具有代表性大小及頁數的合成完成副本，從申請、離頁、查進度、下載到解壓比對，確認沒有遺漏、重複、跨人誤配或中斷正常簽署。

**Acceptance Scenarios**:

1. **Given** 持有效員工 session 的使用者與一份由其他人建立且已有簽署人的文件，**When** 申請匯出全部已簽副本，**Then** 無須該建立人另行授權，系統快速顯示已受理與可追查的匯出紀錄，不要求維持原頁面直到打包完成。
2. **Given** 匯出工作已受理，**When** 使用者關閉頁面或登出，**Then** 背景準備繼續；重新登入後可看到排隊、處理、完成或失敗狀態及已處理／預期份數。
3. **Given** 首次建立匯出工作時已有 6,000 人完成簽署，**When** 背景準備副本，**Then** 固定這 6,000 人的簽署紀錄與對應副本版本；申請後才簽署的人不混入此次成果。
4. **Given** 名單內有人已簽但個人副本仍在產製，**When** 匯出尚未齊備，**Then** 顯示等待副本的狀態與數量，不默默跳過；副本永久失敗則明確標示匯出失敗原因。
5. **Given** 全部指定副本已備妥且驗證成功，**When** 匯出完成，**Then** 提供一個 ZIP，或一組各自可解壓的 ZIP，並顯示檔案數與容量；使用者不必手動拆分名單或重新發起多個工作。
6. **Given** 同一文件已有完成未滿七天的匯出成果，**When** 原申請人或另一位人資再次申請匯出、下載或中斷後續傳，**Then** 驗證權限後回傳同一份成果，不重新繪製或打包、不延長期限；後來新增的簽署不混入，畫面須顯示快照時間及收錄份數。
7. **Given** 成果已滿七天，**When** 再次申請匯出，**Then** 依當時已簽名單建立新工作，原匯出紀錄保留且標示成果已到期；原始個人副本不受影響。
8. **Given** 讀取失敗、檔案遺失、完整性錯誤或背景處理中斷，**When** 匯出無法完成，**Then** 不發布不完整成果，保留可理解的狀態及原因；重試沿用固定名單，不能擅自改成當下的全部簽署人。
9. **Given** 使用者無有效員工 session 或僅持外部簽署 session，**When** 嘗試申請、查詢或下載其他人的匯出成果，**Then** 拒絕存取，即使知道工作或檔案識別也不能取得內容。

### User Story 4 - 簽署人拒絕簽署並保留可追溯結果 (Priority: P1)

被允許拒簽的內部或外部簽署人，可以確認拒簽並選填原因。拒簽後自己的流程完成，其他待簽者仍能繼續；建立人能辨識拒簽者、時間及原因。

**Why this priority**: 補足已拒絕分頁與原因欄位，並明確定義全員處理完成後如何結案。

**Independent Test**: 以一份允許拒簽、含內外部簽署人的文件驗證一人簽署、一人拒簽、其餘人繼續，最後確認結案及結果分類。

**Acceptance Scenarios**:

1. **Given** 已開放拒簽且目前可簽署的文件，**When** 本人確認拒簽，**Then** 系統以權威時間記錄已拒絕及原因，不建立簽名或已簽副本。
2. **Given** 拒簽確認畫面，**When** 原因留白或輸入 trim 後最多 200 個 Unicode code points，**Then** 可提交；超過限制時拒絕且不改狀態。
3. **Given** 文件未開放拒簽、本人已簽／已拒、文件尚未開始／已到期／已停止，**When** 提交新的拒簽操作，**Then** 後端拒絕，不只依賴按鈕停用。
4. **Given** 一人已拒簽而其餘仍待簽，**When** 其餘人開啟文件，**Then** 可依原規則繼續；拒簽者不能再次簽署，也不納入補簽或催簽。
5. **Given** 全部人員都已成功簽署或拒簽，**When** 最後一人完成處理，**Then** 文件進入既有結案程序；有成功簽署者時須等其必要副本產製完成才標示文件完成，全員拒簽則不等待不存在的 PDF。
6. **Given** 同一人同時送出簽署與拒簽，或重送同一次拒簽，**When** 後端處理，**Then** 僅成立一種終態；同一次成功拒簽重送不新增事件、不覆寫原時間或原因。

### User Story 5 - 一次通知多位外部待簽署人 (Priority: P1)

建立人在列表點擊外部簽署人的通知圖示、勾選多位外部人員按「通知所選」，或按「通知所有待簽外部簽署人」。系統記錄一次通知批次，逐人寄送提醒，建立人可離開頁面並稍後查看結果。

**Why this priority**: 同一操作涵蓋單人與多人提醒，避免建立人逐一寄信，也讓寄送結果可追查。

**Independent Test**: 對三位符合資格的外部待簽者申請一批通知，其中一位寄送失敗，驗證各人的結果與重試不互相影響。

**Acceptance Scenarios**:

1. **Given** 文件可簽署且有待簽者，**When** 建立人送出一位或多位已選簽署人，**Then** 後端確認文件與名單歸屬，記錄批次、操作者及逐人通知明細後回覆已受理，寄送於背景繼續。
2. **Given** 建立人選擇通知所有未簽署者，**When** 後端受理，**Then** 以受理時完整符合資格的外部名單為準，不只通知目前畫面頁次的人員；內部員工不計入可通知人數。
3. **Given** 同一批次含重複簽署人，**When** 處理，**Then** 同一簽署人在該批只保留一筆提醒；單人和多人操作使用相同規則。
4. **Given** 名單含跨文件或不存在的識別，**When** 提交，**Then** 整批拒絕且不寄信，不洩漏其他文件的存在或人員資料。
5. **Given** 人員已簽／已拒、無可用收件地址，或不屬於本階段支援的簽署人類型，**When** 受理或實際寄送前檢查，**Then** 明確記錄未寄送與原因，其他合法待簽者可繼續；不能把略過者顯示成成功。
6. **Given** 受理後、實際寄送前文件停止、到期或該人完成處理，**When** 背景工作再次驗證，**Then** 不再對失去資格的人送出新提醒，保留原因。已交付郵件服務的信件無法收回，但入口仍須即時驗證資格。
7. **Given** 符合資格的收件人，**When** 收到催簽信，**Then** 信件含文件名稱、有效期限與可用簽署入口，不含管理備註、其他收件人、其他人簽名或文件附件。
8. **Given** 寄送失敗或背景工作重試，**When** 再次處理同一明細，**Then** 可追查嘗試次數與結果；已確認寄送成功的明細不因整批重試再寄一次。
9. **Given** 文件補簽重新開放，**When** 建立人主動催簽，**Then** 可對本輪符合資格的待簽者提醒，信中期限與入口屬於目前有效輪次；補簽本身仍不自動催簽。
10. **Given** 文件同時有內外部待簽者，**When** 使用全部通知或送入混合名單，**Then** 全部通知僅選外部人員；指定名單中的內部員工須明確列為本階段不支援，不寄信、不計入成功數。

11. **Given** 同一外部簽署人於台北時間當日已寄出催簽，**When** 同日再次通知，**Then** 回報當日已通知；次日 00:00 起可再次申請，仍須驗證待簽資格，且跨午夜尚未完成的通知不得重複排入。

### User Story 6 - 列表顯示結果、通知紀錄與永久保存的備註 (Priority: P1)

建立人在同一張簽署人表格中查看簽署／拒簽時間、拒簽原因、逐次通知結果，並輸入簡短管理備註。重新整理後資料仍保留。

**Why this priority**: 對應使用者截圖要求，避免未支援欄位或僅存頁面記憶體造成誤判。

**Independent Test**: 準備待簽、已簽與已拒各一人，完成催簽及備註儲存後重新整理，逐欄核對後端資料與畫面。

**Acceptance Scenarios**:

1. **Given** 三種簽署結果，**When** 建立人讀取名單，**Then** 已簽者有簽署時間、已拒者有拒簽時間與選填原因；未發生的時間為空，不混用同一時間代表兩種事件。
2. **Given** 已拒絕分頁或簽署紀錄匯出，**When** 查看已拒者，**Then** 原因及時間與名單一致，已簽與已拒人數分開計算。
3. **Given** 建立人輸入備註，**When** 儲存 trim 後 0–30 個 Unicode code points，**Then** 後端保存並回傳正規化值；空字串表示清除，超過 30 字拒絕且保留原值。
4. **Given** 備註正在編輯，**When** 取消，**Then** 恢復上次保存內容且不寫入；儲存失敗須顯示錯誤，不得假裝已保存。
5. **Given** 有多次通知紀錄，**When** 建立人查看，**Then** 能區分首次邀請與人工催簽，看出每次操作者、申請時間、逐人結果及可公開的失敗／未寄送原因；已受理不等於已寄出。
6. **Given** 簽署人完成簽署或拒簽，**When** 建立人查看歷程，**Then** 可辨識該人的姓名及穩定識別，不再把簽署人動作一律標成系統。
7. **Given** 簽署人本人或其他無管理權限者，**When** 讀取簽署頁、通知或下載副本，**Then** 不得取得建立人的管理備註與其他人通知資料。

### Edge Cases

- 草稿修改與發起同時發生：只允許一致結果，不得在文件已發起後覆寫部分設定。
- 草稿含已離職或已不在目前組織架構中的員工：沿用既有資格檢查，畫面明確指出需處理的人員，不得宣稱完整回填卻靜默遺漏。
- 使用者瀏覽器所在時區不同：起迄日期以台北時間解讀及呈現，不得重新開啟後偏移一天。
- 只有拒簽者或沒有人成功簽署：提示沒有已簽署副本可匯出，不產生假成功的空 ZIP。
- 同名簽署人、外部簽署人沒有員編：ZIP 內檔名仍可唯一辨識，不覆蓋或誤配。
- 文件仍簽署中、已到期或已停止：持有效員工 session 者可匯出既有已簽副本，不要求文件先全員結案。
- 大檔超出單包容量目標：可形成多個獨立 ZIP，不切斷單份 PDF；支援總量超過 4 GiB 的情境。
- 同時有多個匯出要求：可排隊、可追查，不得無限制搶占正常簽署所需資源。
- 重複送出同一次申請或重試：不得造成使用者無法辨認的重複工作或不一致成果。
- 儲存空間不足、成果不可用或下載權限已失效：顯示正確失敗狀態，不影響來源副本與既有證據。

- 通知所有未簽者時名單跨頁，不能只取可見列；名單為零時提示無人可通知，不建立空的成功批次。
- 同一次操作因網路重送或按鈕連點：不得重複建立整批通知；建立人另一次明確操作仍受逐人一天一次限制，不因建立新批次解除。
- 外部邀請寄出後原可解密資訊可能已清除：催簽必須有有效入口，不能假設重跑原工作即可寄出；不得恢復舊補簽輪的失效資格。
- 郵件服務接受信件後、成功紀錄寫回前中斷：不得保證實際送信絕對一次；記錄結果未確認的情況，重試策略在 plan 明定。
- 已寄出只表示郵件服務接受，不代表送達收件匣、已讀或已簽署。
- 原因留白、中文、emoji、組合字元：長度以 Unicode code points 計算，不把 UTF-16 code units 或畫面字形數當成同一規則。
- 已到期、停止或完成文件：禁止新的催簽與拒簽；建立人仍可維護非證據性管理備註，不改變文件與簽署結果。
- 已發起文件若未開放拒簽，不因功能上線而自動開啟；既有證據及固定選項不變。
- 備註修改不影響簽名證據與已產製 PDF；同時儲存採最後成功寫入值，畫面以後端回覆為準。

## Requirements

### Functional Requirements

- **FR-001**: 系統 MUST 讓建立人暫存完整的公司員工與外部簽署人混合名單；純外部名單亦可暫存。外部姓名、Email 與類型須正確保存及回填，沿用既有正規化與身分驗證規則。
- **FR-002**: 草稿 MUST 保存起始與截止時間，允許尚未填齊；兩端皆有值時開始必須早於截止。明確清空須被保存，未要求變更的期間須保留。
- **FR-003**: 名單與期間的同次保存 MUST 全部成功或全部不變。僅建立人可修改草稿，發起後不得透過草稿暫存改寫固定設定。
- **FR-004**: 暫存 MUST NOT 發起文件、寄送邀請或授予簽署資格；正式發起仍驗證完整名單、期間與其他必要條件。重新開啟與列表顯示須一致。
- **FR-005**: 起迄日期 MUST 以台北時間解讀及顯示，並保留可辨認的時間意義，不受瀏覽器時區影響。
- **FR-006**: 後端 MUST 依前端提交並由後端驗證保存、於發起時固定的 watermark 設定產製個人完成副本；true 才加印、false 不加印。前端保留設定能力，移除下載時繪製責任；下載請求不得覆寫文件設定。
- **FR-007**: 浮水印 MUST 使用「饗賓集團 內部文件 請勿外流」，參照既有前端淡灰、斜向、錯列與透明樣式，覆蓋所有可視頁面，中文無缺字且不妨礙簽名及驗證資訊辨識。
- **FR-008**: 浮水印 MUST 在完成副本定稿及完整性紀錄確立前完成。原始文件、已成立簽署證據及已產製副本不得因本功能被覆寫；舊文件遵守原固定設定。
- **FR-009**: 個別下載與 ZIP 內的同一副本 MUST 使用相同完成產物，不因下載者、次數或入口改變內容。
- **FR-010**: 持有效員工 session 者 MUST 能對所有簽署文件逐份申請全部已簽署副本匯出，不受建立人限制，無須逐文件另行授權；須能查找各文件、查詢其匯出紀錄並下載成果，系統先受理並在背景處理；不得要求使用者逐人下載或手動拆分 6,000 人名單。
- **FR-011**: 新建匯出工作 MUST 固定該次受理時的成功簽署範圍與對應紀錄；既有副本固定版本，尚未產製者綁定該次簽署的副本，不混入之後的簽署。
- **FR-012**: 拒簽雖視為該人的流程完成，MUST NOT 被計入已簽署副本數或生成假的簽署副本。待簽者亦不納入。
- **FR-013**: 系統 MUST 重用已產製副本；未備妥時等待並可追查，永久失敗或完整性驗證失敗須明確回報，不得漏檔而宣稱完成。
- **FR-014**: 匯出 MUST 支援至少 6,000 份代表性完成 PDF 及超過 4 GiB 的成果；限制同時處理量與資料緩衝，不能以一次把全部副本載入記憶體作為前提。
- **FR-015**: 成果 MAY 為單一 ZIP 或依容量形成的一組獨立 ZIP；每份 PDF 必須完整且僅出現一次，不得要求跨分卷拼接才可解壓。打包參數須由效能驗證決定，不預設固定人數分包。
- **FR-016**: 匯出紀錄 MUST 保存申請者、文件、申請時間、固定範圍、預期及已處理數、目前狀態、完成時間、失敗原因與可用成果；進度不得把尚未成功儲存的成果當成完成。
- **FR-017**: 系統 MUST 在所有指定副本驗證、打包與儲存完成後才發布該次完整成果，並確保同名人員不互相覆蓋。
- **FR-018**: 工作中斷及重試 MUST 保留同一範圍並可追查；未完成成果不可下載，失敗暫存物不得無限制累積；不得影響來源副本。
- **FR-019**: 匯出成果 MUST 自完成起保留七天；同一文件在此期限內再次申請匯出或下載，皆重用相同成果，不重新打包、不刷新到期時間，並支援續傳。須顯示快照時間、收錄份數與到期時間；七天內新增簽署不納入既有成果。到期後再申請才建立新快照，保留歷史紀錄及來源副本；每次存取仍須驗證權限。
- **FR-020**: 系統 MUST 以排隊及受控資源處理同時申請；使用者離開或登出不取消已受理工作，正常簽署不得因匯出而失敗或遺失。
- **FR-021**: 所有錯誤與歷史資訊 MUST 遵守既有資料裁切規則，不揭露儲存位置、憑證、其他文件內容或未授權的簽署人資料。

- **FR-022**: 新發起文件 MUST 可由建立人決定是否開放拒簽，並固定該設定；管理與本人簽署畫面須讀取後端權威設定。
- **FR-023**: 已開放拒簽時，符合資格的本人 MUST 可確認拒簽；原因選填，trim 後最多 200 個 Unicode code points，時間由後端決定。
- **FR-024**: 拒簽 MUST 為該人的不可逆終態，不可再簽署、補簽或催簽，亦不得產生假的已簽 PDF；不得阻止其他待簽者繼續。
- **FR-025**: 無待處理人員時 MUST 能結案，包括混合已簽／已拒或全員拒簽；已簽者必要副本須完成，全員拒簽不得等待不存在的副本。已簽與已拒數量始終分開。
- **FR-026**: 簽署與拒簽競態 MUST 僅成立一種結果；同一次成功拒簽重送不得改寫證據或重複歷程。
- **FR-027**: 建立人 MUST 能以一次操作要求一位、多位指定或全部符合資格的外部待簽者催簽。前端提交文件與簽署人識別，不以任意姓名、Email 或邀請憑證指定收件人。
- **FR-028**: 後端 MUST 驗證管理權限、文件狀態、簽署人歸屬與資格，從權威資料取得收件資訊，持久保存批次及逐人紀錄後才受理寄送；背景寄送不依賴頁面保持開啟。
- **FR-029**: 批次 MUST 對重複簽署人去重；跨文件或不存在識別整批拒絕，其餘業務上已不適合寄送的人員記錄未寄送原因，至少一人可寄時才建立批次。
- **FR-030**: 實際交付郵件服務前 MUST 再次驗證資格、有效期限及入口；不向已簽、已拒或失效資格寄送新提醒。已寄出的郵件不構成繞過簽署資格的授權。
- **FR-031**: 催簽信 MUST 包含文件名稱、目前有效期限及可用入口，逐人寄送，不向收件人揭露管理備註或其他簽署人資料。
- **FR-032**: 首次邀請與各次催簽 MUST 可區分，保留批次、操作者、時間、對象、結果、嘗試次數及穩定失敗原因；成功明細不因整批重試再寄。
- **FR-033**: 同一次申請的技術重送 MUST 不建立重複批次；使用者另一次主動催簽仍須遵守同一文件、同一外部簽署人按台北時間曆日一天一次，每日午夜 00:00 重置，不採滾動 24 小時，不能以不同批次或操作者繞過。排隊或處理中的同一人不可重複排入；受限制者明確回報未寄送原因。本功能不新增自動排程催簽。
- **FR-034**: 已受理、等待寄送、處理中、已寄出、失敗及未寄送的業務結果 MUST 可辨識；不得以受理成功代替寄送成功，亦不得聲稱已讀。
- **FR-035**: 名單 MUST 回傳每人的 `signedAt`、`rejectedAt`、`rejectReason`、管理備註及通知摘要；未發生的時間為空，留白原因可為空字串。本人視角須裁切管理欄位。
- **FR-036**: 建立人 MUST 能儲存及清除任一名單成員的管理備註；trim 後最多 30 個 Unicode code points，後端驗證，保存成功後重新讀取一致。
- **FR-037**: 備註 MUST 僅為管理資料，不得進入簽署人頁面、催簽信或已簽署 PDF，不得改寫簽署證據；越權或不合法輸入不得改變既有值。
- **FR-038**: 建立人可見的簽署與拒簽歷程 MUST 回傳可辨識操作者的姓名與穩定簽署人識別，真正系統事件才標記為系統；本人僅看本人與必要文件事件。
- **FR-039**: 已拒分頁、列表與簽署紀錄匯出的拒簽資料 MUST 一致；不得因拒簽算流程完成就計入已簽人數或 ZIP 副本數。
- **FR-040**: 所有功能 MUST 不洩漏 credential、簽名圖或其他人敏感資料，保存與讀取管理資料均需後端授權。
- **FR-041**: 本階段催簽 MUST 僅支援外部 Email 簽署人；全部通知只選符合資格的外部待簽者，指定名單中的內部員工須回報未支援且不寄送。畫面可選對象、按鈕說明及可通知人數須反映此範圍。內部同事催簽已列為後續規格，不在本次實作，亦不預先加入員工 Email 欄位、來源整合或內部寄送流程。

### Key Entities

- **草稿簽署設定**：文件建立人尚可修改的內外部名單與起迄時間；暫存不代表發起。
- **個人完成副本**：對應一位成功簽署者的固定 PDF，含該人的簽名、日期、驗證資訊及適用浮水印，與原始檔及簽署證據可追溯。
- **匯出工作**：一次受理的範圍與處理歷程，具有固定簽署名單、進度、結果及申請人。
- **匯出成果**：工作產生的一個或一組可下載 ZIP，與實際收錄的個人副本一一對應；不取代原始完成副本。

- **簽署人處理結果**：待簽、已簽或已拒，及相應時間／拒簽原因；已簽與已拒都終止該人的待辦，但只有已簽有個人副本。
- **通知批次與明細**：一次催簽操作及各人的寄送狀態，與首次邀請區分，可重試並追查。
- **管理備註**：建立人針對該文件某位簽署人的簡短文字，不是簽署內容或拒簽原因。
- **簽署歷程**：可追溯動作、操作者及時間，依管理與本人視角裁切。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 混合及純外部名單、完整／部分／清空期間的保存與重新登入回填驗收中，預期資料一致率為 100%；錯誤保存不改變原資料的案例通過率為 100%。
- **SC-002**: 新發起且 watermark=true 文件的直向、橫向、90／180／270 度旋轉及裁切頁面驗收中，每頁浮水印中文可辨識、原內容可讀且驗證碼可使用，通過率為 100%；watermark=false 不加印，設定與產物一致率為 100%。
- **SC-003**: 個別下載與匯出取出的同一副本內容一致率為 100%；舊文件、原始檔與簽署證據不被覆寫的案例通過率為 100%。
- **SC-004**: 一次 6,000 份代表性副本的匯出，解壓後份數與固定名單完全一致，漏件、重複與誤配均為 0；至少包含一組超過 4 GiB 的成果驗收。
- **SC-005**: 在約定測試環境中，至少 95% 匯出申請於 5 秒內顯示受理結果；使用者離頁後均可由歷史紀錄找到工作，無須等待全部打包。
- **SC-006**: 6,000 份匯出期間，無記憶體耗盡或正常簽署失敗；與相同負載但未匯出的基準比較，簽署提交的第 95 百分位耗時增加不超過 20%。此為驗收目標，非已達成的容量承諾，環境與負載須於 plan 固定。
- **SC-007**: 讀取失敗、內容竄改、工作中斷與未授權下載的驗收中，不完整或越權成果發布數為 0；重試不改變固定名單；人資跨建立人查找、匯出、查詢及下載均成功，無員工 session 或僅持外部簽署 session 者仍拒絕。
- **SC-008**: 七天內再次申請匯出或下載均重用同一成果，不新增打包工作或延長效期；新增簽署不混入，滿七天後新申請才更新快照；支援續傳的下載端可在中斷後取得完整成果並成功解壓，內容與原成果一致。

- **SC-009**: 內外部本人拒簽、原因長度、設定關閉、截止及競態驗收皆通過；每人有效終態與拒簽事件最多一筆。
- **SC-010**: 全員已簽、混合已簽／已拒、全員拒簽三種結案情境皆完成正確分類，拒簽者的假簽名或假 PDF 數為 0。
- **SC-011**: 單人、多人、所有外部待簽及跨頁名單的催簽驗收中，受理範圍與逐人結果可完整核對；已知失去資格者不新增寄送，跨文件及內部員工寄送數為 0；同日重送、台北時間午夜前後及跨午夜排隊的頻率驗收均通過。
- **SC-012**: 同一次申請重送只形成一批紀錄；同一文件與外部簽署人的每日催簽限制，在不同批次及並發操作下仍成立；失敗重試不重寄已確認成功明細，結果不明案例須可追查而非假稱完全成功。
- **SC-013**: 備註 0／30／31 code points、空白清除、取消、重新整理與越權驗收全部通過；其他人取得管理備註的案例數為 0。
- **SC-014**: 列表、已拒分頁、匯出及歷程的簽署／拒簽時間、原因、姓名與人數一致率為 100%。

## Assumptions

### 已確認方向及本規格採用的預設

- 一次匯出以「同一份電子簽文件的全部已簽署個人副本」為範圍，不包含跨文件全公司總匯出。
- 人資可跨建立人查找所有簽署文件、申請各文件全部已簽副本、查詢匯出紀錄與下載成果；不要求建立人逐份授權。本次不在本專案判斷人資角色，後端仍驗有效員工 session、資源歸屬及成果期限。Portal 管理發起入口資格；這不代表本地 API 已驗證人資。因此任何持有效員工 session 的使用者在本階段均能使用跨建立人匯出相關 API。此決定不自動變更草稿編輯、催簽或備註的既有管理權限；role／permission 留待後續規格。
- 浮水印以文件保存的 watermark 設定為準；前端保留記錄選擇的能力，後端依設定繪製，未開啟者不加印。
- 草稿簽署設定保存沿用至少一位已加入名單的要求；上傳初始草稿不需名單的既有能力維持。姓名是否可留白沿用既有規則，本次不另改外部身分要求。
- 起迄時間以既有台北日期選擇體驗為準；本功能不新增尚未到期延期或發起後任意修改期間。
- ZIP 自完成起保留七天，期間內申請皆重用同一成果與快照；不因後續新增簽署或下載延長期限。到期保留匯出紀錄，可再申請；不改變原始副本留存規則。若期限內成果意外毀損或遺失，須顯示不可用，不可假稱能下載或默默另建新快照。
- 單包／分包、壓縮等級、併發、儲存方式與完成耗時須依 [效能研究](../../docs/research/2026-10-20-bulk-pdf-export-performance.md) 及代表資料實測決定；研究中的容量與併發數字僅是實驗起點。
- 6,000 份為容量驗收情境，不是固定產品人數上限；測試須涵蓋真實可接受範圍的檔案大小、頁數與內容類型，不能以複製同一份極小 PDF 代替。

### 簽署人管理與催簽邊界

- 催簽以同一文件、同一外部簽署人為單位，按台北時間曆日一天一次，每日午夜 00:00 重置；不採滾動 24 小時。 已排隊／處理中不得重複申請；明確失敗的寄送重試沿用原明細，結果未確認不可當成未寄送。

- 內外部簽署人皆適用拒簽、列表結果與管理備註；只有催簽的收件範圍限定外部，不能把此外部限制誤套到拒簽或名單。
- 備註上限 30 字、拒簽原因選填且最多 200 字，依使用者提供的畫面與既有字元計算規則。
- 起始時間尚未到達時不催簽；到期後須先補簽重新開放，再由建立人主動催簽。
