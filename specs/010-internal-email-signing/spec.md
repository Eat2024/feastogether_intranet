# Feature Specification: 內部員工 Email 邀請與 OTP 簽署

**Feature Branch**: `feat/010-internal-email-signing`（功能整合分支；未部署）

**Feature Directory**: `specs/010-internal-email-signing`

**Created**: 2026-10-21

**Status**: Backend Implemented — 已依八張 tickets 實作；完整驗證結果與交付限制見 [quickstart](quickstart.md)，票單合併／審查紀錄另見本機 tracker，不代表前端或部署完成。

**Input**: 公司內部員工簽署也要走 Email；fgapi 已新增 org_chart 與 hr/staff_emails，本規格串接兩個 endpoint 以取得員工與 Email，將內部員工簽署串成與外部簽署相同的 Email 邀請、OTP 與簽署流程。

## Clarifications

### Session 2026-10-21 — Grilling 決策

- Q1：一人缺少有效信箱是否阻擋整份發起？ → 是。列出需處理的人員，建立人可移除後再發起，或待來源資料修正；不自動略過、不手填替代信箱，草稿可暫存。
- Q2：發起後信箱是否固定？ → 是。邀請、OTP、催簽與補簽皆使用發起時固定地址；本次不做地址更正功能。
- Q3：不同員工同信箱是否阻擋？ → 否，一律依各自指派寄出；不新增共用信箱檢查、警告或阻擋，不依 Email 合併通知。
- Q4：本次交付範圍？ → 僅後端串接與驗證；前端不實作，透過 spec 與後續 API contract 告知前端工程師的 agent 如何串接。一般員工登入仍不可繞過後端 OTP 檢查。
- Q5：是否納入內部催簽？ → 是，包含人工催簽、補簽通知與內外部混合名單，沿用每天一次的催簽限制。
- Q6：是否保留舊內部免 OTP 簽署途徑？ → 否。本專案尚無 UAT、PRD，本次以新發起的測試文件驗收，不建立舊文件免 OTP 相容分支；既有簽署證據不改寫，也不自行刪除資料。

## 背景與範圍

- Spec 006 已完成組織樹後端與兩小時共用 Redis 快取。本次沿用，前端組織選人只提供串接規格，由前端工程師的 agent 後續實作。
- Spec 008 已完成外部 Email 邀請、OTP、簽署與本人副本下載，本次將相同行為提供給內部員工。
- Spec 009 將內部催簽留待後續規格，本次一併接上既有人工催簽與混合名單通知，不增加自動催簽。
- 內部員工仍是內部簽署人，保留本機帳號關聯與員工身分快照；Email 是通知與驗證管道，不將其轉換成外部人員。
- 本次實作包含後端選人資料、信箱查詢與發起驗證、邀請與補簽通知、OTP、簽署／拒簽、本人副本下載及既有人工催簽，以及前端串接交接規格。不修改 client；「我的簽署」整個列表的正式化亦不在本次範圍。後端所有相關入口均不得成為略過 OTP 的途徑。

## User Scenarios & Testing

以下保留完整使用者情境作為前後端共同契約。此次交付以後端 API、授權、通知及資料結果驗收；涉及畫面顯示與瀏覽器操作的描述是前端後續串接要求，不代表本次須實作或已完成前端。Independent Test 於本次以對應 HTTP／整合測試重現，前端完成後再執行畫面端到端驗收。

### User Story 1 - 選取公司員工並確認可寄送邀請 (Priority: P1)

建立人可瀏覽公司組織選取員工，系統依員編取得員工 Email，發起前指出無法寄送的人員，無須建立人逐筆輸入信箱。

**Why this priority**: 取得可信且正確對應員工的信箱，是邀請與 OTP 的前提。

**Independent Test**: 使用含巢狀部門、前導零員編及缺少信箱的合成人員資料完成選人、暫存與發起，確認人員身分及通知對象一致。

**Acceptance Scenarios**:

1. **Given** 建立人具有有效員工登入，**When** 開啟組織選人，**Then** 顯示上游部門階層與直屬員工，可選取員工並與既有員編搜尋的結果去重；單純瀏覽不匯入全公司帳號。
2. **Given** 已選取內部員工，**When** 檢查通知資料，**Then** 依完整員編取得每人的信箱結果，顯示可通知或無法取得有效信箱；不得將某一筆結果依陣列位置配給另一位員工。
3. **Given** 有人缺少有效信箱，**When** 暫存草稿，**Then** 可保留選人結果且不寄信；發起時列出需處理的已選員工，整份文件維持草稿，其他人也不會先收到邀請。
4. **Given** 草稿先前曾查到信箱，**When** 發起，**Then** 後端重新取得所有內部簽署人的有效信箱，通過全部驗證後固定此次收件信箱並發起，不信任前端傳入或舊預覽中的地址。
5. **Given** 選人數超過 100 人，**When** 查詢信箱，**Then** 建立人無須自行拆分名單，所有員工都被核對；任一批失敗不得被當成完整查詢成功。

### User Story 2 - 員工從 Email 完成 OTP 與簽署 (Priority: P1)

員工收到專屬邀請信，在一般瀏覽器或手機點開連結，驗證同一信箱收到的 OTP 後閱讀、簽名與送出，不必先登入內部入口網。

**Why this priority**: 完成使用者要求的內部 Email 簽署主流程，且持有連結不足以簽署。

**Independent Test**: 發起一份含內外部簽署人的文件，使用未登入入口網的瀏覽器，兩者各自從 Email 通過 OTP 完成簽署，確認歸屬、證據與副本正確。

**Acceptance Scenarios**:

1. **Given** 文件成功發起，**When** 寄送通知，**Then** 每位內部員工收到寄往固定信箱的專屬邀請，混合名單中的外部簽署人也沿用原流程；建立人可查看各人的寄送狀態。
2. **Given** 有效邀請，**When** 只開啟連結，**Then** 顯示邀請確認頁，不寄 OTP、不建立存取，也不顯示文件內容；按下開啟後才寄 OTP 並顯示遮罩信箱。
3. **Given** OTP 正確且有效，**When** 驗證成功，**Then** 只取得該簽署人對該文件的受限存取，可同意聲明、閱讀、手寫簽名與確認送出；不取得一般員工登入權限。
4. **Given** 已有員工登入但尚未通過本次文件的 OTP，**When** 從舊內部入口或直接呼叫簽署介面，**Then** 不得完成該指派的簽署；需引導使用邀請與 OTP，不能僅以登入取代驗證。
5. **Given** 文件尚未開始、已停止、到期或刪除，**When** 待簽者開啟或提交，**Then** 依既有期限與狀態規則顯示尚未開始或不可簽署，不產生成功簽署。
6. **Given** 員工通過 OTP 後選擇拒簽，**When** 符合 Spec 009 的拒簽條件並提交，**Then** 沿用既有拒簽、備註與歷程規則，後續通知不得再將其當成待簽者。

### User Story 3 - 簽署後留存本人副本 (Priority: P1)

員工簽署後可立即等待並下載本人副本，日後也可從原信件重新驗證並下載。

**Why this priority**: 內外部簽署人均須能自行留存簽署文件。

**Independent Test**: 員工簽署後下載本人副本，關閉瀏覽器並在簽署期限過後重新開啟邀請與驗證，確認仍能取得相同副本。

**Acceptance Scenarios**:

1. **Given** 簽署完成，**When** 本人副本產生中、可下載或產製失敗，**Then** 分別顯示等待、自行下載或聯絡發起人的狀態；產生中自動更新，不要求重新簽署。
2. **Given** 已簽署者日後開啟原邀請，**When** 重新完成 OTP，**Then** 直接進入完成與下載畫面，不再提供簽署；不受文件停止、到期或完成影響，文件刪除後不可存取。
3. **Given** 有效的某位員工簽署存取，**When** 更換文件或簽署人識別，**Then** 不能讀取其他人的資料或副本，也不能操作文件管理或一般員工功能。

### User Story 4 - 對內部員工催簽與補簽 (Priority: P2)

建立人可使用既有人工催簽通知尚未簽署的內部員工，文件補簽時也能寄出新邀請。

**Why this priority**: 接續 Spec 009 暫緩的內部通知，避免發起後的必要通知仍僅適用外部人員。

**Independent Test**: 對含內外部待簽、已簽與已拒簽人員的名單執行全部／指定催簽及補簽，核對通知對象與結果。

**Acceptance Scenarios**:

1. **Given** 符合 Spec 009 催簽條件的內外部混合名單，**When** 全部或指定催簽，**Then** 兩種類型皆可通知，逐人顯示受理、略過或失敗結果；同一文件同一簽署人台北時間每天最多一次，午夜重置。
2. **Given** 同一人今日已催簽、已簽署、已拒簽或文件不可催簽，**When** 再次提交或與另一請求同時提交，**Then** 沿用既有限制且不重複受理；OTP 寄送額度與人工催簽額度分開計算。
3. **Given** 到期文件符合補簽規則，**When** 開放補簽，**Then** 內部未簽者同樣取得新邀請，舊邀請不得再授權其簽署；已簽者的原邀請下載能力與簽署證據不變。

### Edge Cases

- 上游省略某個員編，無法區分尚未同步、非在職或無信箱：只提示「無法取得有效員工信箱」，不得臆測原因或自動改成外部簽署人。
- 上游回傳空白／不合法信箱、未請求的員編或同員編的衝突結果：不得寄送或接受為完整成功；保留草稿並提示修正或稍後重試。
- 組織樹只有正式員工；既有員編搜尋可包含試用員工。試用員工經原資格檢查且取得有效信箱後可走相同流程。
- 超過 100 人時任一查詢批次逾時或失敗：不得先發起部分名單、先寄出部分邀請或以舊資料補足。
- 不同員工共用同一信箱：依使用者決策一律逐筆指派寄送，不新增共用信箱檢查、警告或阻擋，不依 Email 合併通知；每筆指派、邀請、OTP 與副本仍分離。
- 發起後上游信箱異動：既有邀請、OTP、催簽與補簽均使用發起時固定信箱，不自動改寄新地址。改收件人與舊文件信箱補登不在本次範圍。
- OTP 錯誤、過期、已用、重寄、並發驗證、寄信失敗與舊分頁身分錯置：遵守 Spec 008 規則，不可繞過驗證或簽成另一人。
- 郵件寄送失敗不撤銷已成功發起的文件；建立人看到失敗狀態並沿用既有寄送重試。信箱查詢失敗則發生在發起前，不能混為寄信失敗。
- 既有已發起且無固定信箱的內部指派：不自動補寄、不回填歷史快照或改寫證據，也不保留免 OTP 的簽署／拒簽授權；缺少有效邀請與驗證條件時不得提交。本次以新發起測試文件驗收，既有草稿可在完成信箱驗證後正常發起。不自行刪除既有資料。

## Requirements

### Functional Requirements

- **FR-001**: 後端 MUST 提供組織樹與既有員編搜尋供前端選人，接受依員工身分去重的草稿名單並保留員編前導零。組織樹只供選人，不作為最終授權依據；畫面串接依本規格交接，不在此次實作範圍。
- **FR-002**: 系統 MUST 串接 fgapi 的組織與員工信箱來源（契約見 Dependencies），由後端查詢已選員工的信箱；前端不得直接取得上游憑證或提供可信收件地址。
- **FR-003**: 信箱結果 MUST 依完整員編與內部帳號對應，不依陣列順序；一次查詢超過上游上限時由系統完成拆批與完整性核對，不要求使用者拆單。
- **FR-004**: 草稿 MUST 能保存尚無有效信箱的員工選擇；發起前 MUST 重新查詢並驗證所有內部簽署人的收件信箱，任一缺漏、不合法或上游失敗即拒絕整次發起，不留下部分發起或通知。
- **FR-005**: 發起成功 MUST 固定每人的通知信箱及既有員工身分快照，保留內部類型與帳號關聯；MUST NOT 將內部員工重建為外部簽署人或因相同信箱合併指派。不同內部員工地址相同仍 MUST 依各自指派寄送，不新增共用信箱檢查、警告或阻擋。
- **FR-006**: 新發起文件的內外部簽署人 MUST 均收到個別邀請；未來開始的文件於發起時寄出邀請，開始前依 Spec 008 顯示開始時間且不寄 OTP。
- **FR-007**: Email 邀請 MUST 只授權單一文件的單一簽署人，無須一般員工登入；MUST NOT 建立一般員工 session、開放跨文件或文件管理權限。
- **FR-008**: 單純開啟邀請 MUST 不建立存取或寄碼；主動確認開啟後 MUST 將 OTP 寄至該指派固定信箱，成功驗證前不得從邀請入口讀取文件、簽署或下載。
- **FR-009**: OTP MUST 為 6 位數字、10 分鐘有效、只能用一次、錯滿 5 次失效；所有寄碼入口共同套用每人 60 秒冷卻與每小時最多 5 封，新碼使舊碼失效。並發驗證不得重複消耗成功；寄送失敗不建立存取。
- **FR-010**: OTP 驗證後 MUST 使用獨立於邀請連結的存取憑證，依 Spec 008 保存及驗證；瀏覽器階段結束或 8 小時到期後重新驗證。不得用邀請原值冒充已驗證存取。
- **FR-011**: 內部指派 MUST 通過對應文件與簽署人的 OTP 才能簽署或拒簽；一般員工登入不得繞過此條件。包含舊內部入口在內的後端 API MUST 執行相同限制並回傳穩定錯誤，前端後續依串接規格提供引導；不以文件新舊放寬驗證。
- **FR-012**: 簽署、拒簽、同意版本、文件狀態與期限、重送寬等性、本人副本及證據完整性 MUST 沿用 Spec 003、007、008、009 的現行有效規則。提交時 MUST 核對頁面簽署人與受限存取身分，避免同瀏覽器切換人員後簽錯人。
- **FR-013**: 已簽員工 MUST 能在同次有效存取下載本人副本，也能日後從原邀請重新完成 OTP 後下載；下載不設期限，文件停止、到期或完成不影響此權利，文件刪除後失效。不得授權重簽或其他人副本。
- **FR-014**: 內部人工催簽 MUST 使用 Spec 009 相同資格、每日限額、混合批次與通知紀錄規則，移除僅外部可催簽的限制；補簽 MUST 使用 Spec 007 相同期限與邀請更新規則。兩者使用固定信箱，不另建立自動排程。
- **FR-015**: 建立人 MUST 能辨識查不到信箱、查詢服務不可用與郵件寄送失敗，看到目前文件相關人員的必要結果；未授權者不得查詢員工信箱。一般組織瀏覽不得附帶全公司信箱。
- **FR-016**: 邀請與驗證畫面 MUST 只揭露必要資訊，OTP 頁僅顯示遮罩信箱；上游憑證、名冊、信箱、OTP、邀請與存取秘密不得寫入日誌或對外錯誤。測試資料 MUST 為合成資料。
- **FR-017**: 系統 MUST 保留既有不可變簽署證據，不自行刪除資料；MUST NOT 為舊文件保留免 OTP 的簽署／拒簽途徑，不建立新舊驗證模式的相容分支。以新發起的合成測試文件驗收，不自動補寄或回填既有指派。
- **FR-018**: 本次 MUST 交付後端能力與前端串接規格，不修改 client。規劃及後端交付時 MUST 補齊實際 API 路徑、方法、認證、請求／回應、錯誤與串接順序，供前端工程師的 agent 使用；未完成的畫面不得宣稱為已完成。

### Key Entities

- **組織候選員工**：供選人的部門與員工資料，完整員編是與信箱來源的對應鍵，非本機 userId。
- **員工信箱查詢結果**：已選員工對應的可信收件地址，或無法取得有效地址的結果；上游缺漏不代表已知的人事狀態。
- **內部簽署人指派**：內部帳號、員工身分快照、固定通知信箱、文件及簽署狀態的關係，與外部指派保持區別。
- **簽署邀請與 OTP 存取**：限定一人一文件的邀請與信箱驗證，不能轉為一般員工登入。
- **通知紀錄與個人副本**：沿用既有逐人通知結果與本人簽署產物，不建立另一套簽署證據。

## Success Criteria

### Measurable Outcomes

- **SC-001**: 以 1、100、101 及 6,000 位合成人員進行選人與信箱核對，100% 對應正確；缺漏、跨人誤配及重複指派數皆為 0。
- **SC-002**: 所有缺信箱、格式錯誤與查詢失敗驗收案例，誤發起或提前寄出邀請的案例數為 0；草稿可保留並於修正後成功發起。
- **SC-003**: 後端內部及混合名單的「邀請 → OTP → 簽署 → 本人副本下載」整合驗收通過率 100%，不需手動輸入員工收件信箱；桌面與手機畫面驗收交由後續前端串接階段完成。
- **SC-004**: 僅持有邀請連結、僅有一般登入、身分錯置、跨人／跨文件及 OTP 重放的未授權簽署案例數為 0；OTP 時限、次數與重寄邊界案例通過率 100%。
- **SC-005**: 已簽員工於期限後重新驗證下載的有效案例通過率 100%；取得他人副本或再次簽署的成功案例數為 0。
- **SC-006**: 混合名單催簽與補簽驗收中，應通知、應略過與寄送失敗結果全部正確；同人同日重複受理催簽為 0。
- **SC-007**: 既有外部簽署回歸與內部舊入口不可略過 OTP 的案例通過率 100%，歷史證據被改寫或資料被自行刪除的筆數為 0。
- **SC-008**: 前端交接規格涵蓋本次各個操作的實際契約、順序、錯誤與畫面狀態對應；不把文件中的預期畫面當作已實作成果。

| 簽署與拒簽 | 依驗證後本人狀態顯示操作；同意聲明、提交時帶上契約要求的簽署人識別；舊入口遇驗證不足需引導從邀請信開啟 | 提供本人資料、聲明、閱讀資源、簽署／拒簽契約，明列身分錯置、尚未開始、到期、停止、驗證失效等結果 |
| 本人副本 | 依產生中／可下載／失敗顯示狀態；產生中自動更新，已簽者重開邀請並驗證後直接進完成頁 | 提供本人結果、產製狀態與下載契約，不回傳其他人資料 |

## Assumptions 與 Dependencies

### 已核對的 fgapi 契約

以下為使用者指定的整合依賴，不另設計新的上游 API。2026-10-21 已讀取本機 fgapi routes、文件、實作與測試，尚未對部署環境發送請求。

| 來源 | 已確認契約與限制 | 本規格用途 |
| --- | --- | --- |
| `GET /api/v1/hr/org_chart` | 啟用部門階層及正式員工；員工含 `person_empid`、姓名、職稱，不含 Email；上游快取 60 秒 | 沿用 Spec 006 後端與 7,200 秒快取，提供前端選人串接規格 |
| `POST /api/v1/hr/staff_emails` | `person_empids` 為 1–100 個完整英數員編，每組最多 20 碼；回傳 `data: [{ person_empid, email }]`，重複員編去除 | 後端依已選員工查詢並核對通知信箱 |

- 兩個來源皆使用既有服務端 API Key；沿用既有上游連線設定，不新增環境變數。
- `staff_emails` 只回傳已同步、未刪除、試用或正式且 Email 非 null 的人員；無匹配時可回傳空陣列。仍須驗證空白與不合法地址，不能只憑欄位存在即寄送。
- 信箱來源是每日 04:00 自 Portal 同步的 fgapi 人員資料，新進或異動可能尚未同步；本功能不承諾即時 HR 在職驗證，不新增同步工作或過期資料 fallback。
- 來源依據：fgapi `routes/api.php`、`app/Http/Docs/V1/UserControllerDocs.php`、`app/Http/Controllers/Api/V1/UserController.php`、`app/Services/OrgChartService.php`、`tests/Feature/StaffEmailsTest.php`。

### 已確認決策與不包含項目

- 信箱缺漏阻擋整份發起，草稿可暫存；不提供手填員工信箱或改寄其他信箱的替代流程。
