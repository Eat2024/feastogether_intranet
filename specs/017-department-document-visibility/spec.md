# Feature Specification: 電子簽依部門顯示與建立部門快照

**Feature Branch**: 本次未建立分支，沿用目前工作分支 `dev`

**Created**: 2026-11-02

**Status**: Implemented and locally validated — 部門瀏覽、發起人管理、匯出限制與切換演練完成；真實 UAT 尚未執行

**Input**: 使用者確認同部門員工應看到該部門全部電子簽，列表改為 `role=dep`；建立文件時保存建立人部門。先開 spec，盤點修改位置、API 與 DB 欄位，不實作功能。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 查閱同部門電子簽 (Priority: P1)

員工進入電子簽列表，看見所屬部門各建立人的文件；不因未被指定簽署而漏掉同部門文件，也不看見其他部門未參與的文件。

**Why this priority**: 取代先前「僅本人」及「全公司」的列表範圍，符合部門共同追蹤需求。

**Independent Test**: 使用甲部門兩位員工與乙部門一位員工，各建立文件並交叉查閱列表。

**Acceptance Scenarios**:

1. **Given** 甲、乙同部門，丙不同部門且文件皆未刪除，**When** 甲或乙進入部門列表，**Then** 都看到甲、乙的文件，且不看到丙的文件。
2. **Given** 同部門存在草稿、簽署中、已到期、產製中、已完成及已停止文件，**When** 沒有設定篩選，**Then** 各狀態皆可見，軟刪除文件不可見。
3. **Given** 部門列表已載入，**When** 使用者搜尋建立人姓名／員編、文件名稱，或指定狀態、簽署日期區間，**Then** 僅在已授權的部門文件內篩選，保留原有排序與分頁。
4. **Given** 員工嘗試自行指定其他部門或切回全公司範圍，**When** 發出查詢，**Then** 系統拒絕不支援的參數，不能擴大可見範圍。
5. **Given** 員工沒有可用的部門代碼，**When** 查閱部門列表，**Then** 顯示無法取得部門資料的明確錯誤，不以空部門比對其他無部門的文件，不退回全公司資料。
6. **Given** 同部門員工不是發起人，**When** 開啟文件與來源預覽，**Then** 可唯讀瀏覽；直接呼叫編輯、刪除、發起、停止、補簽或通知管理操作仍由後端拒絕。

### User Story 2 - 建立時固定文件歸屬部門 (Priority: P1)

建立電子簽時，由系統保存建立人當時所屬部門；建立人日後調動，舊文件仍留在原部門。

**Why this priority**: 若只連結建立人目前部門，調職會改變歷史文件歸屬，無法穩定界定部門可見範圍。

**Independent Test**: 在甲部門建立文件後更新建立人的部門為乙，再以甲、乙部門員工查詢並建立新文件。

**Acceptance Scenarios**:

1. **Given** 建立人具可信部門代碼與名稱，**When** 建立草稿，**Then** 文件保存當時的部門代碼、名稱及原建立人，前端不需填寫部門。
2. **Given** 建立人由甲部門調往乙部門且系統員工資料已更新，**When** 查閱部門列表，**Then** 舊文件仍屬甲，新建文件屬乙。
3. **Given** 建立人沒有部門代碼，**When** 建立文件，**Then** 拒絕建立並提示更新部門資料，不留下半完成文件或孤立上傳檔案。
4. **Given** 部門僅改名而代碼不變，**When** 員工查閱部門列表，**Then** 舊文件仍可見，文件建立時的名稱不被覆寫。

### User Story 3 - 切換既有資料與既有入口 (Priority: P2)

維運人員能識別尚無部門歸屬的舊文件，依確認的遷移規則處理；其他登入與匯出入口不能意外造成不同的部門權限結果。

**Why this priority**: 系統已在 UAT，既有資料沒有可直接使用的建立部門快照。

**Independent Test**: 以包含缺部門員工、舊文件及既有登入 session 的資料演練切換，核對遷移前後筆數、權限與簽署證據。

**Acceptance Scenarios**:

1. **Given** 文件沒有建立部門快照，**When** 查詢部門列表，**Then** 不把未知歸屬視為任一部門共有，切換時依 FR-009 歸入 IT策略本部系統開發部後對該部門員工顯示。
2. **Given** 既有員工在不同正式登入入口重新登入，**When** 上游提供部門代碼，**Then** 系統保存一致的部門資訊，查閱同一部門得到一致結果。
3. **Given** 完成部署前演練，**When** 核對既有簽名、固定簽署參數、完成副本與驗證結果，**Then** 不因新增部門歸屬而改動簽署證據。

### User Story 4 - 同部門匯出與下載 (Priority: P1)

同部門員工可取得工作所需的匯出資料，跨部門不能從歷史紀錄或直接下載網址繞過權限。

**Why this priority**: 只限制列表而保留跨部門下載，無法達成此次部門範圍。

**Independent Test**: 對甲部門文件建立 Excel／PDF／ZIP 紀錄，以甲與乙部門員工呼叫列表、單筆、產生、重試與下載入口。

**Acceptance Scenarios**:

1. **Given** 員工與文件同部門，**When** 查詢歷史、匯出或下載，**Then** 依檔案狀態及既有契約成功，原文件設定不改變。
2. **Given** 員工與文件不同部門，**When** 查詢歷史及筆數，**Then** 不包含該文件紀錄；指定其 ID 查詢或下載也被拒絕，沒有新增工作或紀錄。
3. **Given** 原建立人已調往不同部門，**When** 使用一般匯出或歷史下載入口，**Then** 不因建立人身分繞過同部門限制；本人簽署任務的本人副本仍依既有資格使用。
4. **Given** 部門資料已更新或文件已刪除，**When** 重用先前取得的下載網址，**Then** 重新驗證當下權限與文件狀態，不沿用舊列表的授權結果。

### Edge Cases

- 同名不同代碼的部門不互通；只按代碼完全相等判斷，不按名稱或字串前綴。
- 上下層部門不自動互通；多部門兼任與代理權限不在本次範圍。
- 部門代碼缺漏或空白，不可沿用失效的舊代碼取得權限；不可把所有缺值文件聚合成一個部門。
- 員工已離職、停用或刪除，仍依既有身分規則拒絕存取；建立人帳號刪除不移除文件已保存的部門。
- 既有 session 所屬員工尚未補上部門代碼，不可僅因 session 有效就取得部門列表。
- 同部門資格本身不等於可以簽署別人的任務，也不等於可取得他人的簽名與個人副本。
- 文件草稿修改、發起、補簽、停止及完成不得重設建立部門快照。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 電子簽列表必須依登入員工的可信部門與文件的建立部門比對；不由前端傳入部門決定授權。
- **FR-002**: 部門列表須包含同部門所有建立人的未刪除文件，各文件狀態皆可見；已刪除文件一律排除。
- **FR-003**: 文件建立時須保存建立部門代碼與名稱；歸屬代碼固定，後續調職、改名或流程操作不覆寫。
- **FR-004**: 正式登入流程須保存可信上游部門代碼；缺代碼時允許沿用既有登入與本人簽署規則，但拒絕部門列表與新文件建立，不以部門名稱或本機部門流水號替代。
- **FR-005**: 部門列表僅揭露文件摘要及原有建立人姓名／員編，不因部門共享增加簽署人個資、簽名、邀請憑證或檔案位置。
- **FR-006**: 保留原有關鍵字、狀態、簽署期間、排序與分頁功能；篩選無條件時顯示部門內全部，有條件時只縮小此範圍。
- **FR-007**: 不提供一般員工全公司文件列表，也不提供自行指定其他部門的能力。本人建立、本人被指派的既有個人範圍另行保留，不因此取得無關文件。
- **FR-008**: 同部門員工可瀏覽文件列表、文件詳情、來源文件預覽及必要的簽署進度／歷程，不能修改文件。建立人（本規格稱發起人）才可編輯草稿、改簽署設定或名單、刪除、發起、停止、補簽、修改備註或執行催簽／重送通知等管理操作，且仍受文件狀態規則限制。瀏覽不授予代簽、邀請憑證或原始簽名圖取得能力；同部門匯出與下載依 FR-010；本人簽署副本與外部邀請仍依 FR-011。
- **FR-009**: 使用者確認既有 UAT 電子簽文件統一歸屬「IT策略本部系統開發部」。以切換前盤點的舊文件集合補入使用者指定的部門代碼 `1029030000` 與名稱「IT策略本部系統開發部」，不依建立人目前部門推論，不更改 User 所屬部門或原建立人，不修改既有簽署證據。此為明確遷移歸屬決策，不宣稱是文件建立當時的歷史事實；正式代碼已由使用者提供；執行前核對目標環境的代碼／名稱對應，不另以名稱猜測或擴及上層部門。
- **FR-010**: 匯出文件查找、歷史匯出紀錄及各類型筆數、Excel／PDF／ZIP 產生、查詢、重試與下載一併限定同部門，以所屬文件的建立部門快照判斷，不以匯出人的部門判斷。直接使用文件、工作、紀錄或檔案 ID 也必須驗證；跨部門不得讀取或產生工作／下載紀錄。這取代 Spec 015 的全員可見規則。匯出與下載不等於修改原電子簽，同部門可執行，但不得改變簽署設定或證據。
- **FR-011**: 既有簽署人資格、跨部門本人任務、外部邀請、本人副本與公開驗證不因本次列表變更而失效或擴權。
- **FR-012**: 切換前須盤點員工部門完整度及舊文件歸屬；本輪僅規劃，不執行 UAT 回填或刪除。

### Key Entities

- **員工目前部門**：可信來源同步的部門代碼與名稱；反映最近一次成功同步的組織歸屬。
- **文件建立部門快照**：文件建立時固定的部門代碼與名稱，不依建立人目前部門動態改變。
- **部門列表可見範圍**：員工目前部門與文件快照代碼相同且文件未刪除的集合。
- **歷史待歸屬文件**：建立於此功能前、無可靠部門快照的文件；需明確遷移決策。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 以兩部門、每部門至少兩位建立人及六種文件狀態驗收，同部門可見文件命中率 100%，無關其他部門文件出現數為 0。
- **SC-002**: 新建成功的文件 100% 具非空建立部門代碼；員工調職後既有文件歸屬變動數為 0。
- **SC-003**: 部門缺漏、偽造部門及全公司查詢等負向案例中，未授權資料揭露數為 0。
- **SC-004**: 建立人／文件名稱搜尋、狀態與日期區間的既有操作全部通過，清除篩選後恢復部門完整列表。
- **SC-005**: 切換前 100% 舊文件被盤點為可確認歸屬或待處理；既有簽署證據與完成副本被修改數為 0。

## Assumptions

- 「同部門」指單一上游部門代碼相同，不自動包含上下層、同品牌、兼任或代理。
- 文件依建立時部門歸屬；建立人調職後仍保有既有建立人權限，但部門列表顯示其新部門。舊文件可由本人範圍存取，不代表新部門其他員工可見。
- 目前部門指最近一次可信登入同步的資料，不承諾人資異動即時生效。登入同步成功後，既有 session 的後續部門查詢須使用更新後員工資料；不新增排程。
- 部門代碼是授權必要資料；名稱缺漏可顯示未提供，不因名稱缺漏改用別的部門。
- 本 spec 取代本次討論中曾試作、現已撤回的「列表顯示全公司」方案；Spec 015 的全員匯出規則由 FR-010 取代，改為同部門。
- 本次僅產出規格與影響盤點，沒有執行 migration、回填或部署；依使用者要求，先前 `role=all` 的程式、測試及 Spec 003 對應修改已撤回，目前列表仍是原有 `role=created` 行為。
- API 與 DB 欄位盤點見 [impact-analysis.md](impact-analysis.md)，屬實作規劃輸入，不代表已交付。
