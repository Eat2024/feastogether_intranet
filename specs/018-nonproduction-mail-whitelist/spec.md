# Feature Specification: 非 production 寄信收件人白名單

**Feature Branch**: `docs/spec-018-mail-whitelist`

**Created**: 2026-11-02

**Status**: Implemented — 非 production 白名單已改為批次信箱比對，取消逐人資格查詢；本輪驗證結果見 quickstart.md，未部署

**Input**: UAT 不得寄信給所有人；以白名單資料表管理允許部門及額外員工，寄件前檢查環境。使用者確認除 production 外的環境均檢查白名單；初始允許系統開發部、系統開發二部、資訊安全部與員編 09005001，其餘日後增補。原規劃輪僅建立規格；後續依使用者授權實作，環境資料維護仍須依受控程序執行。

## Clarifications

### Session 2026-11-02

- 白名單由資料表管理，增刪後後續寄件無須重啟或重新部署。
- 僅 `NODE_ENV=production` 不檢查白名單；development、test、staging 皆檢查，未設定或不合法不得放行。
- Portal 組織樹唯讀查詢確認：`1029030000` 是 IT策略本部系統開發部，沒有下層部門；上層 IT策略本部代碼為 `1029000000`。
- 使用者追加允許系統開發二部及資訊安全部；最後名單為三個精確部門代碼及一個額外員編，不包含整個 IT策略本部。

### Session 2026-11-02：簡化測試環境寄送檢查

- 使用者要求非 production 的寄信檢查只依白名單規則與可信信箱集合判定，取消逐人查詢在職資格及再次查詢目前部門。此修訂適用 development、test、staging，不限於 NODE_ENV=test。
- 部門規則以本次組織樹精確節點的直接員工為準；額外員編規則由維運明確維護，兩者聯集後批次取得可信信箱，實際地址命中集合才可寄送。
- 不再額外保證離職／停用員工會被寄信政策排除，也不以另一個員工查詢覆核組織樹的新鮮度；相關規則與上游名單的維護由其管理方負責。
- 先前逐人資格查詢是技術方案，現已撤回；登入、簽署權限與既有業務資格驗證不受本次簡化影響。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 非正式環境只寄給允許收件人 (Priority: P1)

測試人員在 UAT 或本機操作電子簽時，通知只寄給白名單內員工，其他員工與未獲允許的外部信箱不收到測試郵件。

**Why this priority**: 避免測試通知、催簽或驗證碼誤寄給實際同仁及外部人員。

**Independent Test**: 在非 production 的合成資料中建立允許部門員工、額外允許員工、非允許員工與無法辨識信箱，逐一發起邀請、催簽及驗證碼寄送，檢查實際傳輸收件人。

**Acceptance Scenarios**:

1. **Given** 非 production，收件人員編出現在本次組織樹的白名單部門直接員工中，且實際地址命中該員編的可信信箱，**When** 寄送，**Then** 可以進入正常寄信流程。
2. **Given** 員工不屬於允許部門，但完整員編命中白名單，**When** 寄送，**Then** 可以寄往該員工可信信箱。
3. **Given** 收件人未命中、信箱無法對應可信員工或偽造員編／部門與信箱不一致，**When** 寄送，**Then** 不把任何郵件交付給該地址，不因同公司網域或顯示名稱相同放行。
4. **Given** 白名單空白、資料來源不可用或環境名稱無效，**When** 嘗試寄送，**Then** 不對未核准地址執行實際寄送。
5. **Given** production，**When** 白名單為空或白名單資料來源故障，**Then** 不因這項非正式環境限制阻擋正常寄信；仍保留原有身分、文件、SMTP 與寄送規則。

6. **Given** 員編符合部門或額外員編規則且具有可信信箱，**When** 寄送，**Then** 不逐人查詢在職狀態或再次查詢目前部門，直接按允許信箱集合判定；員工資格 API 不可用不影響這項政策。
7. **Given** 具有部門規則且候選員編去重後共 300 人，本次收件人為其中 50 人，**When** 來源查詢成功，**Then** 白名單政策只查一次組織樹與三批信箱，不新增 50 次逐人資格查詢。

### User Story 2 - 隨時調整白名單 (Priority: P1)

維運人員能在資料表增補允許部門或員編，也能撤銷；已排程但未送出的通知使用寄送時最新規則。

**Why this priority**: 使用者需要隨時追加測試同仁，不應每次都改程式或重啟 worker。

**Independent Test**: 先對未命中員工嘗試寄信，再新增有效員編規則重新觸發；移除後再觸發，三次結果依序為阻擋、允許、阻擋。

**Acceptance Scenarios**:

1. **Given** 初始種子資料已建立，**When** 查核有效規則，**Then** 正好包含以下四項，而非整個本部。

   | 類型 | 值 | 說明 |
   |---|---|---|
   | 部門 | `1029030000` | IT策略本部系統開發部 |
   | 部門 | `1029090000` | IT策略本部系統開發二部 |
   | 部門 | `1029010000` | IT策略本部資訊安全部 |
   | 員工 | `09005001` | 額外允許同仁，完整字串比對 |

2. **Given** 規則已新增或撤銷並提交，**When** 下一次寄送檢查開始，**Then** 不需重啟服務就使用新規則。
3. **Given** 通知在撤銷前已排入佇列但尚未寄送檢查，**When** worker 取出工作，**Then** 使用撤銷後規則阻擋；不能只沿用發起時判斷。
4. **Given** 同類型相同值已存在或已軟刪除，**When** 再加入，**Then** 不產生重複有效規則；已撤銷規則可被明確恢復。
5. **Given** 一次工作已被白名單阻擋，**When** 之後新增規則，**Then** 不自動補寄該工作，使用者需依既有流程明確重新觸發。

### User Story 3 - 混合群發與結果可信 (Priority: P1)

群發的收件人混有允許與不允許者時，只有符合規則者收到信；畫面與紀錄能區分白名單阻擋、系統檢查失敗與實際投遞結果。

**Why this priority**: 現有內部通知使用群發，若只檢查整批或把跳過當成功，就無法保證收件人範圍與操作人認知一致。

**Independent Test**: 一批含允許及不允許地址，攔截實際寄件 envelope，核對逐人結果；再模擬全數不允許與白名單查詢故障。

**Acceptance Scenarios**:

1. **Given** 群發混合收件人，**When** 寄送，**Then** SMTP 的 To／CC／BCC／envelope 均不包含被阻擋地址，各收件人的結果與原因正確對應。
2. **Given** 群發無人符合，**When** 處理工作，**Then** 不呼叫實際傳輸，全部記為白名單阻擋，不能記為 delivered／accepted 或 unknown。
3. **Given** 明確未命中規則，**When** 完成通知處理，**Then** 記為已跳過且具有穩定原因，不作自動重試，不卡在 pending／processing。
4. **Given** 查詢白名單或可信員工來源失敗，**When** 檢查寄送資格，**Then** 不寄出並記錄可診斷的系統失敗，不冒充未命中、已成功或 SMTP 不明結果；重試僅適用確定尚未寄送的工作，白名單檢查失敗最多 3 次 attempt（含首次），沿既有工作與退避機制處理。
5. **Given** 部分收件人已交 SMTP 且結果不明，**When** 完成批次，**Then** 保留既有 unknown／防重寄規則，不因白名單更新而重送可能已寄出的部分。

### User Story 4 - 驗證碼寄送也受保護 (Priority: P2)

外部邀請的驗證碼不能繞過限制；使用者不應被告知已寄出實際未送出的驗證碼。

**Why this priority**: OTP 在 HTTP 流程寄送，不只 worker 會發信；只限制背景通知仍可能誤寄。

**Independent Test**: 以允許員工的可信信箱建立外部簽署測試，再以非允許信箱測試 OTP；觀察傳輸、回應、驗證碼有效性與稽核事件。

**Acceptance Scenarios**:

1. **Given** 外部簽署 Email 精確對應允許員工的可信信箱，**When** 請求 OTP，**Then** 可沿原限制寄出並繼續驗證；不要求該簽署人已建立本系統 User。
2. **Given** 信箱不在允許員工集合，**When** 請求 OTP，**Then** 不寄出、不回報已寄送、不新增成功寄送稽核，也不能留下可用的本次新驗證碼。
3. **Given** 驗證碼被阻擋或來源故障，**When** 重試，**Then** 維持原防濫用規則；回應不揭露完整白名單或員工／部門名單。

### Edge Cases

- 員編與部門代碼皆為字串，`09005001` 不得轉數值遺失前導零。
- 部門按完整代碼相等，不按前綴、同名、上層或「IT」字樣擴張；不自動加入新子部門。
- 僅缺部門但有可信完整員編與信箱、且員編在白名單時仍可命中員工規則；沒有任何可信身分證據則阻擋。
- 本寄信政策不額外查詢停用／離職狀態。額外員編仍在有效規則內且能取得可信信箱時即可命中；需要停止寄送時由維運撤銷規則或由上游移除相關名單／信箱。
- 發起人被允許不代表所有簽署人可收信；白名單針對實際收件人，不針對寄件人或文件建立部門。
- 群發重複信箱依既有正規化規則去重；多個白名單候選員編對應同一可信信箱也只保留一個地址，不視為檢查失敗。不因名字或欄位注入加入額外 envelope 地址。
- 規則讀取至 SMTP 呼叫之間存在短暫競態，撤銷適用於提交後開始的下一次檢查；已交付 SMTP 的郵件無法追回。
- 非 production 的 fake sender 仍須能驗證相同白名單規則與結果，不把 fake 成功當成真實郵件送達；測試不得為方便把環境改成 production 繞過政策。
- 正式環境只跳過此白名單，不跳過既有收件人資格、憑證、檔案狀態、TLS 與 SMTP 認證。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 唯一免檢查環境為精確合法值 production；development、test、staging 的所有系統寄信都要先驗證白名單。未設定／未知環境不得被視為 production，沿既有環境驗證拒絕啟動或拒絕寄送。
- **FR-002**: 以持久資料表維護部門與員工兩類規則，值為字串，支援追加、撤銷與明確恢復；同類型同值不得存在重複有效規則。
- **FR-003**: 初始四項規則為部門 1029030000、1029090000、1029010000 及員編 09005001；不擴張上層或子部門，其他收件人需明確增補。
- **FR-004**: 非 production 寄送前，從本次組織樹取得精確白名單部門的直接員工，與有效員編規則聯集去重，再批次取得可信信箱；實際地址命中該信箱集合才允許。不得為白名單逐人查詢在職資格或再次核對目前部門，也不得信任前端參數、顯示名稱、網域或寄件人資格。
- **FR-005**: 共同寄送邊界須涵蓋邀請、催簽、內部群發與 OTP，HTTP server 與 worker 採相同政策，無直接 SMTP 旁路。
- **FR-006**: 每次寄送檢查讀取最新已提交的有效規則，不跨寄送快取白名單；隊列重試也重新檢查，不依排程當下判斷。
- **FR-007**: 群發逐地址過濾，僅允許地址可進實際 SMTP envelope；無允許者時不執行傳輸。允許者沿用既有 accepted／rejected／unknown 判定。
- **FR-008**: 明確不允許為白名單跳過，不冒充寄送成功或不明投遞；有可追蹤的穩定原因、不作自動重試。新增規則後不自動補寄先前跳過工作。
- **FR-009**: 白名單 DB 或可信員工來源無法確認時不寄出，以系統檢查失敗處理；確定尚未寄送才可最多嘗試 3 次（含首次），不用空白名單／production fallback 掩蓋錯誤。
- **FR-010**: OTP 被阻擋不能顯示已寄送、不能寫成功寄送稽核、不能留下可使用的本次新 OTP；保留既有節流、有效期限與驗證次數限制。
- **FR-011**: 白名單阻擋及檢查失敗需可在現有通知結果／運維資訊辨識，錯誤、log 不含完整白名單、API key、OTP、邀請 token 或不必要的個資。
- **FR-012**: production 不因白名單表內容或這項檢查故障影響既有寄信；測試須證明不執行僅為白名單而新增的 DB／HR 查詢。
- **FR-013**: 本功能不修改電子簽瀏覽／簽署權限，也不更改收件地址轉寄至測試信箱；通知阻擋不刪除簽署人或變更其簽署資格。
- **FR-014**: 建立表與初始資料須有 migration／回滾設計、欄位驗證及可審查的維護程序；本次不新增管理頁、公開維護 API、排程或環境開關。

### Key Entities

- **收件人白名單規則**：類型（部門或員工）、完整字串值、備註、建立／修改／撤銷時間。
- **白名單候選員工**：本次組織樹白名單部門的直接員工及額外允許員編；以完整字串去重，不額外查詢在職資格，不要求已登入本系統。
- **允許收件信箱集合**：由候選員編批次查得的可信有效信箱，實際地址須命中此集合。
- **寄送資格判定**：允許、白名單阻擋、檢查失敗；與 SMTP 投遞結果分開。
- **通知結果**：每一地址的跳過／投遞／失敗狀態，能保持現有批次與重試一致性。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在 development、test、staging 的全部寄信種類中，未允許實際收件人數為 0。
- **SC-002**: 四項初始規則及追加／撤銷的正負向案例 100% 符合預期，正式環境的原寄送案例全部保持原行為。
- **SC-003**: 白名單異動提交後，下一次開始的寄送檢查 100% 採用新規則，部署與重啟次數為 0。
- **SC-004**: 混合群發的傳輸收件人集合與允許集合完全一致，全部被阻擋時實際寄送呼叫數為 0。
- **SC-005**: 被阻擋通知誤標成功數、被阻擋 OTP 可驗證成功數、自動補寄已跳過工作數皆為 0。
- **SC-006**: DB／HR 查詢失敗時未經確認的郵件實際寄送數為 0，錯誤可與明確未命中區分。

- **SC-007**: 白名單政策的逐人員工資格／部門查詢數為 0；成功完成一次檢查時，組織樹至多查一次，可信信箱依候選員編批次查詢，不因本次匹配收件人數增加逐人請求。

## Assumptions

- 環境沿用部署端 NODE_ENV，不由請求或客戶端選擇；production 的設定正確性屬既有部署責任，不能以其他名稱模糊比對。
- 規則存於各環境自己的 DB，不新增 environment 欄位；非 production 對該環境有效資料表檢查，production 忽略此限制。
- 此功能可獨立於 Spec 017 實作，不能假設該 PR 已合併或已有 users.departmentCode；可信 HR 來源如何形成允許信箱集合在 plan 定義。
- 初始只提供部門與員編兩種規則；不是員工可信信箱的外部個人信箱預設無法通過，不新增 email 白名單型別或測試轉寄規則。
- 初期由受控 DB 維護程序增刪規則，管理 UI／API 不在本次範圍。
- 部門歸屬以寄送檢查時取得的組織樹為準，不讀文件快照或本機 User 判斷，也不另外逐人確認組織樹是否延遲。額外員編規則不受其部門影響。
- 本輪已移除寄信專用逐人資格查詢並同步測試；修訂前與本次驗證結果分別記錄於 quickstart.md。未修改 UAT／production 資料或部署。

## 已確認資料維護約束

使用者確認採 `mail_recipient_whitelist`，欄位為 `id`、`type`、`value`、`remark`、`created_at`、`updated_at`、`deleted_at`。`(type, value)` 唯一，撤銷採軟刪除、恢復原列；不新增 is_active、environment、Email 或操作人欄位。資料型別與 migration 見 [data-model.md](data-model.md)。

## 關聯規格

- Spec 009／010／012：通知、群發、重試與投遞結果需保持原語意，增加跳過原因。
- Spec 008：OTP 寄送失敗與成功稽核不得被白名單跳過破壞。
- Spec 017／PR #37：文件部門可見與本收件人政策是不同責任，本 spec 不修改其權限規則。
