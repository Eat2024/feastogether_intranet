# Feature Specification: 非 production 白名單開放指定收件信箱

> 2026-11-03：員工名單解析、發起信箱與員編／直接部門白名單的即時人資來源，由 [Spec 023](../023-portal-user-email/spec.md) 改為 Portal 匯入的本機 users。部門樹及登入來源不變；缺信箱可簽署、文件固定收件信箱、完整 Email 規則與正式環境 bypass 語意不變。以下歷史設計及驗證紀錄保留，來源切換的驗收以 023 為準。

**Feature Branch**: `docs/spec-021-external-mail-whitelist`

**Created**: 2026-11-03

**Status**: Implemented（未部署）— Ticket 01、02 與 code review 修正已實作並通過 server 驗證；尚未在任何環境套用 migration 或寫入信箱規則

**Input**: 非 production 寄信須通過 Spec 018 白名單，但白名單只能列部門與員編，非公司人員的外部簽署人一律被阻擋，無法在 UAT 以真實外部信箱測試外部簽署流程。使用者要求提供能讓白名單外、非公司人員也收得到信的白名單做法；確認採「新增收件信箱規則類型」，並要求先撰寫 spec 再實作。

## Clarifications

### Session 2026-11-03

- 新增第三種規則「收件信箱」，以完整地址精確比對；部門、員編、信箱三類規則任一命中即允許。
- 不採以下做法：非員工一律放行（白名單本意即避免測試信寄到真實外部人員，且無法由信箱可靠判斷是否為員工）；網域規則（範圍過大）；環境變數清單（需重啟，Spec 018 已排除）；改寄測試信箱的轉寄規則。
- 以本規格修訂 Spec 018「不新增 email 白名單型別」的假設；018 其餘政策（環境判定、群發、worker 結果、OTP 行為）不變。
- 沿用 `mail_recipient_whitelist` 表，不新增資料表或欄位；初始資料不加入任何信箱規則，實際測試信箱由受控維護程序寫入各環境 DB，不提交至 repo。
- 公司同仁一律使用部門或員編規則，信箱規則只用於外部測試信箱；維護人只有使用者本人，系統不另外阻擋公司網域。
- 規則值欄位放寬為 255 字元，以容納完整收件地址。
- 外部簽署人的邀請、催簽與 OTP 都是單一收件人寄送，群發只用於內部同仁；因此外部信箱不會與須查人資來源的收件人混在同一次寄送，不另訂混合情境規則。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 以指定外部信箱測試外部簽署 (Priority: P1)

測試人員在 UAT 以團隊可控的外部信箱（例如測試用個人信箱）擔任外部簽署人，邀請、催簽與驗證碼都能寄達，完成外部簽署流程測試。

**Why this priority**: 現況外部信箱一律被阻擋，只能借用白名單同仁的公司信箱扮演外部簽署人，無法驗證真實外部收件情境。

**Independent Test**: 在非 production 的合成資料新增一筆信箱規則，以該信箱建立外部簽署人，觸發邀請、催簽與 OTP；再以未列入的信箱重複一次，比對實際傳輸收件人。

**Acceptance Scenarios**:

1. **Given** 非 production，外部簽署 Email 命中有效信箱規則，**When** 寄送邀請、催簽或 OTP，**Then** 進入正常寄信流程，OTP 可依原規則驗證。
2. **Given** 收件地址命中信箱規則，**When** 檢查寄送資格，**Then** 不查詢組織樹或員工信箱來源；人資來源暫時不可用也不影響寄送。
3. **Given** production，**When** 寄送，**Then** 行為與現行相同，不讀取信箱規則。

### User Story 2 - 只放行明確列入的地址 (Priority: P1)

開放外部信箱不能讓白名單範圍悄悄擴大；只有逐一列入的完整地址可收信。

**Why this priority**: 白名單的目的是避免測試郵件寄到真實同仁與外部人員；若信箱規則可模糊比對，誤寄風險反而高於現況。

**Independent Test**: 列入一個信箱後，以同網域其他地址、plus alias、子網域、只差一字元的地址，以及大小寫不同的同一地址寄送，核對結果。

**Acceptance Scenarios**:

1. **Given** 已列入 `tester@example.com`，**When** 寄給 `other@example.com`、`tester+uat@example.com`、`tester@sub.example.com` 或 `tester1@example.com`，**Then** 均為 blocked。
2. **Given** 已列入的地址，**When** 收件地址只有大小寫或前後空白不同，**Then** 依既有收件地址正規化視為同一地址並允許。
3. **Given** 部門、員編與信箱規則皆未命中，**When** 寄送，**Then** blocked，不因網域、顯示名稱、文件建立人或寄件人資格放行。

### User Story 3 - 維護信箱規則 (Priority: P2)

維運人員以與部門、員編規則相同的受控程序新增、撤銷、恢復信箱規則，提交後即生效。

**Why this priority**: 外部測試信箱會隨測試案例增減，需與既有規則一樣不重啟即可調整。

**Independent Test**: 對未列入信箱寄送，新增信箱規則後重新觸發，撤銷後再觸發，三次結果依序為阻擋、允許、阻擋；另嘗試寫入格式錯誤的值。

**Acceptance Scenarios**:

1. **Given** 新增或撤銷信箱規則並提交，**When** 下一次寄送檢查開始，**Then** 採用新規則，不需重啟或重新部署。
2. **Given** 規則值含大寫、空白或控制字元、不是恰好一個 `@`、`@` 前後為空，或超過 255 字元，**When** 寫入，**Then** 資料庫拒絕上述格式錯誤的值。DB 不做完整信箱格式驗證，規則值須為寄送端可接受的地址，否則永遠不會命中。
3. **Given** 同一信箱規則已存在或已撤銷，**When** 再次新增，**Then** 不產生重複規則；已撤銷者可明確恢復原列。
4. **Given** 先前因未列入而 skipped 的通知，**When** 之後新增該信箱規則，**Then** 不自動補寄，沿 Spec 018 由使用者重新觸發。

### Edge Cases

- 信箱規則是固定地址，不跟隨人員異動；公司同仁一律走部門或員編規則，不列入信箱規則。
- 信箱規則與收件地址使用同一正規化（去除前後空白、轉小寫）；不解析顯示名稱、不展開 plus alias、不做國際化網域轉換或忽略點號。
- 信箱規則值屬個資：錯誤、log、OTP 阻擋頁不輸出規則內容；repo、seed 與測試 fixture 只使用合成地址（如 `example.com`）。
- 群發輸入的地址全部不是合法單一信箱時，白名單檢查收到空清單，不查人資即全數 blocked，與單封寄送不合法地址直接 blocked 一致；規則表讀取失敗時仍為 check-failed。此為 Spec 021 後的行為，取代先前可能因人資故障記為 check-failed 的結果。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 白名單 MUST 新增「收件信箱」規則類型，值為正規化後的完整收件地址；部門、員編、信箱三類規則任一命中即允許寄送。（US1-1/2）
- **FR-002**: 信箱規則 MUST 以完整地址精確比對，收件地址比對前沿用既有正規化；不支援網域、萬用字元、前綴或 plus alias 展開。（US2）
- **FR-003**: 本次收件人全部命中信箱規則時，白名單檢查 MUST NOT 查詢組織樹或員工信箱；其餘情況沿用 Spec 018 解析部門／員編規則。（US1-2）
- **FR-004**: 信箱規則 MUST 在 Spec 018 的共用寄送邊界判定，HTTP server 與 worker 相同，涵蓋外部簽署的邀請、催簽與 OTP；blocked／check-failed 結果分類、重試與 OTP 行為不變。（US1-1）
- **FR-005**: 資料庫 MUST 拒絕非正規化或格式錯誤的信箱規則值（含大寫、空白或控制字元、非恰好一個 `@`、`@` 前後為空、超過寄送端收件地址上限 255 字元）；部門與員編規則的既有格式限制不變。（US3-2）
- **FR-006**: 信箱規則 MUST 沿用既有新增、撤銷、明確恢復與 `(type, value)` 唯一性規則，提交後下一次檢查生效；不新增管理頁、API、環境變數、排程或快取。（US3-1/3/4）
- **FR-007**: 初始資料 MUST NOT 加入任何信箱規則；實際外部測試信箱只經受控維護程序寫入各環境 DB，不提交至 repo。
- **FR-008**: production MUST 維持不讀取白名單，不受信箱規則影響。（US1-3）
- **FR-009**: 錯誤、log 與 OTP 阻擋頁 MUST NOT 輸出信箱規則內容或完整白名單。（Edge Cases）
- **FR-010**: 資料遷移 MUST 保留既有部門／員編規則與其 id；回滾程序須明確處理已存在的信箱規則，不可靜默刪除維護資料。

### Key Entities

- **收件人白名單規則**：類型新增「信箱」；值依類型為完整部門代碼、完整員編或正規化後的完整收件地址。
- **允許收件信箱集合**：本次收件人中命中信箱規則的地址，與由部門／員編規則解析出的可信信箱取聯集。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 非 production 中，命中信箱規則的外部收件人在邀請、催簽與 OTP 三種寄送 100% 交付寄送 adapter；未列入地址的實際收件數為 0。
- **SC-002**: US2 列出的同網域、plus alias、子網域與相近地址案例 100% blocked。
- **SC-003**: 收件人全部命中信箱規則時，白名單檢查的組織樹與員工信箱查詢次數為 0。
- **SC-004**: 不合法信箱規則值的寫入 100% 被資料庫拒絕；既有四筆初始規則與 Spec 018 原驗收案例維持通過。
- **SC-005**: 新增或撤銷信箱規則後，所需重啟與部署次數為 0。

## Assumptions

- 以信箱規則放行的外部地址由維護人確認為測試人員可控信箱；系統不驗證信箱歸屬。
- 規則值欄位放寬為 255 字元屬既有欄位調整，非新增欄位；具體 migration、CHECK 條件與回滾步驟於 plan／data-model 定義。
- Spec 018 的維護程序（同一交易、`FOR UPDATE` 鎖定、`ROW_COUNT()` 核對）同樣適用信箱規則。
- 本規格僅修改 server；client 沒有畫面變更，OTP 阻擋頁沿用 Spec 018 文案。
- server 已依本規格實作（Ticket 01、02），尚未部署；各環境套用 migration 與寫入實際測試信箱屬上版維運程序，見 [quickstart](quickstart.md)「環境上版」。

## 對 Spec 018 的修訂

- 018 Assumptions「不新增 email 白名單型別」與 data-model「不存 Email」由本規格取代：新增信箱規則類型，但仍不新增 Email 欄位。
- 018 FR-002 的兩類規則改為三類；FR-004 的允許集合增加信箱規則直接比對，部門／員編解析方式不變。
- 018 US4-2「信箱不在允許員工集合」改讀為「不在允許收件信箱集合（含信箱規則）」。
- 實作時於 018 的 spec、contract 與 maintenance 加註指向本規格，不改寫 018 的歷史驗證紀錄。

## 關聯規格

- Spec 018：本規格擴充其白名單規則類型，其餘寄送政策沿用。
- Spec 008：外部簽署邀請與 OTP 寄送沿用原流程，只改變非 production 的收件資格。
- Spec 009／010／012：群發、催簽與通知結果語意不變。
