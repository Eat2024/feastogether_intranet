# Feature Specification: 全量背景發起簽署

> **最新範圍優先**：本輪只改後端 worker 與文件／簽署人異動保護；前端工作暫緩。原本必填 Idempotency-Key 改選填以相容既有 client。具體覆寫與已知限制見 [後端範圍決策](backend-only-scope.md)。

**Feature Branch**: `feat/022-background-signature-initiation`

**Created**: 2026-11-03

**Status**: 規格、Phase 1 設計與 tasks／本機 tickets 拆解完成 — 尚未實作、功能驗證或部署

**Input**: 使用者於 UAT 選取約 5,000 位簽署人，發起前的名單解析耗時過久，畫面顯示發起失敗；要求「如果簽署人超過 100 人就開 worker 執行，慢慢消化，別讓前端等」，並明確指示先開 spec。2026-11-03 後續確認：「全部都走 worker」，取代原 100 人門檻，並要求繼續 022 規劃。

## 背景與範圍

> **2026-11-03 來源決策更新（Spec 023）**：使用者確認只有選人部門樹保留饗賓人 API；員工基本資料及 Email 從 Portal 匯入，本規格的背景解析、資格／信箱查核與寄信白名單一律讀本機。背景工作不再即時向人資匯入缺少的帳號；缺資料時提示先同步。詳見 [Spec 023](../023-portal-user-email/spec.md)。

- 現場證據顯示一批名單解析耗時約 110 秒，後端記錄成功，但前端代理記錄連線中斷。這確認使用者等待同步處理時可能先收到失敗；尚未證實是哪一層的逾時設定觸發中斷。
- 目前名單解析、員工信箱查詢與正式發起分屬不同階段。只把名單解析移至背景，不能保證後續發起不再遇到長時間等待。
- 本規格採已確認的完整背景發起：建立人一次確認提交後，名單解析、發起前驗證與正式發起由系統接續處理，離開頁面仍繼續。這是使用者已確認的範圍，並非已完成的功能。
- 所有有效名單均採背景處理，包含 1 人，不保留同步發起分支，也不設 100 人門檻。沿用 Spec 003 FR-009／FR-037 的完整名單與全公司五千多人需求，不要求拆成多份文件。
- 本次不更改簽署資格、建立人權限、部門可見範圍、共用欄位、簽署證據、寄信白名單或簽署人登入方式。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 所有名單提交後立即取得受理結果 (Priority: P1)

文件建立人選擇至少一位簽署人並確認發起後，立即知道工作已受理。系統在背景逐步完成工作，建立人可以離開頁面，不必等所有人解析完成或保持瀏覽器連線。

**Why this priority**: 解決目前大量選人時長時間等待、代理中斷與誤認發起失敗的實際問題。

**Independent Test**: 使用已從 Portal 匯入的合成員工名單與刻意延遲的本機查核，分別提交 1、100、101、5,001 人；在背景受理後關閉頁面，確認系統仍可完成整份文件發起。

**Acceptance Scenarios**:

1. **Given** 建立人具有效登入狀態且草稿設定完整，**When** 提交 1 或 101 位有效簽署人，**Then** 很快取得可追蹤的受理結果，畫面顯示排隊／處理中，不顯示已成功發起。
2. **Given** 5,001 位簽署人需花較長時間解析，**When** 建立人在受理後關閉頁面，**Then** 工作繼續，全部通過後自動發起，不需瀏覽器再次觸發正式發起。
3. **Given** 同一員工出現在多個勾選來源，**When** 提交完整名單，**Then** 依既有選人去重規則計算實際簽署人數，不因重複展開而建立重複指派；非法重複身分仍沿用既有拒絕規則。
4. **Given** 名單為 100 人且所有資料有效，**When** 發起，**Then** 與 1、101、5,001 人相同，回報已受理並由背景完成；原本發起驗證不得略過。
5. **Given** 背景工作無法可靠受理，**When** 建立人提交，**Then** 明確回報尚未受理並保留輸入，不假裝排隊成功，也不悄悄改成長時間同步處理。

### User Story 2 - 回到文件即可追蹤進度與結果 (Priority: P1)

建立人可在文件列表辨認背景發起中的文件，進入文件後查看目前階段、已處理與總人數、成功或失敗原因。重新登入或重整後仍能找到原工作。

**Why this priority**: 沒有可恢復的進度入口，使用者仍會重複提交，或誤以為工作遺失。

**Independent Test**: 在工作等待、處理與完成時重整頁面、重新登入，確認同一建立人能讀到一致的最新結果，其他使用者不能取得工作中的個資與控制權。

**Acceptance Scenarios**:

1. **Given** 工作已受理，**When** 建立人重整或從列表重開文件，**Then** 可看到同一工作的狀態、目前階段、已處理及總人數，不另建工作。
2. **Given** 名單解析已完成但正式發起尚未完成，**When** 查看進度，**Then** 顯示仍在準備發起，不以解析完成冒充文件已發起。
3. **Given** 文件正式發起成功但通知被白名單跳過，**When** 查看結果，**Then** 文件顯示發起成功，寄送狀況沿既有通知紀錄呈現，不顯示整份發起失敗。
4. **Given** 不是工作建立人的員工知道工作識別，**When** 嘗試查看工作明細或重試，**Then** 被拒絕；原本的部門文件唯讀範圍不因此擴大。

### User Story 3 - 失敗後可修正或安全重試 (Priority: P1)

背景處理遇到人員資格、來源服務或文件狀態問題時，建立人能知道應修正什麼，並從原文件安全重試；不會因重試形成重複發起或重複初邀。

**Why this priority**: 長時間工作必須能面對中斷與重放，避免讓大量文件或簽署人落在不一致狀態。

**Independent Test**: 注入人員查核失敗、工作中斷及發起成功後結果尚未回報的情境，重新處理並核對文件發起事件、名單與初邀批次數。

**Acceptance Scenarios**:

1. **Given** 名單中有人資格不符，**When** 背景查核完成，**Then** 整份文件不發起、不寄初邀，建立人可辨認需修正的人員；不得靜默略過後發起剩餘名單。
2. **Given** 本機人員資料查詢暫時失敗，**When** 工作無法繼續，**Then** 顯示可重試的失敗原因，保留已確認的工作紀錄；重試仍重新確認必要的權限、資格與文件狀態。
3. **Given** 處理程序中斷後恢復，**When** 原工作繼續處理，**Then** 不建立重複帳號、重複簽署指派或第二次發起；既有員工主檔不要求人工刪除後重來。
4. **Given** 已完成正式發起，但回報工作結果前中斷，**When** 系統恢復或建立人重試，**Then** 辨認既有成功結果，不再次發起或重建初邀批次。
5. **Given** 相同文件正有工作處理中，**When** 重複點擊、另一分頁再次送出或嘗試修改／刪除草稿，**Then** 回到原工作或顯示衝突，不並行發起或改變已受理內容。
6. **Given** 處理期間建立人被停用、文件不再可發起或簽署截止時間已過，**When** 即將正式發起，**Then** 工作失敗並說明原因，不沿用過期授權、不自行延長期間。

### Edge Cases

- 0 人沿用既有驗證失敗；1／100／101／5,001 人、混合名單及全外部名單均走背景，不因人數或輸入格式切回同步。
- 即使只有一位簽署人且帳號已存在，仍走背景受理，處理時間可以較短，不改變契約。
- 現有程式存在個別查核的批次／數量限制；本次不能將其當作文件總人數上限，完整名單不得截斷。
- 部分員工沒有信箱：沿用 Spec 016，仍可指派及發起，通知記錄缺少收件信箱，不因此剔除員工或使整份發起失敗。
- 受理結果在網路中遺失：重新進入文件能找回原工作，重新提交不建立第二個同時執行的工作。
- 受理後瀏覽器斷線、登出或登入逾期：已受理工作繼續；再次查詢須重新登入，正式發起前仍查核建立人目前有效資格。
- 工作等待時尚未進行人員查核：顯示排隊，不顯示不存在的完成百分比；長時間處理不偽造成功。
- 改正失敗工作的名單後重新提交：新嘗試使用新確認內容，舊工作不能稍後恢復並覆蓋新結果。
- 草稿原檔、簽署欄位、期間或選項在背景處理中出現不一致：整份發起停止，不能混用不同版本。
- 背景初邀遇到拒收、結果未知或白名單阻擋：沿用既有寄送及重試規則，不以工作恢復為理由自動重複投遞。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 所有有效發起 MUST 由背景工作完成，不保留依人數切換的同步分支。實際總人數由服務端依既有身分正規化與重複驗證規則計算，不信任前端提供的計數。
- **FR-002**: 背景受理 MUST 不等待全體員工逐人查核、信箱查詢或完整發起完成；只有工作與必要輸入已可靠保存且可供背景執行時，才能回報已受理。
- **FR-003**: 背景工作 MUST 涵蓋本機名單解析、員工身分及信箱核對、文件／欄位／期間驗證，以及原本完整的正式發起。前端不得先同步解析全部人員才提交背景工作。
- **FR-004**: 建立人 MUST 能在受理後離開頁面；工作不依賴瀏覽器持續開啟或額外確認才進入正式發起。受理與完成為不同結果，畫面不得混淆。
- **FR-005**: 同一文件 MUST 同時最多有一個未結束的背景發起工作。重複提交、重放與恢復 MUST 不造成第二次正式發起、重複指派或重複初邀批次。
- **FR-006**: 系統 MUST 保存本次確認的完整名單、欄位、期間、選項及所依據的文件內容識別；工作進行中禁止修改／刪除該草稿或再次直接發起，且服務端必須執行限制。失敗後才允許建立人修正並重新提交。
- **FR-007**: 背景發起 MUST 沿用全有或全無的文件業務結果：全部必要驗證通過後才正式發起；任何必要人員不合格不得局部發起。工作不建立員工帳號，既有主檔不因工作失敗被刪除。
- **FR-008**: 受理與正式發起前 MUST 分別確認文件建立人權限、帳號有效性與文件仍可發起；工作進度／失敗人員明細及重試只向該建立人提供。背景處理不得靠保存瀏覽器登入憑證延續權限。
- **FR-009**: 建立人 MUST 能從文件列表辨識背景工作，並在文件入口查詢等待、處理、成功或失敗狀態、目前階段、總人數、已處理人數及最後進度時間；重整、換裝置或重新登入後仍可查回未結束工作及最近結果。
- **FR-010**: 人數進度 MUST 對應明確階段，處理數不得超過總數、重試不得重複累加；只有正式發起成功才顯示完成。恢復後需要重新驗證時，須標明新嘗試或重新查核階段，不偽裝成未中斷進度。
- **FR-011**: 失敗結果 MUST 區分可重試的暫時問題與需修改名單／文件的問題，以繁體中文提供下一步。人員問題只提供建立人辨識所需的最少資料，不輸出人資原始回應、完整組織資料或憑證。
- **FR-012**: 系統 MUST 能處理背景程序重啟、工作重送及成功結果回報前中斷；恢復時以已成立的文件結果為準。前次已完成的查核可供追蹤，但不略過必要的最新本機資格及文件檢查。
- **FR-013**: 背景作業 MUST 有受控的處理量，不得一次對全體簽署人同時啟動無限制本機查核／寫入；實際分批、並行量與暫時失敗重試界線於 plan 定義並驗證。持續失敗必須有可辨識的失敗結果，不永久無限重試。
- **FR-014**: 缺少員工信箱、白名單不允許或後續郵件投遞失敗 MUST 沿用既有規格處理，不改變員工簽署資格，亦不將已成立的發起回報為失敗。工作完成不代表全部通知已送達。
- **FR-015**: 背景發起 MUST 保留原發起者、單一文件與完整簽署名單、原有簽署參數快照及稽核關聯；不得要求拆文件或以名單頁數、批次大小、共用欄位數間接限制總人數。
- **FR-016**: 工作受理、處理失敗、重試與完成 MUST 可由授權維運人員依工作／文件識別及時間追查；紀錄只包含必要進度、分類錯誤與關聯資訊，不寫入完整名單、信箱、登入憑證或簽署內容。

- **FR-017**: 少量文件與大量工作同時排隊時 MUST 有可追蹤的狀態及有限的恢復界線；不得依人數優先插隊而使已受理工作永久飢餓。
- **FR-018**: 建立人 MUST 能於保留期間取回失敗工作的確認名單與設定以修正；來源組織樹改變不得使已提交名單無聲遺失。工作摘要與完整輸入／人員問題明細須分離讀取。

### Key Entities *(include if feature involves data)*

- **背景發起工作**：由文件建立人提交，關聯一份草稿與一次確認的輸入；具有工作識別、目前階段、狀態、總人數、處理數、時間、嘗試與最終結果。plan 採一張專用持久工作表承載，與正式文件及簽署證據分離。
- **發起輸入快照**：本次建立人確認的完整簽署名單、共用欄位、簽署期間、選項與文件內容識別；與既有正式發起後不可變的簽署證據快照分開。
- **人員查核結果**：每位選定簽署人的身分解析結果與必要失敗分類，用於確認完整名單；不得直接授予文件存取權限。
- **文件發起結果**：沿用既有文件狀態、指派與稽核證據，是背景工作宣告成功的依據；通知投遞有各自結果。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在正常 UAT 連線且受理服務可用的條件下，1、100、101 與 5,001 人的合成名單各提交至少 20 次，95% 的提交於 3 秒內顯示受理結果；人員查核刻意延遲時亦不延後受理。這是驗收目標，不代表已量測通過。
- **SC-002**: 1／100／101／5,001／6,001 人、混合內外部名單及重複選取情境，處理方式與有效人數判斷 100% 符合 FR-001；5,001 人成功案例的指派數與確認名單完全一致，沒有截斷或拆分文件。
- **SC-003**: 受理後關頁、重整及重新登入三種情境，均能查回同一工作，且不影響最終發起；正常連線下，已產生的最新進度或結果於 10 秒內可在畫面看到。
- **SC-004**: 重複點擊、兩分頁同送、處理程序中斷及發起完成後回報中斷等案例，成功發起事件與有效初邀批次皆不重複，沒有重複簽署指派。
- **SC-005**: 不合格人員、文件內容衝突、建立人被停用及截止時間已過的案例，100% 不產生部分發起；建立人可取得可理解的失敗原因與處理方式。
- **SC-006**: 5,001 位合成人員且每位首次查核延遲 1 秒的驗收中，受理後 120 分鐘內可完成背景發起，全程不需建立人再次點擊；本機資料查詢持續失敗的案例必須在 plan 定義的有限處理界線內呈現失敗，不能無限顯示處理中。
- **SC-007**: 非建立人查詢工作明細／重試、未登入操作與越權修改草稿等負向案例全部被拒絕；缺信箱及白名單跳過案例仍可成立正確指派，不被錯報為發起失敗。

- **SC-008**: 在受控單一 worker 環境先提交一份 5,001 人工作，再提交 5 人工作；兩份皆於 3 秒目標內受理，顯示正確排隊順序；大型工作成功或有限失敗後，小型工作於 60 秒內取得執行權（不含其他既存佇列），不需再次點擊。記錄實際等待與完成耗時。
- **SC-009**: 失敗後重整並重新登入，建立人可在 30 天輸入保留期間取回完整確認名單修正；非建立人無法讀取，超過保留期明確提示重新設定。

## Assumptions

- **已確認決策（2026-11-03）**：所有發起都走 worker，涵蓋解析至正式發起，不等待建立人再次確認；取代早期只處理超過 100 人的提案。
- 名單包含內部與外部簽署人；來源重複展開沿既有規則去重，輸入違規不能透過去重掩蓋。
- 少量工作仍可能排在大量工作後面；首版需顯示排隊狀態並驗收有限等待，不承諾 worker 化會縮短實際運算時間，也不透過提高代理逾時宣稱完成。
- 沿用現有 worker、MySQL、Redis。使用者已同意續做含專用工作表的方案；plan 設計一張工作表及對應 migration，不新增環境變數、獨立排程或基礎設施。本輪僅寫設計，尚未建立資料表或執行 migration。
- 進度入口沿用文件列表及文件頁，不新增通用工作中心、完成 Email、工作取消、排程發起或管理員代他人發起功能。
- 非終態工作不可因一般結果保留期限而無聲消失；終態工作明細保留期限、復原界線及精確錯誤契約在 plan 定義，正式文件與稽核結果沿用原保留規則。
- 依賴 Spec 023 的 Portal 匯入本機人員資料、文件發起與共用欄位規則（Spec 003／009）、員工通知與本人簽署（Spec 016）、部門可見性（Spec 017）及非正式環境收件人白名單（Spec 018／021）。
