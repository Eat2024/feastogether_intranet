# Feature Specification: Portal 直連取代饗賓人人資查詢

**Feature Branch**: `feat/024-portal-hr-source`（基於 `dev`，已含 Spec 023）

**Created**: 2026-11-03

**Status**: Draft

**Input**: 使用者要求：「我要在這個專案建立 portal 連線方式，估計會放在跟 db 同一層的 infra 資料夾內，然後把三個可以從饗賓人 api 移掉搬到 portal 查詢的功能規劃規格」。三個功能為選人部門樹（`hr/org_chart`）、登入時的員工資料查詢（`hr/staff_lookup`），以及員工信箱來源（`hr/staff_emails`）。後續確認的決策見 Clarifications。

## 背景與已確認範圍

- 2026-11-03 已在 UAT 主機實測：intranet 所在環境可唯讀連線 Portal，並能讀取人員表與部門表。正式環境尚未建置，使用者會要求 SRE 沿用相同架構。
- 饗賓人平台的這三個 API 本身也是讀 Portal：
  - 組織樹即時查 Portal 的部門表與人員表。
  - 員工查詢與信箱讀的是饗賓人每天同步一次的 Portal 人員表副本。
  - 改成直連 Portal 後資料內容相同；員工查詢因此不再落後最多一天。
- 饗賓人的帳密驗證（`staff/login`）用的是饗賓人自己的密碼，Portal 無法提供，不在本規格範圍。未來 intranet 會改由 auth（OAuth）決定登入狀態，該串接也不在本規格範圍。
- Spec 023 已完成：簽署人解析、正式發起與寄信白名單都改讀本機員工主檔，執行期已沒有地方呼叫 `hr/staff_emails`。本規格處理信箱的方式，是把 023 的人工匯入改為 worker 每天自動從 Portal 匯入本機主檔；esign 流程仍讀本機，不改為即時查 Portal。
- 本規格取代以下既有決策：
  - Spec 023 FR-012 中「選人部門樹維持饗賓人 API」。
  - Spec 023 FR-006 與 Assumptions 中「不新增自動排程、人工觸發匯入」與「本批不自動停用」。
  - Spec 023 FR-004、FR-005、FR-014 與 US4 情境 5 中的私有預覽檔、原值檔與回復程序。
  - Spec 023 research §5「不新增 Portal runtime 連線與環境變數」。
  - Spec 023 local-directory 契約中，維護 CLI 以 HEX TSV 檔作為輸入。
  - Spec 006 中以饗賓人 API 作為組織樹上游。
- 使用者初步指定 Portal 連線放在 server 的基礎設施層，與既有資料庫連線同層。部門樹（esign）、登入（auth）、每日匯入（worker）與手動匯入 CLI 共用這個連線，符合憲章 IV「確實跨 feature 重用才進共用層」。

## Clarifications

### Session 2026-11-03

- 信箱的處理方式為「主檔匯入改直連 Portal」，不再人工匯出 HEX TSV 檔。esign 的解析、發起與白名單照 Spec 023 讀本機，不改為即時查詢 Portal。
- 正式環境由 SRE 沿用 UAT 架構，讓 intranet 所在主機可以連線 Portal。
- 登入：未來 intranet 改由 auth 決定登入狀態。本規格範圍內，三個登入入口的員工資料直接即時讀 Portal。
- Portal 連線帳號使用 `survey_role`，連線設定以新增的環境變數提供。
- 主檔匯入改為 worker 每天早上 04:00 自動從 Portal 匯入本機 users。
- 選人部門樹改為直接讀 Portal。
- 離職處理：Portal 明確標為非在職的既有員工，每日匯入自動停用本機帳號；Portal 恢復在職時不自動恢復。Portal 查不到某人不算離職。單次停用人數異常時整批停止。
- 不保存原值檔或名冊檔，一切以 Portal 為準。資料有誤時修正 Portal 後重跑，不提供回復功能。
- 不合法資料列個別略過，其餘照常匯入，不再整批停止。這是因為目前 Portal 有 1 位在職者缺姓名，維持整批停止的話，每日匯入會天天失敗。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 選人部門樹改由 Portal 提供 (Priority: P1)

建立人開啟選人功能時，系統直接用 Portal 的部門與人員資料組出部門樹。建立人看到的樹與現在相同，饗賓人平台故障也不影響選人。

**Why this priority**: 使用者最先提出的就是這一項，也是 023 刻意留給饗賓人的最後一個選人依賴。

**Independent Test**: 用合成的 Portal 部門與人員資料，在饗賓人組織樹 API 被阻斷的情況下，以有效員工 session 查詢部門樹。比對結構、排序、欄位與快取行為，並確認對饗賓人的請求數為 0。

**Acceptance Scenarios**:

1. **Given** 使用者已登入且快取不存在，**When** 查詢部門樹，**Then** 從 Portal 組出部門樹，回應格式與現行一致，並寫入 1,800 秒快取。
2. **Given** Portal 有多個根部門、深層子部門與沒有員工的部門，**When** 查詢，**Then** 保留完整階層與空陣列；子部門的員工不會被複製到上層部門。
3. **Given** 某部門的上層部門不存在或已停用，**When** 查詢，**Then** 該部門以根節點出現，不會消失。
4. **Given** 人員中有試用員工、離職員工，或所屬部門已停用的員工，**When** 查詢，**Then** 只列出所屬部門仍有效的正式員工；被排除的人數記入 log，不記錄個資。
5. **Given** 部門代碼為空、部門代碼重複或上下層形成循環，**When** 查詢，**Then** 整批回傳現行的組織架構來源錯誤，不寫入快取。
6. **Given** 快取仍有效，**When** 任何已登入使用者查詢，**Then** 不查 Portal，也不延長快取期限；未登入時即使快取存在仍回傳 401。

### User Story 2 - 三個登入入口的員工資料改讀 Portal (Priority: P1)

同仁以三種方式登入時，系統直接從 Portal 讀取員工資料，並更新本機員工資料：

- 帳密登入
- 饗賓人 App WebView 進入
- OAuth 登入

身分驗證仍由上游負責：帳密與 WebView 由饗賓人驗證，OAuth 由 auth 驗證。intranet 讀 Portal 是為了取得最新的員工資料，並沿用現行的在職檢查。

**Why this priority**: 登入是所有功能的入口。改讀 Portal 後，員工資料以 Portal 當下狀態為準，不再受饗賓人每日同步延遲影響。

**Independent Test**: 用合成 Portal 人員資料，在饗賓人員工查詢 API 被阻斷的情況下，對三個入口分別測試以下情境，並比對結果與本機員工資料：
- 試用員工
- 正式員工
- 其他狀態
- 查無此人
- 欄位不合法
- Portal 無法連線

**Acceptance Scenarios**:

1. **Given** Portal 中該員編剛好有一筆試用或正式資料，**When** 由任一入口登入，**Then** 登入成功，本機員工的姓名、人員狀態名稱、部門代碼／名稱與職稱照現行規則更新。
2. **Given** Portal 查無該員編、同一員編有多筆，或狀態不是試用／正式，**When** 登入，**Then** 依現行規則拒絕，錯誤碼與訊息不變。
3. **Given** Portal 資料欄位不合法，例如姓名空白、員編或部門代碼含非法字元、長度超過限制，**When** 登入，**Then** 依現行規則拒絕，不把不合法資料寫入本機。
4. **Given** Portal 無法連線或查詢逾時，**When** 登入，**Then** 回傳現行的「暫時無法使用」類錯誤，不改查饗賓人，也不改用本機舊資料放行。
5. **Given** 帳密登入時饗賓人驗證密碼通過，但 Portal 顯示此人已非在職，**When** 登入，**Then** 拒絕登入。
6. **Given** 今天才進入 Portal 的新進同仁，**When** 由 OAuth 登入，**Then** 員工資料查詢當天即可通過，不必等饗賓人的每日同步。

### User Story 3 - 每天自動從 Portal 更新本機員工主檔 (Priority: P2)

worker 每天早上 04:00 自動從 Portal 讀取員工資料，更新本機員工主檔，包括新進同仁與資料異動。維運人員不再需要登入主機手動匯出 HEX TSV 檔、搬檔再匯入；需要臨時同步時，仍可手動執行匯入工具，來源同樣是 Portal。

**Why this priority**: 本機主檔是 esign 解析、發起與寄信白名單的資料來源。改成每日自動更新，可移除人工匯出與搬檔，也避免主檔因為忘記匯入而過期。

**Independent Test**: 以至少 5,001 位合成人員的 Portal 資料觸發每日匯入，再以同一來源觸發第二次。核對建立、更新與停用結果、中文完整性，以及第二次實際變更數為 0。再分別注入不合法資料、超過門檻的停用人數與 Portal 無法連線，確認本機主檔維持前一次結果，且主機上沒有留下名冊檔。

**Acceptance Scenarios**:

1. **Given** 已到每天 04:00（台北時間），**When** worker 執行每日匯入，**Then** 讀取 Portal 在職（試用／正式）人員的員編、姓名、人員狀態、部門代碼／名稱、職稱與 Email，依 023 的規則建立缺少的帳號並更新既有帳號；同一天只執行一次，部署多個 worker 也不會重複執行。
2. **Given** 本機資料已與 Portal 相同，**When** 每日匯入執行，**Then** 實際變更數為 0，不改動資料的更新時間。
3. **Given** 來源姓名或部門名稱含中文、罕用字或全形符號，**When** 匯入，**Then** 內容完整，沒有亂碼或缺字。
4. **Given** 來源有不合法的資料列（缺姓名、Email 格式錯、欄位超長），或同一員編的資料互相衝突，**When** 每日匯入執行，**Then** 只略過這些員編，其餘照常匯入；略過的員工本機資料不變也不停用；log 只記原因分類與筆數，不記個資。
5. **Given** Portal 在 04:00 無法連線、權限不足或查詢逾時，**When** 每日匯入執行，**Then** 該次失敗並記錄，不把來源故障當成「沒有任何員工」，不更新或停用任何帳號；隔天照常執行。
6. **Given** Portal 上某位既有員工的狀態變為試用／正式以外的值，**When** 每日匯入執行，**Then** 停用該員工的本機帳號；之後名單解析回報此人不可用，已發起文件的指派與證據不變。
7. **Given** 某位本機員工在 Portal 查不到，**When** 每日匯入執行，**Then** 不停用，也不更新該帳號。
8. **Given** 被匯入停用的員工後來在 Portal 恢復為試用或正式，**When** 每日匯入執行，**Then** 不自動恢復帳號，恢復走既有人工程序；已被人工停用或軟刪除的帳號同樣不自動恢復。
9. **Given** 這一次要停用的人數超過門檻，**When** 每日匯入執行，**Then** 整批停止、本機不做任何變更，並記錄要停用的人數。
10. **Given** 有新進同仁需要在下一次 04:00 前就能被選為簽署人，或停用人數超過門檻但經確認無誤，**When** 維運人員手動執行匯入工具，**Then** 可先看預覽摘要再正式執行，規則與每日匯入相同；超過停用門檻時需明確確認才會套用。
11. **Given** 員工已參與正式文件，**When** 匯入更新其姓名、部門、狀態或信箱，**Then** 舊文件的身分與信箱快照、通知歷史與簽署證據不變。
12. **Given** 匯入執行完成，**When** 檢查主機上的檔案，**Then** 不留下任何名冊、原值或預覽檔。

### Edge Cases

- **Portal 部分權限被收回**：例如部門表不能讀了，部門樹要明確失敗；不影響只需要人員表的登入與匯入。
- **同一員編有多筆在職資料**：目前 Portal 為 0 筆，但登入仍要拒絕；匯入時內容完全相同的視為一筆，內容不同則略過該員編並計入衝突。不得取第一筆或最後一筆。
- **員編格式**：必須保留前導零與英文字母，以完整字串精確比對。不得以模糊查詢後取第一筆。
- **Portal 中文編碼**：連線必須能完整讀出中文。若讀出內容無法還原成合法文字，視為來源錯誤，不寫入本機或快取。
- **Portal 暫時故障或逾時**：
  - HTTP 服務與 worker 仍要能啟動。
  - 已登入的 session、簽署、文件管理與背景寄信照常運作。
  - 只有部門樹、登入、每日匯入與手動匯入回報來源不可用。
  - 逾時要在可預期時間內回應，不能讓登入無限等待。
- **worker 在 04:00 沒有運作**（例如停機或重新部署）：worker 恢復後執行一次延遲的匯入，不會補跑多次；之後照常每天 04:00。
- **匯入時剛好有人登入更新同一位員工**：匯入在單一交易中鎖定要寫入的員工，同時發生的登入寫入會等待，不會互相覆蓋或留下部分寫入。兩邊的資料都來自 Portal。
- **Portal 有不合法資料列**：個別略過並記錄筆數。手動匯入的預覽會在操作者的終端機列出這些員編，方便請人資修正 Portal；這份清單不寫入 log。
- **第一次執行時累積了大量離職者**：本機可能有很多早已離職、但從未被停用的帳號，第一次每日匯入很可能超過停用門檻而整批停止。維運人員確認預覽摘要後，用手動匯入明確套用。
- **Portal 資料錯誤**：格式合法但內容錯誤（例如部門被改錯）會被照樣匯入，因為 Portal 是唯一權威。修正 Portal 後，隔天或手動重跑即可更正，不提供回復功能。
- **Portal 狀態值超出已知範圍**：試用／正式以外的任何值都視為非在職，與登入的拒絕規則一致。
- **切換當下仍有饗賓人來源的部門樹快取**：兩者資料同源，自然到期即可，不需要額外清除。
- **饗賓人平台故障**：
  - 帳密登入照舊會失敗，因為密碼仍由饗賓人驗證。
  - WebView 與 OAuth 登入、部門樹與匯入不再受影響。
- **Portal 是公司核心系統**：本系統只能讀取。對 Portal 的同時連線數必須有上限，不能因為大量登入佔滿 Portal 的連線。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**：server MUST 提供單一的 Portal 唯讀連線，供部門樹、登入、每日匯入與手動匯入工具共用。
  - 連線設定（主機、埠、資料庫、帳號、密碼）以新增的環境變數提供；這是本規格明確需要的設定。
  - 憑證不得進入版本控制、log、錯誤訊息或 client 回應。
- **FR-002**：系統對 Portal MUST 只執行讀取查詢，並只讀取本規格列出的資料表與欄位。
  - 連線帳號的權限比本規格需要的寬，所以欄位限制由應用程式負責。
  - 不得讀取密碼、身分證字號、生日等欄位。
  - 原始名冊不得寫入 log 或錯誤訊息。
- **FR-003**：Portal 無法連線、逾時、權限不足或回傳不合法資料時，MUST 只影響部門樹、登入、每日匯入與手動匯入，並各自回傳或記錄現行的錯誤類別。
  - 每次查詢 MUST 有等待上限。
  - HTTP 服務與 worker 的啟動，以及不依賴 Portal 的功能，MUST 不受影響。
  - MUST NOT 改查饗賓人或以本機舊資料放行。
- **FR-004**：選人部門樹 MUST 改由 Portal 部門與人員資料組成，取代饗賓人 `hr/org_chart`。以下項目 MUST 與現行一致：
  - 回應欄位與 envelope
  - 授權（須有效員工 session）
  - 快取（1,800 秒、按需更新、讀取不續期、不排程）
  - 錯誤語意（任一筆必要資料不合法即整批失敗、不寫快取；合法空陣列可快取）
- **FR-005**：組樹 MUST 沿用現行饗賓人組織樹的規則：
  - 只包含未停用的部門，以及人員狀態為正式的員工。
  - 依上層部門代碼建立階層；上層不存在或已停用時，該部門作為根節點。
  - 部門依名稱的位元組順序排序，同名再依部門代碼排序；員工依員編排序。
  - 所屬部門不在樹中的員工不列入，並記錄人數（不記個資）。
  - 部門代碼空白或重複、形成循環、或深度超過 100 層時，整批失敗。
- **FR-006**：帳密登入、饗賓人 App WebView 進入與 OAuth 登入三個入口的員工資料查詢，MUST 改為即時讀 Portal，取代饗賓人 `hr/staff_lookup`。
  - 以完整員編精確比對，必須剛好一筆，且人員狀態為試用或正式。
  - 欄位格式與長度驗證、寫入本機員工資料的欄位與規則維持現行。
  - 試用／正式對應現行的人員狀態名稱。
- **FR-007**：登入失敗語意 MUST 維持現行：
  - 查無、多筆、狀態不合格或欄位不合法：回傳登入交換失敗類拒絕。
  - 來源無法使用：回傳暫時無法使用類錯誤。
  - 帳密登入仍先經饗賓人驗證密碼，驗證順序與密碼錯誤、帳號停用的錯誤不變。
- **FR-008**：worker MUST 每天 04:00（台北時間）自動從 Portal 匯入本機員工主檔，取代人工匯出 HEX TSV 檔再匯入。
  - 讀取欄位與 023 FR-002 相同，並記錄來源取得時間。
  - 欄位驗證、分類、精確員編對應、同值不更新與受保護帳號規則沿用 023；不合法或互相衝突的資料列個別略過，不再使整批停止。
  - 在單一交易中鎖定並寫入，全有或全無提交；寫入途中失敗不得留下部分結果。
  - 同一天只執行一次；部署多個 worker 也不得重複執行。worker 停機錯過時，恢復後執行一次。
  - 每次執行 MUST 記錄結果摘要：來源取得時間、各分類筆數（含停用數）、成功或失敗原因，不記個資。
  - MUST NOT 保存原值檔、名冊檔或預覽檔。Portal 是唯一權威，資料錯誤以修正 Portal 後重跑處理，不提供回復功能。
- **FR-009**：023 的手動匯入工具 MUST 改為「立即執行一次每日匯入」，用於臨時同步：
  - 來源改為直接查 Portal，不再接受 HEX TSV 檔案輸入，也不保留檔案輸入作為替代來源。
  - 可只顯示預覽摘要而不寫入；正式執行時重新讀取 Portal，規則與每日匯入相同。
  - 停用人數超過門檻時，必須由操作者明確確認才會套用。
  - 移除 023 的私有預覽檔、原值檔與回復指令。
- **FR-010**：切換後 intranet MUST NOT 再呼叫饗賓人的 `hr/org_chart`、`hr/staff_lookup`、`hr/staff_emails`。
  - 對應的呼叫程式、資料格式驗證與設定依賴 MUST 一併移除，不保留為 fallback 或開關。
  - 饗賓人 `staff/login` 與 WebView token 驗證不受影響。
- **FR-011**：client 可見的 API 路徑、回應格式、HTTP 狀態、錯誤碼與訊息 MUST 不變，client 不需修改。
- **FR-012**：`.env.example` 與部署說明 MUST 列出 Portal 連線設定與所需的最小讀取權限，不含實際值。主檔匯入 runbook（`server/docs/portal-user-import.md`）MUST 改寫：
  - 移除 HEX 匯出 SQL、搬檔與 `--input` 步驟，以及「不連線 Portal」「部門樹與登入仍用原來源」等描述。
  - 加入每日自動匯入的時間、結果摘要的查看方式與失敗時的處理。
  - Spec 006 與 Spec 023 已在本規格建立時加註取代關係；實作若改變取代範圍，MUST 同步更新這兩處註記。
- **FR-013**：每日匯入與手動匯入 MUST 依下列規則處理離職：
  - Portal 中該員編的狀態為試用／正式以外的值時，停用本機帳號。
  - Portal 查不到該員編時，不停用也不更新。
  - 已停用或軟刪除的帳號不自動恢復，Portal 恢復在職也一樣；恢復走既有人工程序。
  - 停用不得更改已發起文件的指派、身分與信箱快照、通知歷史或簽署證據。
  - 單次停用人數超過門檻時，每日匯入整批不寫入並記錄；門檻值在 plan 依 UAT 實際資料訂定。
- **FR-014**：自動化測試 MUST 只使用合成的 Portal 資料，不連真實 Portal、不使用真實名冊。測試 MUST 覆蓋：
  - 組樹規則
  - 三個登入入口的員工資料查詢
  - 每日匯入的排程觸發、單次執行與冪等
  - 離職停用、查不到不停用、不自動恢復、停用門檻
  - 不合法與互相衝突的資料列個別略過
  - 匯入的中文完整性
  - 連線失敗、逾時、權限不足
  - 不合法資料

### Key Entities *(include if feature involves data)*

- **Portal 人員資料**：員編、姓名、人員狀態（0 試用、1 正式、其他非在職）、部門代碼、部門名稱、職稱、Email。來源為 Portal 人員表，本系統只讀。
- **Portal 部門資料**：部門代碼、部門名稱、上層部門代碼、啟用日、停用日。來源為 Portal 部門表，本系統只讀。
- **Portal 連線設定**：主機、埠、資料庫、帳號與密碼。只存在於部署環境。
- **選人部門樹**：沿用 Spec 006／019 的回應與快取契約，只更換資料來源。
- **每日匯入結果摘要**：每次執行的來源取得時間、各分類筆數與成功／失敗原因，不含個資。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**：在饗賓人 `hr/org_chart`、`hr/staff_lookup`、`hr/staff_emails` 全部被阻斷的情況下，以下功能都能完成，且對這三個端點的請求數為 0：
  - 部門樹查詢
  - WebView 與 OAuth 登入
  - 帳密登入（`staff/login` 正常時）
  - 每日匯入與手動匯入
- **SC-002**：以同一份合成 Portal 資料比對，本系統產生的部門樹與現行饗賓人規則產生的結果 100% 一致，包括結構、排序與欄位。比對案例涵蓋：
  - 多根節點、深層巢狀
  - 上層部門停用
  - 無員工的部門、空資料
  - 所屬部門無效的員工
- **SC-003**：三個登入入口在以下案例中，結果與錯誤類別 100% 符合現行規格：試用、正式、其他狀態、查無、多筆、不合法欄位、來源不可用、逾時。
- **SC-004**：Portal 端剛新增或剛改為非在職的人員，下一次登入時的員工資料查詢就反映新狀態，延遲 0 天。
- **SC-005**：以 5,001 位合成人員（含中文、罕用字與前導零員編）執行每日匯入，結果符合 Spec 023 SC-001：分類一致、員編對應正確率 100%、既有員工 ID 與歷史文件關聯變更數 0；另外中文完整率 100%，同來源第二次執行的實際變更數 0，並行修改或中途失敗時的部分寫入數 0。
- **SC-006**：模擬連續 7 天的排程，每天恰好執行 1 次；即使同時運作 2 個 worker，也沒有重複執行。Portal 故障或資料不合法的那一天，本機主檔的變更數為 0。
- **SC-007**：Portal 無法連線時，HTTP 服務與 worker 可正常啟動，已登入使用者可完成簽署。部門樹與登入在 15 秒內回報來源不可用，改查饗賓人或放行的次數為 0。
- **SC-008**：對 Portal 讀取的欄位中，密碼、身分證字號、生日的出現次數為 0；log 與錯誤訊息中，原始名冊與連線憑證的出現次數為 0；匯入後主機上留下的名冊、原值或預覽檔數量為 0。
- **SC-009**：合成資料中 Portal 標為非在職的既有員工，下一次每日匯入後 100% 被停用；只是在 Portal 查不到的員工被停用的比例為 0%；被停用後又恢復在職的員工被自動恢復的比例為 0%。停用人數超過門檻的那一次，本機變更數為 0。
- **SC-010**：合成資料中混入缺姓名、Email 格式錯與同員編衝突的資料列時，其餘員工 100% 正常匯入，被略過的員工本機資料變更數為 0；log 中出現被略過員編的次數為 0。

## Assumptions

- **Portal 資料位置**：Portal 為公司新 Portal 的 MySQL，人員表為 `sys_person`，部門表為 `chi_department`。plan 階段 MUST 在 UAT 核對實際欄位名稱與型別。
- **人員表需要讀取的欄位**：員編、姓名、人員狀態、部門代碼、部門名稱、職稱、Email。
- **部門表需要讀取的欄位**：部門代碼、名稱、上層部門代碼、啟用日、停用日。
- **連線帳號**：使用 `survey_role`，與 oauth 的同步 worker 共用。UAT 這條帳號規則目前沒有個別連線上限。正式環境由 SRE 依 UAT 架構建立對應的帳號規則，上線前 MUST 驗證網路可達、帳號可登入，以及兩張表的讀取權限。
- **時區**：每日匯入的 04:00 為台北時間。
- **失敗通知**：每日匯入失敗（包括超過停用門檻）只記錄 log，不新增告警通道。
- **停用門檻**：spec 只規定要有門檻與超過時的行為，實際值在 plan 依 UAT 的在職人數與每日離職量訂定。
- **資料即時性**：登入時的員工資料即時查詢不快取；部門樹最多落後 30 分鐘（快取期限）；本機主檔最多落後一天，需要時可手動匯入。
- **與 Spec 023 的關係**：匯入工具已由 Spec 023 以 HEX TSV 檔案輸入完成。本規格沿用它的驗證、分類與交易寫入；更換來源、加上每日排程與離職停用；移除私有預覽檔、原值檔與回復功能。

- intranet 改由 auth 決定登入狀態、收掉帳密或 WebView 登入。
- 簽署人解析、正式發起與寄信白名單改為即時查 Portal。這些流程照 Spec 023 讀本機主檔。

- 對 Portal 寫入、部門樹落地到本機資料表，以及正式環境部署。
