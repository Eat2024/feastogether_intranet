# Feature Specification: 發起受理後立即顯示文件列表摘要

**Feature Branch**: 尚未建立專用實作分支；規格目錄獨立於分支命名。

**Created**: 2026-11-04

**Status**: Draft

**Input**: 使用者希望發起簽署時先保存列表需要的基本資料，受理後立即返回列表；大量簽署資料仍留在背景處理。已確認準備期間顯示「發起中」，呈現文件名稱、編號、簽署期間、建立人與預計簽署人數，完成後才顯示「簽署中」。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 受理後立即確認發起內容 (Priority: P1)

發起人提交簽署名單與期間後，不必等待大量簽署資料準備完成，就能回到列表確認本次發起的文件、日期與人數，知道系統已受理。

**Why this priority**: 單純顯示草稿、空白日期或 0/0，容易讓發起人誤以為操作未成功而重複送出。

**Independent Test**: 暫停背景處理，對草稿發起 5,213 人簽署；確認受理後仍能返回列表並看到完整摘要。

**Acceptance Scenarios**:

1. **Given** 發起人已確認一份文件、簽署期間與 5,213 位簽署人，**When** 系統成功受理但背景處理尚未開始，**Then** 返回列表，同一份文件顯示原文件名稱、編號、建立人、此次確認的開始與結束日期、「發起中」及 `0/5213`。
2. **Given** 草稿先前保存的期間或名單與本次提交不同，**When** 本次發起成功受理，**Then** 發起中摘要以本次受理內容為準，不混用舊草稿資料。
3. **Given** 使用者未通過發起驗證或系統無法可靠受理，**When** 發起失敗，**Then** 顯示既有錯誤訊息，文件不顯示本次發起中摘要，也不宣告已成功發起。
4. **Given** 僅發起 1 位簽署人，**When** 系統受理，**Then** 使用相同流程，準備期間顯示 `0/1`，不依人數切換發起方式。

---

### User Story 2 - 重整後仍可辨識正在發起的文件 (Priority: P1)

發起人重新整理、離開後返回，或有文件閱讀權限的同部門同仁開啟列表時，都能看到一致的發起中摘要。發起期間不允許修改與重複發起，避免畫面與實際工作內容不同。

**Why this priority**: 受理結果必須可靠保存，不能只依賴發起者當下的畫面；其他操作入口也不能改動已確認的內容。

**Independent Test**: 保持任務排隊，重新整理及使用另一位具既有閱讀權限的帳號查看；嘗試修改文件或簽署人。

**Acceptance Scenarios**:

1. **Given** 文件正在排隊或執行背景準備，**When** 發起人重新整理或重新開啟列表，**Then** 仍顯示相同的發起中狀態、確認期間與預計人數。
2. **Given** 同部門同仁原本可閱讀該文件，**When** 查看列表，**Then** 可看到相同摘要，但不因此取得修改權限或完整受理名單。
3. **Given** 文件發起中，**When** 發起人嘗試修改文件、期間、欄位或簽署人、刪除文件或重複發起，**Then** 操作遭拒，並顯示文件正在背景發起、暫時無法異動的訊息；其他操作入口也遵循相同限制。
4. **Given** 一般列表有草稿與發起中文件，**When** 篩選「發起中」，**Then** 只顯示已受理且仍在背景準備的文件。

---

### User Story 3 - 背景結束後切換至真實文件狀態 (Priority: P2)

發起人停留在列表時，系統會更新背景工作的結果。只有正式簽署資料全部準備成功後才可開放簽署；準備失敗時不持續顯示發起中，也不留下假的簽署進度。

**Why this priority**: 快速受理不能犧牲文件狀態與簽署資料的一致性。

**Independent Test**: 分別讓同一類發起工作成功、最終失敗與暫時重試，觀察列表及簽署資格。

**Acceptance Scenarios**:

1. **Given** 發起中顯示 `0/5213`，**When** 全部正式簽署資料準備完成，**Then** 列表自動改依文件正式狀態及實際簽署統計顯示；一般有效期間內顯示「簽署中」，不需手動重整。
2. **Given** 文件尚在背景準備，**When** 有人嘗試簽署，**Then** 系統不得因列表已有日期與人數而提前授予簽署資格。
3. **Given** 背景工作明確最終失敗，**When** 列表取得最新結果，**Then** 不再顯示發起中摘要，恢復既有草稿顯示與可用操作；不將失敗工作的預計人數當成正式簽署人數。
4. **Given** 工作遇到暫時錯誤且仍會自動重試，**When** 查看列表，**Then** 保持「發起中」、相同期間與預計人數，不暫時解鎖編輯。
5. **Given** 正式發起成功但通知信被白名單略過或寄送失敗，**When** 查看文件，**Then** 文件狀態與簽署人數不受寄信結果影響。

### Edge Cases

- 背景準備快於頁面切換：首次顯示即可使用正式狀態，不為了展示發起中而倒退狀態。
- 已受理但使用者未收到回應：重新整理可看到可靠保存的摘要；重複提交不得產生第二組正式簽署資料，沿用既有防重規則。
- 同時開啟多個分頁：任一入口皆遵循發起中異動限制，舊畫面不能覆寫確認的內容。
- 背景處理停止或恢復：排隊與可恢復中的工作保留摘要；只有明確終態才解除發起中。
- 名單中有人在受理後失去資格：依既有整批成功或整批失敗規則處理，不靜默減少人數並宣告成功。
- 到達簽署截止時間仍未準備成功：沿用既有逾時規則，不因摘要已存在而開放簽署。
- 列表讀取中背景工作恰好完成：不得出現正式狀態搭配缺少正式名單，或持續顯示舊摘要；下一次成功更新須收斂為正式結果。
- 列表更新失敗或網路中斷：不得將讀取失敗當成任務失敗或成功，沿用既有讀取錯誤提示。
- 預計人數不是處理進度：背景已檢查幾位不會使 `0/N` 的分子增加；分子只表示已完成簽署人數。

### 追加需求：文件建立時間

2026-11-04 使用者要求電子簽列表增加文件建立時間。欄名為「建立時間」，放在文件編號之後、簽署開始時間之前；所有文件狀態均顯示原始文件建立時間，採台北時間 `YYYY/MM/DD HH:mm`。發起、背景完成、編輯或重新發起不改變此時間；原有開始／結束時間仍表示簽署期間。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 保留所有人數規模均以背景方式準備正式簽署資料；受理後返回列表不以完成大量正式資料建立為前提。（US1）
- **FR-002**: 系統 MUST 在回報受理成功前，可靠保存與本次確認內容一致的文件關聯、開始／結束時間及預計簽署人數；摘要與受理結果不得一成一敗。（US1、US2）
- **FR-003**: 發起中列表 MUST 顯示文件名稱、文件編號、建立人、確認的簽署期間、「發起中」及 `0/N`；N 為本次受理且經既有名單規則確認的預計簽署人數，不是已建立數量或寄信數量。（US1）
- **FR-004**: 系統 MUST 區分受理成功與正式發起完成；受理訊息應說明已受理並正在背景處理，不得宣稱已通知所有簽署人。（US1）
- **FR-005**: 摘要 MUST 可在重整、重新登入與其他具原有文件閱讀權限的使用者查看時取得；不得新增文件可見範圍或揭露完整名單、信箱、簽署憑證。（US2）
- **FR-006**: 準備中的文件 MUST 可用「發起中」篩選；排隊、執行與自動重試等待都屬於發起中。（US2、US3）
- **FR-007**: 系統 MUST 延續既有發起中異動限制，禁止修改文件與簽署人、刪除及重複發起；列表停用相應操作，直接從其他入口送出也必須拒絕。（US2）
- **FR-008**: 列表 MUST 在有發起中文件時自動取得最新結果，離開列表或全部工作結束後停止為本功能持續更新；狀態顯示不依賴使用者手動重整。（US3）
- **FR-009**: 系統 MUST 只有在正式簽署資料完整建立後才開放簽署；成功後改用文件正式狀態、期間與實際簽署統計，不再使用受理摘要替代正式結果。（US3）
- **FR-010**: 最終失敗 MUST 移除該工作對列表顯示的覆蓋，恢復既有草稿與操作規則；不得留下可簽署的部分名單，也不得把受理內容當成已成功發起。（US3）
- **FR-011**: 防重、工作恢復與全有或全無的正式發起保障 MUST 沿用既有規則；已受理的重複請求不能新增摘要副本或重複簽署人。（US2、Edge Cases）
- **FR-012**: 通知信是否寄送、被白名單略過或失敗 MUST 與發起中顯示及正式簽署資格分開判斷。（US3）
- **FR-013**: 發起中日期 MUST 與使用者確認的日期一致，沿用列表日期顯示規則，不得因時區轉換偏移一天。（US1、US2）

- **FR-014**: 電子簽列表 MUST 在文件編號與開始時間之間新增「建立時間」欄，所有狀態顯示文件原始建立時間，格式為台北時間 `YYYY/MM/DD HH:mm`；不得以更新時間、發起受理或完成時間替代，不改既有預設排序。（US1）

### Key Entities *(include if feature involves data)*

- **文件**：既有文件身分、名稱、編號、建立人與正式生命週期；可顯示發起中，但不表示已開放簽署。
- **發起受理摘要**：綁定一份文件與一次有效發起，包含確認的簽署期間、預計簽署人數及準備狀態；描述業務資訊，不預設新增儲存結構。
- **正式簽署人與簽署統計**：準備成功後的正式名單與已簽數量；與受理時預計人數分開。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在正常測試網路下，分別以 1、100、5,213 人各測試 20 次，自確認送出且既有前置名單檢查完成起，到返回列表並看到受理摘要，95% 操作在 3 秒內完成。另行記錄從點擊發起起的完整等待時間，不將前置檢查排除後的結果宣稱為整體等待時間。
- **SC-002**: 在背景工作刻意延後至少 30 秒的情況，受理後首次列表顯示與重整後的期間、預計人數、文件身分 100% 與確認內容一致，且不出現 0/0 或空白日期替代已確認資料。
- **SC-003**: 正常連線且前景列表持續開啟時，工作成功或最終失敗後 5 秒內顯示對應結果；無需手動重整。
- **SC-004**: 排隊、執行與重試等待各階段的文件／簽署人異動與提前簽署測試，100% 被既有權限及狀態規則阻擋。
- **SC-005**: 5,213 人成功案例正式簽署人數等於受理預計人數，無重複或部分開放；失敗案例不留下本次部分正式簽署資料或虛假的簽署中狀態。

- **SC-006**: 草稿、發起中與正式發起完成的同一文件，其建立時間顯示保持相同，並與原始建立時間的台北時區轉換 100% 一致；窄螢幕可透過既有表格捲動讀取新欄位。

## Assumptions

- 本規格延伸 [Spec 022](../022-background-signature-initiation/spec.md) 與 PR #50 的「發起中」顯示，不回退背景發起。規劃時已確認 PR #50 於 2026-11-04 合併，沿用其狀態與輪詢，避免重複實作。
- 使用者已明確同意本次修改前端；本規格取代 Spec 022 [backend-only-scope.md](../022-background-signature-initiation/backend-only-scope.md) 中「不改前端、列表仍可呈現草稿」對本功能的限制，其餘可靠性與權限保障保留。
- 優先沿用既有文件及已受理工作保存的資訊。此規格未授權新增資料表、環境變數或額外排程；必要技術選擇留待 plan 評估。
- 發起中不提供正式簽署進度、匯出或新增編輯能力；`0/N` 僅提供名單規模確認。
- 最終失敗採回到既有草稿呈現；不要求把受理輸入覆寫成草稿設定。獨立失敗詳情、新的重試畫面、取消工作功能不在本次範圍。
- 本次不修改員工資料同步、前置員編解析、寄信白名單、通知投遞、簽署證據與既有大量處理容量限制。
- 3 秒受理及 5 秒結果更新為規劃驗收目標，並非宣稱現況已達成；背景執行總時間不作為返回列表的等待條件。
