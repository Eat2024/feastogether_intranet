# Feature Specification: 多子功能角色權限與電子簽授權

**Feature Branch**: 未建立專用分支；規格編號 `028-module-authorization`

**Created**: 2026-11-04

**Status**: Draft — grilling 決策已確認，待 plan

**Input**: 沿用 CKS 角色／權限管理概念，改為子功能隔離與同功能多角色聯集；有效員工固定具備電子簽同仁資格，Super user 全權且獨占授權管理。管理 API 與 REPL 共用業務規則及稽核；本次不做管理畫面。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 員工自動取得電子簽基本資格 (Priority: P1)

有效員工不必先請人授權，即可簽署自己的任務、取得本人副本並閱讀自己部門的文件。

**Why this priority**: 確保電子簽基本工作不中斷，也不把建立／匯出權限自動授予全體員工。

**Independent Test**: 使用沒有任何額外角色的有效員工，以同一會話驗證本人任務、同部門閱讀與受限操作。

**Acceptance Scenarios**:

1. **Given** 有效員工尚未取得任何角色，**When** 從 OAuth／WebView 完成登入，**Then** 自動具備同仁資格，不需要人工指派。
2. **Given** 有效員工已具有其他角色，**When** 查詢有效權限，**Then** 同仁資格仍存在；移除其他角色不影響同仁。
3. **Given** 同仁與同部門未刪除文件，**When** 查列表、詳情與原始 PDF，**Then** 可以唯讀瀏覽各既有可見狀態；沒有跨部門可見資格的文件不揭露。
4. **Given** 同仁是指定員工簽署人，**When** 簽署／拒簽或讀本人結果與副本，**Then** 依既有資格、期限與狀態規則處理；別人的個人副本與簽名圖仍不可取得。
5. **Given** 只有同仁資格，**When** 建立文件、管理他人文件、一般／批次匯出或讀一般匯出歷史及下載，**Then** 後端拒絕，不因同部門或前端未隱藏按鈕而放行。
6. **Given** 員工本地停用或刪除，**When** 沿用既有會話，**Then** 不得因同仁或其他角色繼續存取；缺少可信部門時，部門閱讀依既有錯誤規則拒絕，本人簽署資格另行判斷。

### User Story 2 - 跨子功能角色隔離與多角色聯集 (Priority: P1)

同一員工可以在不同功能具備不同角色，也可以在同一功能兼任多個角色。

**Why this priority**: 防止某功能管理員變成全平台管理員，並避免大量組合角色。

**Independent Test**: 用兩個子功能的隔離測試資料與同名角色，驗證多角色聯集、跨功能拒絕及生效時間；不建立虛構業務的正式權限目錄。

**Acceptance Scenarios**:

1. **Given** 甲只有電子簽管理角色，**When** 嘗試操作另一子功能，**Then** 不因角色同名或管理員字樣而取得該功能權限。
2. **Given** 同功能兩個有效角色各授予不同能力，**When** 員工使用兩項能力，**Then** 均可通過功能授權；未授予能力仍拒絕。
3. **Given** 某能力由兩個角色同時授予，**When** 撤銷其中一個，**Then** 另一角色仍授予該能力；不引入拒絕權限或角色優先序。
4. **Given** 角色／權限來自不同子功能，**When** 嘗試綁定或偽造指派範圍，**Then** 寫入被拒絕，原關聯不變。
5. **Given** 員工已登入，**When** 角色停用、權限修改或角色指派撤銷提交成功，**Then** 下一次請求依最新有效權限判斷，不要求重新登入，各服務實例一致。

### User Story 3 - Super user 管理授權與預先指派 (Priority: P1)

Super user 透過管理介面契約或 REPL 維護角色與指派；員工不必先登入才能被配置。

**Why this priority**: 支援沒有管理前端的第一版，以及上線前的角色配置。

**Independent Test**: Super user 建立角色、配置權限、查核員編並指派，員工登入驗證結果，再撤銷並核對稽核。

**Acceptance Scenarios**:

1. **Given** Super user，**When** 查權限目錄、建立／修改／停用／刪除一般角色、配置權限、查看及修改員工角色，**Then** 僅操作已登錄子功能與權限，異動可追查。
2. **Given** 普通員工或電子簽管理員，**When** 呼叫任何授權管理操作，**Then** 拒絕；不能透過自訂角色或猜測權限碼取得授權管理能力。
3. **Given** 員工尚未登入，**When** Super user 提供員編指派角色，**Then** 查核既有 Portal 有效員工，建立或取得同一本地員工後指派；不存在、無效、模糊匹配或查核失敗皆拒絕。
4. **Given** 同仁內建角色，**When** 嘗試修改權限、停用、刪除或移除有效員工的同仁資格，**Then** 拒絕；不得把它變成全員高權限角色。
5. **Given** 同一授權變更，**When** 分別使用 API 與 REPL，**Then** 遵守相同資格、範圍與交易規則，記錄相同必要稽核資料；失敗不留下半套角色指派。
6. **Given** 使用中的一般角色，**When** 刪除，**Then** 拒絕並要求先解除指派；停用可保留關聯但下一請求不再授權。

### User Story 4 - 全權限仍遵守文件與簽署規則 (Priority: P1)

電子簽管理員與 Super user 可跨部門管理文件，但不能代替他人簽名或破壞已成立的證據。

**Why this priority**: 分清資料管理範圍與簽署身分，避免全權限變成任意改寫。

**Independent Test**: 用不同建立人與部門、不同文件狀態，驗證一般角色、電子簽管理員與 Super user 的操作差異。

**Acceptance Scenarios**:

1. **Given** 文件建立者角色，**When** 建立及維護／發起自己的文件，**Then** 按既有部門、建立人與狀態規則處理；不能因有建立權限修改別人的文件。
2. **Given** 電子簽管理員或 Super user，**When** 跨部門查閱、管理或一般匯出文件，**Then** 功能與資料範圍允許，但文件狀態、並發保護、儲存與證據限制仍須成立。
3. **Given** 任一管理者不是指定簽署人，**When** 嘗試代簽、代拒簽或使用別人的本人副本入口，**Then** 拒絕；全權限不能冒用簽署身分或外部邀請。
4. **Given** 管理者修改他人文件，**When** 操作合法完成，**Then** 保留原建立人、建立部門與歷史簽署證據，不把操作者冒寫成原建立人。
5. **Given** 全權限使用者操作已完成或停止文件，**When** 請求現有狀態不允許的修改，**Then** 仍拒絕，不因管理角色繞過狀態規則。
6. **Given** Super user 沒有部門，**When** 建立需要歸屬部門的新文件，**Then** 必須明確提供並驗證有效歸屬部門，不能偽造員工部門或建立無歸屬的業務資料。

### User Story 5 - 舊資料導入與維運查詢 (Priority: P1)

上線前保留既有員工與文件關聯，配置必要額外角色後才啟用授權限制。

**Why this priority**: 避免上線後所有文件建立者突然無法工作，也避免用全權限過渡。

**Independent Test**: 在保留既有員工、文件及會話的測試資料中完成導入、預先指派與切換，再查有效權限。

**Acceptance Scenarios**:

1. **Given** 既有有效員工與會話，**When** 導入新授權規則，**Then** 不必重新登入即具備同仁資格，原員工 ID、文件／簽署關聯保持不變。
2. **Given** 既有使用者曾建立或匯出文件，**When** 初始化角色，**Then** 不從歷史行為自動推導額外權限；上線前依核定名單指派。
3. **Given** 預先授權已完成，**When** 啟用新規則，**Then** 需要額外角色者可繼續工作，只有同仁者依新限制被拒絕，不以全域放行補救。
4. **Given** REPL 查詢某員工／角色權限，**When** 查詢，**Then** 結果與實際後端授權一致，排除停用／刪除角色，Super user 與同仁來源可辨識。

### Edge Cases

- 同名角色分屬不同子功能，不得碰撞；角色更名不改變授權身分，角色名稱不構成權限。
- 權限目錄只含現有電子簽與平台授權管理；未知／已移除權限不得由管理者自行創造，殘留指派不得繼續授權。
- 所有非公開入口須明確分類為登入即可或特定能力；漏標不得成為永久放行入口，切換前盤點完整覆蓋。
- 身分有效但無能力與未登入必須可區分；403 不等同要求重新登入。為避免資料探測，既有資源不可見時的 404 語意保留。
- 本人跨部門簽署／副本資格、調職後部門查閱與一般匯出仍按各自規則，不能全部收斂成部門判斷。
- 角色變更後尚未提交的後續操作以新權限為準；已受理的背景工作不承諾倒退取消，但後續結果查詢／下載須重驗當前權限。
- 並發預先建檔與首次登入，只產生同一本地員工；重複指派不產生重複有效關聯。
- 讀取有效權限不得偷偷建立角色或業務關聯；同仁補齊在導入／登入寫入或等效的唯讀授權判定中實現，不讓查詢產生業務寫入。
- 不新增局部停權功能；整個員工停用沿用既有規則。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 角色與權限 MUST 各自歸屬一個子功能，以穩定識別區分；跨子功能不能混綁，不能以名稱或選單群組推論隔離。（US2）
- **FR-002**: 員工 MUST 可在同一或不同子功能持有多個角色，有效能力取聯集；不引入拒絕權限、優先序或全域單一員工角色。（US2）
- **FR-003**: 有效員工 MUST 永久具備電子簽同仁基本資格，首次登入、預先建檔與既有員工導入均涵蓋；有其他角色不排除同仁。（US1、US3、US5）
- **FR-004**: 同仁 MUST 是受保護內建角色，其能力由程式版本維護，管理 API／REPL 不得修改、停用、刪除或撤銷有效員工此基本資格。（US3）
- **FR-005**: 同仁 MUST 僅具備本人任務簽署／拒簽、依既有業務規則可取得的本人結果與副本，以及同部門列表／詳情／原始 PDF 閱讀；不授予建立、一般匯出或跨部門管理。（US1）
- **FR-006**: 系統 MUST 提供下列初始角色矩陣；除同仁外，其餘角色可由 Super user 維護，不因初始化重跑覆蓋已調整的一般角色設定。（US1～US4）
- **FR-007**: Super user MUST 擁有全部已登錄功能權限與跨部門管理範圍，且獨占授權管理；其他角色不能取得等同 Super user 的平台授權管理資格。（US3、US4）
- **FR-008**: 所有角色與 Super user MUST 遵守指定簽署身分、外部憑證邊界、文件狀態、並發保護及證據不變量；不能代簽／代拒簽或冒用本人副本。（US4）
- **FR-009**: 電子簽跨部門管理 MUST 是可辨識的明確能力，不靠角色名稱；可管理他人文件的例外只放寬建立人／部門限制，不變更原建立人／歸屬或狀態規則。（US4）
- **FR-010**: 系統 MUST 提供子功能／權限目錄、角色列表與詳細資料、一般角色建立／修改／停用／刪除、角色權限配置、員工角色查詢／指派／撤銷及目前操作者有效能力的管理／查詢契約。（US2、US3、US5）
- **FR-011**: 權限與子功能目錄 MUST 隨程式版本定義；管理者只能組合已存在且同範圍的權限，不能動態新增無業務實作的權限。（US3、Edge Cases）
- **FR-012**: 員編預先指派 MUST 查核既有 Portal 的有效員工並沿用同一本地身分；不存在、失效、模糊匹配或查核失敗拒絕，不使用任意員編或舊資料 fallback。（US3）
- **FR-013**: 授權異動成功提交後，下一次請求 MUST 使用最新角色／權限狀態，適用所有既有 session 與服務實例；不把權限固定在 cookie 內，也不新增每功能 cookie。（US2）
- **FR-014**: API 與 REPL 授權寫入 MUST 共用業務規則與原子結果，記錄操作者、來源、時間、子功能、目標與必要前後差異；無稽核不得宣稱變更成功。（US3）
- **FR-015**: REPL MUST 可查詢角色／員工實際有效能力、執行授權管理及查詢授權稽核；寫入須明確以維護操作者執行，不以裸 SQL／repository 寫入當作正式授權流程。（US3、US5）
- **FR-016**: 授權記錄 MUST 不含登入憑證、完整隱藏入口、員工不必要個資、簽名或文件內容；不恢復文件操作／簽署事件歷程。（US3）
- **FR-017**: 所有受影響的文件查詢、寫入、來源檔、一般匯出、歷史／下載、本人簽署／副本及管理入口 MUST 由後端逐次驗證；不能只保護選單或主列表。（US1～US4）
- **FR-018**: 既有有效員工 MUST 僅自動取得同仁，不根據歷史行為提升為建立者／管理員；正式切換前以核定名單完成額外指派與驗證。（US5）
- **FR-019**: 授權目錄／角色匯入 MUST 可重複執行且不重複指派、不重建使用者 ID、不破壞文件與簽署關聯；切換失敗不得改用全域放行。（US5、Edge Cases）
- **FR-020**: 目前能力查詢 MUST 提供按子功能區分的穩定權限識別與最小必要身分種類，供 Spec 029 顯示選單；不回傳其他員工完整授權資料或任何憑證。（US1、US5）
- **FR-021**: 刪除仍被指派的一般角色 MUST 拒絕；停用角色可保留關聯但不得授權，重新啟用依現存有效關聯恢復，不重複插入。（US2、US3）

### 初始角色與能力範圍

| 角色 | 閱讀與本人簽署 | 建立與流程管理 | 一般匯出／歷史／下載 | 授權管理 |
|---|---|---|---|---|
| 同仁 | 同部門文件閱讀；本人任務與副本 | 無 | 無；本人副本例外 | 無 |
| 文件建立者 | 疊加同仁資格 | 建立與管理自己文件，含合法發起、停止、補簽、提醒等既有流程 | 沿既有同部門範圍與檔案規則 | 無 |
| 電子簽管理員 | 跨部門文件閱讀；仍只能本人簽署 | 跨部門管理，保留狀態與證據限制 | 跨部門，保留檔案與證據限制 | 無 |
| Super user（非可指派角色） | 全功能閱讀；不冒用任何簽署人 | 全功能管理，保留狀態與證據限制 | 全功能，保留本人副本邊界 | 全部 |

一般匯出與「他人個人副本」是不同能力；取得完整文件的合法一般匯出不代表可使用任意簽署人的個人憑證／副本入口。員工基本身分不因角色提升成外部簽署人。沒有歸屬部門的管理者不能任意推導部門；新文件歸屬必須明確驗證，詳細輸入契約於 plan 定義。

### Key Entities

- **子功能**：獨立的業務授權範圍，例如電子簽；不等同部門或選單群組。
- **權限**：某子功能可執行的具體能力，由程式目錄定義，具有穩定識別。
- **角色**：單一子功能內的權限集合；同仁為受保護基本角色，其餘可管理。
- **角色指派**：員工與角色的關係，可同時多筆；不把員工限制為一個全域角色。
- **有效授權**：當前有效角色聯集加上基本資格，仍需個別業務資料範圍檢查。
- **授權異動紀錄**：誰經何管道對哪個範圍／對象修改授權，以及必要差異；與簽署事件歷程分離。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 兩子功能、同名角色、多角色聯集及跨範圍偽造的驗收全部通過，跨功能越權成功數為 0。
- **SC-002**: 有效員工在首次登入與既有資料導入後均取得同仁能力；僅同仁者建立、一般匯出與授權管理成功數為 0。
- **SC-003**: 角色／指派變更成功後，全部受測既有會話於下一次操作採用新權限，無須重新登入。
- **SC-004**: API 與 REPL 的相同授權變更結果一致，成功變更稽核覆蓋率 100%，無半套指派或重複有效關聯。
- **SC-005**: 管理者代簽、代拒簽、越過文件狀態或取得他人個人副本的負向情境全部拒絕；合法跨部門管理情境全部通過。
- **SC-006**: 導入後既有員工／文件／簽署關聯保持率 100%；正式切換前核定需額外權限的名單全部完成指派驗證。

## Assumptions

- 依賴 [027](../027-super-user-access/spec.md) 提供可區分員工與 Super user 的會話、維護登入及 REPL 基礎；角色功能不反向依賴選單前端。
- 初期只提供電子簽與平台授權管理目錄；驗收、資產等僅可作隔離測試 fixture，不加入正式業務目錄。
- 不新增子功能停權、委派授權、角色階層、拒絕權限、動態子功能管理、OAuth scope 對應角色或額外快取排程。
- 有效員工與可信部門來源沿用現有 Portal／本地停用規則，不新增逐請求查人事上游的要求。
- 已受理背景工作不因後續撤權自動取消；所有後續存取重新授權。更強的執行中撤銷語意不在本次範圍。
- 本規格預設使用中角色刪除拒絕，可先停用；一般角色權限可由 Super user 調整。同仁權限仍只能隨版本改變。
- Super user 建立文件所需有效歸屬部門是既有文件不變量的延伸；plan 必須確定操作歸屬與稽核身分，不得製造假員工或錯置建立人。

## Scope & Dependencies

- 本 spec 同時涵蓋角色、權限、指派、電子簽後端保護、必要 migration／初始化與 REPL 授權 helpers。這些構成可驗收的單一授權閉環，不拆成可各自漏掉保護的零件。
- 不製作角色／員工管理前端；[029](../029-permission-navigation/spec.md) 只消費有效能力顯示導覽。
- 取代 [001](../001-auth-cleanup-schema/spec.md) 中本次範圍的「不含角色／permission」限制；保留同一員工主體、預設身分驗證與外部憑證隔離。
- 明確取代 [017](../017-department-document-visibility/spec.md) 的「同部門即可一般匯出」：現在需匯出能力與資料範圍同時成立。亦新增明確管理能力可跨部門／建立人管理的例外；一般建立者仍依舊規則。保留部門快照、調職、本人簽署與證據邊界。
- [026](../026-retire-signing-audit/spec.md) 已移除文件／簽署事件歷程；本 spec 只新增授權設定變更的必要稽核，不恢復舊表或用 log 重建同一份文件時間軸。
- 使用者已授權多角色關聯、子功能區分與授權稽核所需持久結構。僅增加欄位無法表達多角色及關聯一致性；plan 須選最小資料模型並處理撤銷／軟刪除／唯一性，不搬整套 CKS schema。
- 啟用前完成端點分類與初始指派；plan 須描述可執行的資料導入、切換與回復順序，不以新增永久 fallback 或預設管理員解決過渡。
- 詳細管理介面路徑、DTO、權限代碼清單與契約留待 plan；沿用專案既有 API 格式與錯誤語意，需含 Super user-only 管理契約和本人能力查詢契約。
