# Feature Specification: 已簽署 ZIP 按需更新與舊版清除

**Feature Branch**: 沿用 `dev`；本次未建立或切換分支

**Created**: 2026-11-06

**Status**: Draft（規格檢核完成，待 plan）

**Input**: 使用者確認：新增簽署只標示 ZIP 已過時；有人點擊更新下載時，依受理當下已簽署名單背景打包。處理期間新簽署不觸發重新打包；新版成功後刪除舊 ZIP。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 有需求才更新 ZIP (Priority: P1)

有匯出權限的員工能知道 ZIP 已包含及尚缺的簽署份數，並在需要下載時才要求更新，避免無人需要也持續打包。

**Why this priority**: 解決後續簽署 PDF 未納入的問題，同時減少不必要的打包。

**Independent Test**: 產生含 1 人的 ZIP，再完成第 2 人簽署。確認只顯示提醒；要求更新後，取得實際含 2 份個人 PDF 的 ZIP。

**Acceptance Scenarios**:

1. **Given** 尚無 ZIP 且無人簽署，**When** 查看匯出頁，**Then** 說明沒有可匯出的文件，不建立工作。
2. **Given** 尚無 ZIP 且已有 2 人簽署，**When** 要求產生下載檔，**Then** 固定受理當下的 2 筆紀錄並背景打包，顯示份數及進度。
3. **Given** 已有含 10 份的 ZIP，**When** 再有 3 人簽署，**Then** 下次讀取匯出狀態時顯示「目前 ZIP 共 10 份，另有 3 份新簽署尚未包含」與「更新並下載 ZIP」，不自動打包。
4. **Given** 有新增簽署且無進行中的工作，**When** 點擊「更新並下載 ZIP」，**Then** 依後端受理時已成立的全部簽署紀錄產生新版，不只打包增量。
5. **Given** 有效 ZIP 已包含全部紀錄，**When** 下載，**Then** 直接提供現有檔案，不建立工作；重複下載不新增歷史紀錄。
6. **Given** 使用者開著過時畫面但另一人已更新完成，**When** 要求更新，**Then** 重新確認實際範圍，已完整涵蓋即沿用，不依畫面人數重複打包。

### User Story 2 - 打包期間持續簽署仍能取得本次成果 (Priority: P1)

使用者要求更新後，能取得本次固定範圍的成果，不因後續簽署反覆重做或無限等待。

**Why this priority**: 大量簽署期間仍須完成下載，多人的相同需求不能造成重複負載。

**Independent Test**: 以 13 份開始打包，期間增加第 14 人並由多人再次申請。確認僅一個進行中的工作，成果仍為原 13 份且可下載，第 14 份只形成過時提醒。

**Acceptance Scenarios**:

1. **Given** 已固定 13 筆紀錄且正在打包，**When** 第 14 人簽署，**Then** 不取消、不重啟、不追加名單，也不排入下一個更新工作。
2. **Given** 同文件正在排隊、等待個人副本或打包，**When** 重複點擊或多人同時申請，**Then** 共用同一工作與名單，即使已有新增簽署也不平行建立新版。
3. **Given** 本次 13 份完成時已有 14 人簽署，**When** 取得本次成果，**Then** 可下載這 13 份並提示尚缺 1 份，不在下載前強迫重新打包。
4. **Given** 成果已完成且仍有新增簽署，**When** 再次明確選擇「更新並下載 ZIP」，**Then** 才依新受理時點產生下一版；查詢、重新整理與成果下載都不觸發更新。
5. **Given** 使用者離頁或重新整理，**When** 回到匯出頁，**Then** 能取得同一進行中工作的進度或完成成果，不重複申請。
6. **Given** 本次範圍有人已簽但個人 PDF 尚未就緒，**When** 背景處理，**Then** 等待該副本，不以少檔 ZIP 宣告完成；副本失敗須顯示原因與適用重試方式。

### User Story 3 - 新版成功後清除舊 ZIP (Priority: P1)

新版可用後清除被取代的 ZIP 實體檔，歷史保留版本資訊；新版失敗則仍有原本成果可下載。

**Why this priority**: 防止版本累積占用空間，也避免先刪舊版造成更新失敗時沒有可下載成果。

**Independent Test**: 驗證新版成功、失敗、刪檔失敗與中斷恢復，檢查下載資格、實體檔案、歷史與個人 PDF。

**Acceptance Scenarios**:

1. **Given** 舊版可下載，**When** 新版尚在處理或失敗，**Then** 舊版仍可用，明示舊版份數及新工作進度／失敗；適用重試沿用失敗工作名單。
2. **Given** 新版完整且確認可用，**When** 切換版本，**Then** 新版成為有效成果，同文件所有被取代的舊 ZIP 停止接受新下載，並清除其實體檔案。
3. **Given** 舊版已被取代，**When** 查看歷史或使用舊連結，**Then** 歷史顯示「已被新版取代」且不可下載；舊連結回報不可用，不以原識別冒充提供新版。
4. **Given** 新版有效但舊檔刪除失敗，**When** 下載新版，**Then** 正常提供新版，舊版仍不可重新下載；保存待清理狀態供恢復後補清理，不將新版降級為失敗。
5. **Given** 切換後、刪檔前中斷，**When** 系統恢復，**Then** 可接續清理，重複清理不誤刪新版、原始文件或個人 PDF。
6. **Given** 舊版有下載名稱與匯出資訊，**When** 新版取代，**Then** 舊紀錄的匯出人、時間、份數及名稱不被改寫，新版獨立記錄其申請與下載名稱。

### Edge Cases

- 新簽署與申請同時發生：依後端固定名單的受理時點劃界，其後成立者留待下一次明確更新。
- 份數相同不能單獨證明範圍相同；新增判斷依簽署紀錄身分，名稱、檔名或個人 PDF 就緒狀態不單獨觸發重包。
- 失敗重試沿用原名單，不暗中擴大範圍；完整性失敗明確報錯，不得繞過驗證提供成果。
- 產製期間暫需兩版空間；清理失敗可能暫存多個舊檔，但不可提供新下載或無聲遺忘清理。
- 已開始的舊版傳輸允許完成；若底層清理導致中斷，提示重新取得新版，不保證舊版續傳。切換後新的下載及續傳請求不得取得已取代版本。
- 有效 ZIP 意外缺檔或損壞須明確報錯；僅缺檔且無新增簽署不構成本次自動重建條件。有新增簽署且明確要求更新時可產生新版，不假稱恢復原檔。
- 權限撤銷、文件刪除或未登入時，不可因掌握工作識別下載；申請及下載均重新驗證現有授權。
- 升級前 ZIP 依原快照比較新增簽署，不在升級時批次重包。首次成功更新後清除該文件被取代舊 ZIP，不影響其他文件。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系統 MUST 顯示 ZIP 份數、資料時點及未包含的新簽署數，區分最新、已過時、處理中、失敗、已被取代。
- **FR-002**: 新簽署、查看頁面、輪詢與重新整理 MUST NOT 建立或重啟打包；只有明確要求產生／更新才可開始。
- **FR-003**: 更新受理 MUST 由後端確認權限、目前工作與簽署紀錄；有效成果已涵蓋全部紀錄時直接沿用。
- **FR-004**: 新版 MUST 包含受理時固定範圍的全部已簽署副本，不受列表篩選影響，不僅包含新增者；無簽署不得建立空 ZIP。
- **FR-005**: 同文件 MUST 最多有一個進行中的打包工作；並行、重複及過時畫面的申請須共用該工作，不因新簽署另排後續工作。
- **FR-006**: 每次工作 MUST 固定紀錄名單及份數；受理後簽署不得改變範圍、導致重啟或阻止本次成果下載。
- **FR-007**: 「下載本次成果」與「再次更新」MUST 是可區分的操作；不得為追逐最新資料自動連續打包。
- **FR-008**: 產製 MUST 在背景執行，使用者可離頁再返回；須顯示等待個人 PDF、進度與失敗，不以少檔成果假稱完成。
- **FR-009**: 適用的失敗重試 MUST 沿用原名單，完整性錯誤不得繞過；新版成功前須保留原有效 ZIP 的檔案與下載資格。
- **FR-010**: 新版完整且可用後 MUST 成為有效版；舊版停止新下載並刪除實體 ZIP，不得先刪舊版才開始產製。
- **FR-011**: 清理 MUST 僅限同文件被取代 ZIP，不得刪除原始文件、簽署證據、個人 PDF、有效版或進行中工作所需資料。
- **FR-012**: 刪檔失敗及處理中斷 MUST 保存可恢復狀態並能補清理；重複清理須安全，不得將成功新版降級為失敗。
- **FR-013**: 歷史 MUST 保留舊版匯出資訊並標示已取代、不可下載；舊連結不得冒充提供新版。新版獨立記錄，重複下載不新增紀錄。
- **FR-014**: 產生、查詢、歷史及下載 MUST 沿用現有文件權限與揭露限制；過時判斷不得向前端洩漏整份快照或額外個資。
- **FR-015**: 既有 ZIP MUST 能依原快照按需更新；升級不得自動全量重包、刪檔或改寫歷史。
- **FR-016**: 自訂檔名 MUST 沿用既有規則，不影響新舊判斷；改名不打包，新版不得改寫舊版名稱。

### Key Entities *(include if feature involves data)*

- **簽署紀錄**：已成立簽署的唯一識別，是判斷是否有新增副本的依據。
- **匯出範圍快照**：一次受理固定的紀錄集合、份數與時點，後續簽署不改寫。
- **ZIP 匯出工作**：固定快照的背景產製及重試，包含申請人、進度、成果及失敗原因。
- **ZIP 版本成果**：具有獨立識別與下載資訊的檔案，可為有效版或已取代版；過時代表尚缺新簽署，不等同已取代或不可下載。
- **舊版清理狀態**：被取代檔案待刪除或已清除的持久紀錄，不等同刪除匯出歷史。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 原 ZIP 1 份、新增 1 人後，明確更新的成果包含正確 2 份 PDF，無漏檔或重複。
- **SC-002**: ZIP 產生後連續新增 100 筆簽署，只查看或重新整理而無更新操作時，新增打包工作數為 0。
- **SC-003**: 同文件 10 人同時申請最多產生 1 個進行中工作；無新增簽署時連續下載 10 次，新增工作及歷史紀錄均為 0。
- **SC-004**: 固定 13 份後新增第 14 人，本次仍可下載原 13 份且提示尚缺 1 份；再次明確更新前，後續工作數為 0。
- **SC-005**: 新版成功、失敗、刪檔失敗及中斷恢復均符合「成功前舊版可用，成功後新版可用」；正常完成清理後同文件只留 1 份有效 ZIP 實體成果。
- **SC-006**: 模擬一次刪檔失敗，恢復能力並完成補清理後，被取代 ZIP 實體數為 0；重試兩次後新版及全部個人 PDF 仍完整存在。
- **SC-007**: 舊版歷史資訊不變且標示已取代，舊連結不再下載；未授權使用者不能透過更新、歷史或舊連結取得文件。
- **SC-008**: 既有 6,000 份容量情境可背景更新，離頁後返回仍可取得進度及成果；處理期間不因新增簽署重做。

## Assumptions

- 本輪只開規格，不實作、部署、刪除檔案或執行資料調整。
- 「點擊當下」指後端受理固定範圍的時點，不是瀏覽器時間；已簽但 PDF 未就緒者仍納入等待。
- 完成後提供明確的「下載本次成果」，不要求瀏覽器自動下載；再次明確更新才追上後續簽署。
- 「刪除舊版」指 ZIP 實體檔，不包含歷史、原始文件、簽署證據與個人 PDF；不提供舊版復原。
- 新版產製中可明確選擇下載舊版，須標示份數與過時資訊，此操作不另啟更新。
- 有效版不因時間經過到期；不新增固定頻率全量更新、簽署後自動打包、增量 ZIP 或取消工作功能。
- 本規格取代 [Spec 019](../019-esign-uat-refinements/spec.md) User Story 2、FR-008／FR-009／FR-010、SC-006 的「後續簽署仍永久沿用原 ZIP」，並限縮 FR-007／SC-005 永久保留對象為未被取代的有效版；新版成功後舊版依本規格清除。其他 UAT 調整不變。
- 沿用 Spec 009 的背景產製、完整性與大量匯出能力，以及現有部門授權、歷史查詢和下載檔名規則。
- plan 須決定最小狀態、清理恢復、並發切換與舊資料相容設計；本規格不預先授權新資料表、環境變數、額外排程或依賴套件。
- 編號 027–029 已存在其他規格分支，使用 030 避免衝突。

## 2026-11-06 範圍澄清

使用者已確認目前沒有 ZIP 匯出 `expired` 資料，本次移除該歷史狀態的相容分支與驗證，不做資料回填或恢復。文件簽署期限／到期邏輯不在此調整範圍；已完成 ZIP 意外缺檔仍依不可用處理。

## 2026-11-06 狀態邊界補充

- 文件 expired 仍代表「已超過簽署期限且尚有人未簽」，完全保留文件 DTO、查詢推導與 client esignDocuments 的此狀態。
- 只清 ZIP 匯出 service／repository 的 expired 判斷與未使用 archiveFile()；未確認其他匯出類型資料前，共用 EsignExportStatus 與歷史頁保留 Excel／PDF 的 expired 相容，不能用 ZIP 查詢結果推論全部。
- 保留 expires_at、idx_esign_export_jobs_expires_at、idx_esign_exports_reuse 中原欄位及 API expiresAt（新 ZIP 仍為 null），不做 schema migration。本輪未查驗所有 export_type 的非 null expires_at，亦未查驗全部檔案 archive_status 分布，不能宣稱可全域刪除。
- 若另案要移除所有匯出 expired／expires_at，需先唯讀盤點全部 export_type/status、file_purpose/archive_status 及非 null expires_at，再明確規劃 migration 與相容切換；不納入 030。
